# Vestra Player AI (reworking the Plugin Workshop): requirements and implementation plan

Draft of 2026-10-24. Based on two investigations: an investigation of integrating pi, and a feasibility investigation on the maintainer side. `[Decision]` marks items awaiting a user ruling.

## 1. Positioning

The built-in plugin `vestra.workshop` is renamed **Vestra Player AI** and becomes an agentic chat application of the same kind as claude.ai:

- The user talks with the AI; the AI answers directly, or creates and modifies plugins in a sandbox;
- Generated plugins can be trial-loaded and installed into the player with one click;
- Each conversation has its own folder, and the agent can only read and write inside that folder;
- Users bring their own API key (BYOK), managed on a separate settings page;
- The UI is labelled "powered by pi", with pi's logo.

Out of scope: general file management, cloud sync, an account system, a paid proxy.

## 2. Functional requirements

### 2.1 Entry point and window

- The menu entry keeps the position of "Plugin Workshop…", renamed to "Vestra Player AI…".
- Suggested main window size 900×620, minimum 720×480, using the Aurora palette.
- The home screen has a centred logo, one line of hint text and a standard AI input box. Sending the first message switches to the chat view.

### 2.2 Conversation sidebar (left, 220px)

- "+ New Chat"; conversations are grouped into "Today / Earlier"; each item has a "⋯" menu to rename or delete it.
- The conversation title is generated by the AI after the first exchange, and the user can change it.
- Deleting a conversation also deletes its folder, after confirmation.
- At the bottom of the sidebar: ⚙ Settings (opens the BYOK page), and π powered by pi.

### 2.3 Chat area

- **Messages**
  - User messages are right-aligned bubbles;
  - Assistant messages are streamed Markdown, including headings, lists, code blocks and tables;
  - The thinking process is collapsed by default.
- **Tool cards**: for example "Wrote main.ts ✓" or "Type check failed ▸ expand"; expanding shows the details.
- **Result actions**: after a plugin is generated or modified, "Trial Load", "Install", "Open Folder" and "View Files" appear. Installation always goes through host confirmation; on an id conflict the user is asked whether to replace, and it can be rolled back.
- **Input box**
  - Multi-line; Enter sends, Shift+Enter inserts a newline; Enter does not send while a Chinese input method is showing candidates.
  - Has an attachment button (version 1 only supports choosing files) and a model drop-down.
  - After sending, the "Send" button becomes "■ Stop".
- **Errors**: shown in an error bar with "Retry", e.g. invalid key, quota exceeded, network error, timeout.
- **Copy**: every message and every code block has a "Copy" button (Slint cannot select text across messages).

### 2.4 BYOK settings page (Options ▸ Plugins ▸ Vestra Player AI)

- Provider drop-down: Anthropic, OpenAI, Google, OpenRouter, DeepSeek, and "OpenAI-compatible" (custom Base URL, which works with Ollama and LM Studio).
- The API key uses a password field and is saved to the system keychain (the host's `secrets` capability). After saving, only "Saved ••••1234" is shown. The key is never written to files, logs or conversation records.
- Choose the default model; "Test Connection".
- Without a configured key, opening the AI window shows a hint with a button that goes straight to the settings page.

### 2.5 Conversations and files

- **Directory layout**: no hidden directories, and never `.pi/`.
  - `sessions/<sid>/work/<plugin-id>/` holds the plugin source, with the same layout as `plugins/<name>/` in the official plugin repository;
  - `sessions/<sid>/dist/<plugin-id>-<version>.vxp` holds the packed result.
- **Installation**: the install location is managed by the host's package repository, not a directory we choose. The flow is: validate from the `.vxp` → trial load → install (source recorded as workshop); on an id conflict, confirm whether to replace; it can be rolled back.
- **One-click actions for a finished plugin**:
  - "Install": needs host confirmation;
  - "Export .vxp": for sharing;
  - "Export Source Zip": packed in the official plugin repository's layout, without `node_modules` and `dist`, ready to be used for a PR to the official plugin repository;
  - "Open Folder".
  - The zip is produced in pure Node, without calling system commands.

- Conversations are stored in `sessions/<id>/` in the plugin data directory:
  - `work/` is the agent's working directory;
  - The conversation record uses pi's JSONL, and contains no key.
- After closing and reopening, the previous conversation can be continued. When the context gets too long, pi compacts it automatically.

## 3. Technical plan

### 3.1 Integrating pi

- pi is `earendil-works/pi` (formerly `badlogic/pi-mono`), by Mario Zechner, acquired by Earendil in 2026. It is an MIT-licensed, pure TypeScript ESM package that works on Node 22.19 and later; it was tested to load on our Node 26, and has no native modules. The current workshop already uses its `pi-agent-core`/`pi-ai` 1.3.0, only with a mock model.
- Switch to the SDK mode `createAgentSession` of `@earendil-works/pi-coding-agent`, which comes with sessions, compaction, tools and a model catalogue. Pin the version exactly: pi released 5 minor versions in three weeks, with frequent breaking changes.
- **Process structure**: the plugin process handles the UI and the conversation list. The agent runs in a Node child process started by the plugin, and the two communicate with JSON messages. The plugin passes the key read from the keychain to the child process over the message channel, not through environment variables, and does not write `auth.json`.
- **Streaming events**: `message_update` carries text and thinking deltas, `tool_execution_*` maps to tool cards, and `abort()` is used to stop.
- **pi configuration**:
  - Telemetry off (`PI_TELEMETRY=0`, settings kept in memory);
  - Offline mode (`PI_OFFLINE=1`, no downloading of `rg`/`fd` at run time);
  - A custom `ResourceLoader` that discovers no files automatically and never loads `.pi/` extensions from the conversation directory.
- **Package size**: the full dependencies are 149 MB; bundle with esbuild, cutting the TUI and unused providers.

### 3.2 Tools and sandbox

pi itself has no sandbox and does not restrict paths; its official documentation says so explicitly. So all restrictions are ours to implement:

1. Version 1 provides no bash/powershell, only read, write, edit, ls, grep and find. The file-access layer of these tools is replaced with our own implementation: real paths are checked, and anything outside the conversation directory is refused, symbolic links included.
2. Plugin-related operations are custom tools with fixed parameters, with no free shell: `scaffold_plugin`, `typecheck` (reusing the workshop's existing tsc child process), `check_plugin`, `trial_load`, `install_plugin` (needs user confirmation).
3. The agent child process is started with the Node permission model (`--permission`): it can only write the conversation directory, only read the conversation directory and the SDK documentation, and cannot start further child processes. Network access must remain for the LLM calls. Node itself says this is only a "seat belt" against mistakes and cannot stop malicious code.
4. A system-level sandbox (Seatbelt / sandbox-runtime on macOS, a restricted user on Windows) is left for later, when the agent needs a shell, and goes into the host platform modules under the cross-platform rule. `[Decision]` Whether version 1 gives no shell at all.

### 3.3 Knowledge injection

- Make the plugin SDK documentation and examples into fixed context or a skill, kept outside the conversation directory.
- The system prompt states three things: the target is a Vestra plugin, the plugin independence rules must be followed, and the UI is in Chinese.

### 3.4 UI (Slint)

| Part | Current state |
| --- | --- |
| Window, conversation list, virtualised ListView, auto-scroll pinned to the bottom, input box (Enter-to-send based on `UrlInputRow`), copy (`clipboard`), logo (`@image-url`), settings page (`ui.settings`), keychain (`secrets`), opening links | Plugins can do this today |
| Rendering Markdown per message (`MarkdownRef` can currently only be a whole property value and cannot go into a list) | Needs an API extension |
| Rebuilding only the last block while streaming (currently every delta reparses the whole document) | Needs an API extension |
| Syntax highlighting of code blocks, copy callback for code blocks | Needs an API extension |
| Dragging attachments into a tool window | Needs an API extension |
| Continuous text selection across messages, HTML rendering | Slint cannot do this; use each message's "Copy" button, or switch to a read-only TextInput for selection |

Enter handling while a Chinese input method is showing candidates needs verification on real macOS and Windows machines.

## 4. Expected API requests (filed by the workshop author under §4.1, negotiated with the maintainer)

- R-a: `MarkdownRef` can be a field of a list row.
- R-b: incremental Markdown updates.
- R-c: syntax highlighting of code blocks, and a copy callback.
- R-d: drag and drop into tool windows.
- R-e (optional): a selectable mode for Markdown.
- R-f (optional): plugins start Node child processes with restricted permissions. Need to confirm whether a plugin can currently spawn a child process with `--permission`.
- R-g (optional): lightweight in-window notices or system notifications.

Usable today without a request: `secrets`, `settings.page`, `clipboard`, `openUrl`, `fetch`, `fs`, `child_process`.

## 5. User rulings (2026-10-24)

1. **No command line for the agent** (bash/powershell). The system-level sandbox of layer 4 in §3.2 is not planned.
2. **No subscription login for now**. Version 1 only supports API keys and a custom Base URL.
3. **pi logo**: use the official logo from the pi repository's README, with the caption "powered by pi", linked to the pi repository; credit the source in the plugin's `licenses/`.
4. **The package size is acceptable**. Bundling only cuts what is not used: the terminal UI (`pi-tui`), the CLI entry and the SDKs of providers that are not connected. The SDK core capabilities that are used — sessions, compaction, tools, model catalogue, the chosen providers — are all kept.

## 6. Division of work (per the community workflow)

- **Workshop author** (the author of the renamed AI plugin): first write the plugin plan from the §2.1 template, then deliver a vertical slice: one conversation, a real provider, streamed text; then fill in the other features; request missing capabilities under §4.
- **Maintainer**: handles R-a to R-g; confirms whether child process permissions and network access need new capabilities.
- **Interaction lead (coordinator)**: owns consistency of the menu entry and window conventions; does acceptance on real machines, including the Chinese input method.
