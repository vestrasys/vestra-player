# Vestra Player AI（插件工坊改造）：需求与实现方案

2026-10-24 草案。依据两份调查：pi 的集成调查和维护者侧的可行性调查。`[决定]` 是待用户裁决的项目。

## 1. 定位

内置插件 `vestra.workshop` 改名为 **Vestra Player AI**，做成一个与 claude.ai 同类的 agentic 聊天应用：

- 用户和 AI 对话，AI 直接回答，或者在沙箱里新建、修改插件；
- 生成的插件可以一键试载、安装进播放器；
- 每个会话对应一个文件夹，agent 只能在这个文件夹里读写；
- 用户自带 API key（BYOK），在独立的设置页里管理；
- 界面标注「powered by pi」，并配上 pi 的 logo。

不做：通用文件管理、云同步、账号体系、付费代理。

## 2. 功能需求

### 2.1 入口与窗口

- 菜单入口沿用「插件工坊…」的位置，名称改为「Vestra Player AI…」。
- 主窗口建议尺寸 900×620，最小 720×480，用 Aurora 配色。
- 首页是居中的 logo、一句提示和一个标准 AI 输入框。发送第一条消息后进入聊天界面。

### 2.2 会话侧栏（左侧，220px）

- 「+ 新对话」；会话按「今天 / 更早」分组；每项有「⋯」菜单，可以重命名或删除。
- 会话标题在第一轮对话后由 AI 生成，用户可以改。
- 删除会话时同时删除它的文件夹，删除前要确认。
- 侧栏底部：⚙ 设置（打开 BYOK 页），以及 π powered by pi。

### 2.3 聊天区

- **消息**
  - 用户消息显示为右对齐的气泡；
  - 助手消息是流式 Markdown，包括标题、列表、代码块、表格；
  - 思考过程默认折叠。
- **工具卡片**：例如「写入 main.ts ✓」「类型检查未通过 ▸ 展开」，展开后看到细节。
- **结果操作**：生成或修改插件后，出现「试载」「安装」「打开文件夹」「查看文件」。安装必须经过宿主确认，同 id 冲突时询问是否替换，也可以回退。
- **输入框**
  - 多行；Enter 发送，Shift+Enter 换行；中文输入法候选期间按 Enter 不发送。
  - 有附件按钮（第 1 版只支持选文件）和模型下拉。
  - 发送后，「发送」按钮变成「■ 停止」。
- **出错**：显示错误条，带「重试」，例如 key 无效、额度不足、网络错误、超时。
- **复制**：每条消息和每个代码块都有「复制」按钮（Slint 不能跨消息选中文字）。

### 2.4 BYOK 设置页（选项 ▸ 插件 ▸ Vestra Player AI）

- 服务商下拉：Anthropic、OpenAI、Google、OpenRouter、DeepSeek，以及「OpenAI 兼容」（自定义 Base URL，可接 Ollama、LM Studio）。
- API Key 用密码框，保存进系统钥匙串（宿主的 `secrets` 能力）。保存后只显示「已保存 ••••1234」。key 永远不写进文件、日志或会话记录。
- 选择默认模型；「测试连接」。
- 没配 key 时，打开 AI 窗口会提示并带一个直达设置页的按钮。

### 2.5 会话与文件

- 会话存放在插件数据目录的 `sessions/<id>/`：
  - `work/` 是 agent 的工作目录；
  - 会话记录用 pi 的 JSONL，记录里不含 key。
- 关闭后重新打开可以继续上次的会话。上下文过长时 pi 自动压缩。

## 3. 技术方案

### 3.1 pi 的集成

- pi 即 `earendil-works/pi`（原 `badlogic/pi-mono`），作者 Mario Zechner，2026 年被 Earendil 收购。它是 MIT 许可的纯 TypeScript、ESM 包，Node 22.19 以上可用，在我们的 Node 26 上实测能加载，没有原生模块。现在的工坊已经在用其中的 `pi-agent-core`/`pi-ai` 1.3.0，只是模型换成了 mock。
- 改用 `@earendil-works/pi-coding-agent` 的 SDK 模式 `createAgentSession`，它自带会话、压缩、工具、模型目录。版本锁到精确值：pi 三周发了 5 个小版本，breaking 改动频繁。
- **进程结构**：插件进程负责界面和会话列表。agent 跑在插件启动的 Node 子进程里，两边用 JSON 消息通信。插件把从钥匙串读到的 key 经消息通道交给子进程，不走环境变量，也不写 `auth.json`。
- **流式事件**：`message_update` 携带文本和思考的增量，`tool_execution_*` 对应工具卡片，`abort()` 用于停止。
- **pi 的配置**：
  - 关闭遥测（`PI_TELEMETRY=0`，设置放在内存里）；
  - 离线模式（`PI_OFFLINE=1`，不在运行时下载 `rg`/`fd`）；
  - 自定义 `ResourceLoader`，不自动发现任何文件，绝不加载会话目录里的 `.pi/` 扩展。
- **包体积**：完整依赖 149 MB，要用 esbuild 打包，裁掉 TUI 和不用的服务商。

### 3.2 工具与沙箱

pi 本身没有沙箱，路径也不做限制，官方文档明确说明了这一点。所以限制全部由我们来做：

1. 第 1 版不提供 bash/powershell，只给 read、write、edit、ls、grep、find。这些工具的文件访问层换成我们自己的实现：对真实路径做检查，会话目录以外一律拒绝，符号链接也算。
2. 插件相关的操作做成固定参数的自定义工具，不开放自由的 shell：`scaffold_plugin`、`typecheck`（复用工坊现有的 tsc 子进程）、`check_plugin`、`trial_load`、`install_plugin`（需要用户确认）。
3. agent 子进程用 Node 权限模型启动（`--permission`）：只能写会话目录，只能读会话目录和 SDK 文档，不能再开子进程。网络要保留给 LLM 调用。Node 官方说这只是「安全带」，防误操作，防不住恶意代码。
4. 系统级沙箱（macOS 的 Seatbelt / sandbox-runtime，Windows 的受限用户）放到以后，在需要给 agent 开 shell 时再做，按跨平台规则放进宿主平台模块。`[决定]` 第 1 版是否完全不给 shell。

### 3.3 知识注入

- 把插件 SDK 的文档和示例做成固定的上下文或 skill，放在会话目录之外。
- 系统提示写明三点：目标是 Vestra 插件，必须遵守插件独立规则，使用中文界面。

### 3.4 界面（Slint）

| 部分 | 现状 |
| --- | --- |
| 窗口、会话列表、虚拟化 ListView、贴底自动滚动、输入框（Enter 发送参考 `UrlInputRow`）、复制（`clipboard`）、logo（`@image-url`）、设置页（`ui.settings`）、钥匙串（`secrets`）、打开链接 | 插件现在就能做 |
| 每条消息各自渲染 Markdown（`MarkdownRef` 目前只能作为整个属性值，放不进列表） | 需要 API 扩展 |
| 流式时只重建末尾的块（目前每次增量都整篇重解析） | 需要 API 扩展 |
| 代码块语法高亮、代码块复制回调 | 需要 API 扩展 |
| 把附件拖进工具窗口 | 需要 API 扩展 |
| 跨消息连续选中文字、HTML 渲染 | Slint 做不到；用每条消息的「复制」按钮，或切换成只读 TextInput 来选择 |

中文输入法候选期间的 Enter 处理，需要在 macOS 和 Windows 真机上验证。

## 4. 预计的 API 请求（由工坊作者按 §4.1 提交，维护者协商）

- R-a：`MarkdownRef` 可以作为列表行的字段。
- R-b：Markdown 增量更新。
- R-c：代码块语法高亮，以及复制回调。
- R-d：工具窗口拖放。
- R-e（可选）：Markdown 可选中模式。
- R-f（可选）：插件以受限权限启动 Node 子进程。要确认现在插件 spawn 带 `--permission` 的子进程是否可行。
- R-g（可选）：窗口内轻提示或系统通知。

不需要请求、现在就能用的：`secrets`、`settings.page`、`clipboard`、`openUrl`、`fetch`、`fs`、`child_process`。

## 5. 待用户裁决

1. **shell**：第 1 版不给 agent shell（推荐）？
2. **服务商**：第 1 版只支持 API key 和自定义 Base URL，不做 ChatGPT、Claude、Copilot 订阅登录（推荐，订阅登录是否允许第三方应用使用要看服务商条款）？
3. **pi logo**：pi 没有公开的商标和品牌使用条款，MIT 只覆盖代码。是否先联系 Earendil 获得许可（推荐），拿到许可前只用文字「powered by pi」？
4. **包体积**：裁剪后插件体积的上限是多少（现在 dist 是 23 MB）？

## 6. 分工（按社区流程）

- **工坊作者**（改名后的 AI 插件作者）：先按 §2.1 模板写插件方案，再出纵向切片：一个会话、真实服务商、流式文本，然后补齐其它功能；缺的能力按 §4 提请求。
- **维护者**：处理 R-a 到 R-g；确认子进程权限和网络是否需要新能力。
- **交互负责人（协调者）**：负责菜单入口和窗口规范的一致性；真机验收，其中包括中文输入法。
