# Vestra Player AI: current state and improvement roadmap

Compiled on 2026-10-24. Based on: the requirements and rulings ([vestra-ai.md](vestra-ai.md)), PR #4 (2.0.0 → 2.1.2) and today's tests on a real machine. Work is divided per the community workflow: plugin code belongs to the AI plugin author, and needed APIs go through §4 requests.

## 1. Current state (2.1.2, merged into main)

**What exists**

- Conversations: "New Chat" and the conversation list in the sidebar; one folder per conversation; after quitting and reopening, the chat continues.
- Agent: pi-coding-agent 1.4.0, about 4.8 MB after bundling, running in a child process restricted with `--permission`.
  - Only read/write/edit/ls/find/grep, no command line.
  - The file layer only accepts the conversation directory, and refuses symbolic links and files whose names start with a dot.
  - Telemetry and auto-discovery are off; pi's User-Agent is not changed.
- Providers: the 23 pay-as-you-go providers in pi's catalogue, plus the two entries "Custom · OpenAI / Anthropic format", all of which support "Fetch Models".
  - The key is stored in the keychain, passed to the child process only over IPC, and never written to any file.
  - All coding plans and subscription-type providers have been removed.
- UI:
  - Each message is displayed as Markdown (R-a); code blocks can be copied; links only open http(s); remote images are never loaded.
  - Streamed replies, refreshed every 100 ms.
  - Tool calls are merged into one scrolling status line (Thinking… → Wrote x ✓ → Replying…), which can be expanded after the turn ends to see everything.
  - Errors are shown by category: invalid key, model unavailable, network, keychain unreadable, with "Retry" or "Open Settings" as appropriate.
- Robustness:
  - The keychain is not touched at startup, and the plugin runs normally when authorisation is denied.
  - The model shown on the settings page is the model actually used.
  - When a provider is removed, the user is told; it is not silently replaced with another.

**What does not exist yet (from phase 3)**

- The system prompt is only three lines and feeds in no SDK documentation. The model can only write Vestra plugins from general knowledge and easily invents APIs that do not exist.
- The agent has no plugin-related tools: it cannot type-check, run tests, pack, trial-load, install or export. The old workshop's "tsc → trial load → install → roll back" chain was removed in the rework.

## 2. Improvement directions

In priority order. P0 decides whether the AI can write plugins that work; P1 decides whether users can take the result away; P2 is experience and long-term maintenance.

### P0-A Feed documentation: let the model know how to write Vestra plugins

- **The SDK provides a "reference for AI to read"** (SDK maintainer, SDK patch):
  - Generate `llms.txt` / `llms-full.txt` in the package, containing the API signatures, the capability table, manifest rules, the §1 plugin independence rules, common error codes, and the source and key points of the 8 atomic examples.
  - Generated by a script from TSDoc and `docs/`, updated with each version; no second hand-written copy.
- **How the AI plugin uses it**:
  - The reference documentation, `.d.ts` files and examples are placed in a read-only location outside the conversation directory (the child process only has read permission).
  - The system prompt requires: check the documentation before writing code; for an uncertain API, first read the corresponding `.d.ts`; do not use APIs that are not in the documentation.
  - The system prompt contains a condensed checklist (directory structure, manifest template, `activate` skeleton, capability names); details are read on demand instead of filling the context at once.
- **Project template**: `scaffold_plugin` generates the same structure as `plugins/<name>/` in the official plugin repository, with an id using the user's own prefix `<GitHub username>.<name>`; `vestra.` cannot be used (the host refuses it).

### P0-B One complete "write → check → test → try" chain

Implemented as custom tools with fixed parameters, run in the plugin process (privileged operations are not handed to the restricted child process), returning results to the agent as structured text so it can loop and fix its own errors:

| Tool | What it does | Result |
|---|---|---|
| `scaffold_plugin{id,name}` | Generates a skeleton from the template | List of generated files |
| `typecheck{id}` | Runs tsc with the plugin's bundled typescript, with types from the SDK bundled with the player | File, line, error code, message |
| `test{id}` | Runs the plugin's own tests (SDK TestHost) in a new restricted child process | Names of passed/failed tests and assertion messages |
| `check{id}` / `pack{id}` | Runs `vestra-plugin check/pack` with the plugin's bundled SDK CLI (the alternative to R-h) | Manifest diagnostics; `dist/<id>-<ver>.vxp` |
| `trial_load{id}` | `packages.validateArchive` → `candidate.trial()` | Activation succeeded or failed; failures include the host error code and a log excerpt |
| `install_plugin{id}` | Confirm in the UI first, then host confirmation; on conflict ask whether to replace; can be rolled back | Install result |

- The definition of "done" goes into the system prompt: typecheck with 0 errors, all tests passing, check passing, then prompt the user to trial-load.
- Every tool call has a timeout and an output limit, and can be cancelled (reusing the old workshop's tsc child process approach).
- During a trial load the plugin really runs inside the player; the UI needs a "Stop Trial", and leaving the trial rolls back automatically.

### P0-C Evaluation: know whether a change makes things better or worse

- Prepare a fixed set of tasks, for example:
  - a panel that shows the playback duration;
  - a watermark on snapshots;
  - speed shortcuts;
  - a subtitle delay adjustment window;
  - listing chapters in the sidebar;
  - a plugin with a settings page.
- Record for each task whether it "passes first time", and how many rounds of fixes it needs to pass (typecheck, test, trial load).
- Running with a real model spends the user's quota, so it is run by hand only when the prompt or tools change, and the results go into this round's record.
- Regression tests against a mock server stay in CI as usual.

### P1-A Delivering the result

- "Export .vxp" and "Export Source Zip": the zip is a complete plugin project, with README, tests and release CI, and can be turned directly into the user's own GitHub repository (user ruling).
- Listing: submit a `registry/<id>.toml` entry to the official plugin repository. The official plugin repository still needs "build third-party plugins from source", which is a to-do of the plugin repository infra; without it the entry cannot be merged.
- "Open Folder" and "View Files": first a read-only file list and content view; change comparison (diff) comes later.

### P1-B Conversation experience

- "Retry" currently sends the user message again, so the record contains two identical ones. pi 1.4 has no regenerate interface; this needs another look, or we roll back from the conversation branch ourselves.
- Renaming and deleting conversations: deleting a conversation also deletes its folder, after confirmation.
- Chinese input method: Enter must not send while the candidate window is open. Not yet tested on a real machine.
- Acceptance of "Stop" on a real machine.
- Attachments: first "Choose File"; dragging into the tool window waits for R-d.
- When a long conversation exceeds the limit, only the latest 200 lines are sent, with a note at the top that "N earlier messages are not shown".

### P2 Maintenance and security

- **Outdated model catalogue**: pi's bundled catalogue falls behind; for example MiniMax has retired M2.7, but its own `/models` still lists it. So the default model should prefer the newer one in the "fetched list". The plugin should be allowed to update the catalogue with its versions, while keeping the ability to enter a model by hand.
- **Upgrading pi**: the version is pinned exactly; an upgrade must rerun the bundle comparison, the User-Agent test, the sandbox tests and the evaluation tasks.
- **Keychain authorisation in development builds**: every re-signing shows an authorisation prompt, and reading the old key asks for the login password; this only affects development and testing. Once release signing is fixed it only appears the first time. Tests avoid it by using a new data directory.
- **The host's `secrets.get` has no timeout**: the plugin no longer waits for it, but the UI stays at "Reading" forever. The maintainer decides whether keychain calls get a timeout.
- **Security baseline** (kept):
  - No command line; the child process can only read and write this conversation's directory;
  - Remote images are not loaded, links only open http(s);
  - The key never touches disk and never enters the conversation record;
  - The User-Agent is not changed;
  - Installation always requires user confirmation.
- **Layout regressions**: the AI author built an offline rendering tool in the scratchpad that captures the layout at various sizes. It is worth asking the maintainer to turn it into a "plugin layout render test" in the host, so that CI catches overlaps, stretched buttons and similar problems when a plugin changes its UI.
