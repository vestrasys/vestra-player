# Vestra Player AI：现状与优化路线

2026-10-24 整理。依据：需求与裁决（[vestra-ai.md](vestra-ai.md)）、本轮记录（[2026-10-vestra-ai.md](../process/rounds/2026-10-vestra-ai.md)）、PR #4（2.0.0 → 2.1.2）和今天的真机测试。按社区流程分工：插件代码归 AI 插件作者，需要的 API 走 §4 请求。

## 1. 现状（2.1.2，已合并进 main）

**已经有的**

- 会话：侧栏「新对话」和会话列表，每个会话一个文件夹，退出重开后接着聊。
- agent：pi-coding-agent 1.4.0，打包后约 4.8 MB，在 `--permission` 受限子进程里运行。
  - 只有 read/write/edit/ls/find/grep，没有命令行。
  - 文件层只认会话目录，拒绝符号链接和以点开头的文件。
  - 关闭遥测和自动发现，不改 pi 的 User-Agent。
- 服务商：pi 目录里 23 个按量付费的服务商，加「自定义 · OpenAI / Anthropic 格式」两项，都能「获取模型」。
  - key 存在钥匙串里，只经 IPC 传给子进程，不写入任何文件。
  - 去掉了所有编程套餐和订阅类服务商。
- 界面：
  - 每条消息用 Markdown 显示（R-a），代码块可以复制，链接只打开 http(s)，远程图片一律不加载。
  - 流式回复，每 100 ms 刷新一次。
  - 工具调用合成一行滚动状态（思考中… → 写入 x ✓ → 回复中…），本轮结束后可以展开看全部。
  - 出错分类显示：key 无效、模型不可用、网络、读不到钥匙串，按情况给「重试」「打开设置」。
- 健壮性：
  - 启动时不碰钥匙串，授权被拒绝时插件照常运行。
  - 设置页显示的模型就是实际使用的模型。
  - 服务商被移除时会提示，不悄悄改成别的。

**还没有的（第 3 阶段起）**

- 系统提示只有三行，没有喂任何 SDK 文档。模型只能凭通用知识写 Vestra 插件，很容易编出不存在的 API。
- agent 没有插件相关的工具：不能类型检查、跑测试、打包、试载、安装、导出。旧工坊的「tsc → 试载 → 安装 → 回退」链路在改造时已删除。

## 2. 优化方向

按优先级排列。P0 决定 AI 能不能写出能用的插件；P1 决定用户能不能把成品带走；P2 是体验和长期维护。

### P0-A 喂文档：让模型知道 Vestra 插件怎么写

- **SDK 提供「给 AI 读的参考」**（SDK 维护者，SDK patch）：
  - 在包里生成 `llms.txt` / `llms-full.txt`，内容是 API 签名、能力表、manifest 规则、§1 插件独立规则、常见错误码、8 个原子示例的源码和要点。
  - 由脚本从 TSDoc 和 `docs/` 生成，跟随版本更新，不手写第二份。
- **AI 插件的接入方式**：
  - 参考文档、`.d.ts` 和示例放在会话目录之外的只读位置（子进程只有读权限）。
  - 系统提示要求：先查文档再写代码；不确定的 API 先 read 对应的 `.d.ts`；不许使用文档里没有的 API。
  - 系统提示里放一份精简清单（目录结构、manifest 模板、`activate` 骨架、能力名），详细内容按需读取，不一次性塞满上下文。
- **项目模板**：`scaffold_plugin` 生成与官方插件仓库 `plugins/<name>/` 相同的结构，id 用用户自己的前缀 `<GitHub 用户名>.<名字>`，不能用 `vestra.`（宿主会拒绝）。

### P0-B 一条完整的「写 → 查 → 测 → 试」链路

做成参数固定的自定义工具，在插件进程里执行（特权操作不交给受限子进程），结果用结构化文本返回给 agent，让它能自己循环修错：

| 工具 | 做什么 | 结果 |
|---|---|---|
| `scaffold_plugin{id,name}` | 按模板生成骨架 | 生成的文件列表 |
| `typecheck{id}` | 用插件自带的 typescript 跑 tsc，类型来自播放器自带的 SDK | 文件、行、错误码、信息 |
| `test{id}` | 在新的受限子进程里跑插件自己的测试（SDK TestHost） | 通过/失败的测试名和断言信息 |
| `check{id}` / `pack{id}` | 用插件自带的 SDK CLI 跑 `vestra-plugin check/pack`（R-h 的替代方案） | manifest 诊断；`dist/<id>-<ver>.vxp` |
| `trial_load{id}` | `packages.validateArchive` → `candidate.trial()` | 激活成功或失败，失败带宿主错误码和日志片段 |
| `install_plugin{id}` | 先在界面确认，再走宿主确认，冲突时询问替换，可回退 | 安装结果 |

- 「完成」的标准写进系统提示：typecheck 0 错误、test 全过、check 通过，再提示用户试载。
- 每次工具调用都有超时、输出上限，可以取消（复用旧工坊的 tsc 子进程做法）。
- 试载时插件真实运行在播放器里，界面上要有「停止试载」，退出试载后自动回退。

### P0-C 评估：知道改动是变好还是变坏

- 准备一组固定题目，例如：
  - 显示播放时长的面板；
  - 截图加水印；
  - 倍速快捷键；
  - 字幕延迟调节窗口；
  - 在侧栏列出章节；
  - 一个带设置页的插件。
- 记录每题是否「一次过」，以及要修几轮才过（typecheck、test、试载）。
- 用真实模型跑会花用户的额度，所以只在改提示词或工具时手动跑，结果记进本轮记录。
- 用 mock 服务器的回归测试照常放在 CI 里。

### P1-A 成品交付

- 「导出 .vxp」「导出源码 zip」：zip 是完整的插件项目，含 README、测试、发布用 CI，可以直接建成用户自己的 GitHub 仓库（用户裁决）。
- 上架：到官方插件仓库提交 `registry/<id>.toml` 登记。官方插件仓库那边还要补上「从源码构建第三方插件」，属于插件仓库 infra 的待办，不然登记合并不了。
- 「打开文件夹」「查看文件」：先做只读的文件列表和内容查看；改动对比（diff）再往后放。

### P1-B 对话体验

- 「重试」现在会把用户消息再发一次，记录里出现两条一样的。pi 1.4 没有 regenerate 接口，需要再查一次，或者自己从会话分支里回退。
- 会话的重命名、删除：删除会话要连带删除文件夹，删除前确认。
- 中文输入法：候选框开着时按 Enter 不能发送。这一项还没在真机上测。
- 「停止」的真机验收。
- 附件：先做「选择文件」；拖进工具窗口要等 R-d。
- 长会话超过上限时，只发最近 200 行，最前面提示「更早的 N 条没有显示」。

### P2 维护与安全

- **模型目录过时**：pi 自带的目录会落后，比如 MiniMax 已下线 M2.7，但它自己的 `/models` 仍然列出。所以默认模型应该优先选「获取到的列表」里较新的那个。要允许插件随版本更新目录，同时保留手填模型的能力。
- **pi 升级**：版本锁死为精确版本，升级时要重跑打包对比、User-Agent 测试、沙箱测试和评估题。
- **开发版的钥匙串授权**：每次重新签名都会弹授权框，读旧 key 要登录密码，这只影响开发和测试。正式发布签名固定后只在第一次出现。测试时用新的数据目录绕开。
- **宿主 `secrets.get` 没有超时**：插件已经不等它，但界面会一直停在「正在读取」。由维护者决定要不要给钥匙串调用加超时。
- **安全底线**（继续保持）：
  - 不给命令行；子进程只能读写本会话目录；
  - 远程图片不加载，链接只打开 http(s)；
  - key 不落盘、不进会话记录；
  - 不改 User-Agent；
  - 安装必须经过用户确认。
- **布局回归**：AI 作者在 scratchpad 里做了离线渲染工具，能截出各种尺寸下的布局。值得请维护者做成宿主里的「插件布局渲染测试」，以后插件改界面时 CI 就能发现重叠、被拉大的按钮这类问题。

## 3. 下一步

1. 请 SDK 维护者评估并实现 `llms.txt`（P0-A）。
2. 请 AI 插件作者写第 3 阶段方案：P0-A 的接入、P0-B 的工具链、P0-C 的评估题，以及 P1-A。方案按 §2.1 模板写，需要的 API 按 §4.1 提请求。
3. 方案经协调者审过、报用户同意后开工。每个阶段都做真机验收：用真实模型写一个插件，跑通「试载 → 安装 → 使用 → 导出」。
