# Vestra Player: technical decisions

This document records the technical choices, responsibility boundaries and the reasons for the choices. Project principles are in [Project direction](direction.md), the internal structure of the host in the [Architecture overview](../architecture/README.md), and the plugin API on the [SDK documentation site](https://vestrasys.github.io/vestra-player-sdk/).

## 1. Goals and constraints

The project aims to offer a rich control experience while letting users combine and extend features. The main investment is in interaction, feature organisation and the plugin ecosystem; decoding, sync and rendering reuse mature infrastructure as far as possible.

The choices must serve the following principles:

- **Everything is a plugin**: the core keeps only the infrastructure needed for running and cooperation; user features are provided by plugins.
- Official plugins and third-party plugins use the same public API; being official grants no access to host internal objects.
- Plugin authors do not need to understand Rust internal classes, window controllers or backend object structures.
- First-party Rust forbids `unsafe`; native capabilities come in through safe wrappers or process boundaries.
- Lower the cost of plugin development and allow complex, good-looking native UIs; reuse a mature GUI library instead of building our own GUI framework or layout language.
- The default plugins combine into a player that works out of the box, and users can replace and extend them; a plugin store is not a precondition for the architecture.

## 2. Technology stack

| Layer | Choice | Responsibility |
| --- | --- | --- |
| Host | Rust | Playback backend integration, video presentation, authoritative playback state, UI composition, plugin lifecycle |
| UI | Slint 1.16 (slint-interpreter) | Native windows, widgets, layout; plugin `.slint` files are compiled by the host at run time, so end users do not need a Rust toolchain |
| Plugins | TypeScript, one Node process per plugin (Node 26 bundled with the player) | User features, UI behaviour, command and event handling; can use the Node standard library, network, file system and npm dependencies |
| Plugin API | SDK v2 (handle-based) | The only API plugins see; protocol details are kept inside the SDK |
| Playback | libmpv, through the rsmpv safe wrapper | Decoding, sync, real-time filters, subtitles |
| Export | FFmpeg offline worker process | Snapshots, clip export, with separate decoding that does not affect playback |
| Plugin audio / video streams | cpal audio output + bounded frame queue | Picture and sound generated by plugins (such as NES) |

Slint `.slint` files express the UI, and TS handles behaviour; only data (property values and callbacks) passes between them, never functions or component objects.

## 3. Why Slint

The host connects a mature GUI library so that plugin authors use its UI language, layout, widgets and styles directly, instead of redesigning a widget API. With Slint, Rust can own the native windows while plugin behaviour stays in TS, without moving the core to a Web UI or building a wrapper such as egui-to-TS.

React/Web UI, egui wrappers and others were candidates and were not adopted. Not every candidate got an equal experiment here, so the choice is not a general conclusion about other frameworks.

Accepted costs: plugin authors write both `.slint` and TS; the cross-language property and callback connection is adapted by the host and the SDK (names are converted automatically, with the same rules as Vue props).

## 4. Responsibility boundary between the core and plugins

"Playback features are provided by plugins" means the product features with which users start and control playback are organised by plugins; it does not mean moving the decoder, the playback clock or the window lifecycle out of the core.

| Capability | Owner |
| --- | --- |
| Decoding, playback clock, audio / video sync | libmpv; the host integrates it and provides the capabilities |
| Current media, position, pause state | The host maintains the authoritative state; plugins subscribe to the actual results |
| Playback window, video presentation, keeping playback while the UI is rebuilt | Host |
| Opening files, the playback bar, the playlist, subtitle management, etc. | Plugins (including default plugins) |
| Filter execution | libmpv / FFmpeg; plugins only give a typed processing chain and do not process pixels frame by frame |
| Site parsing, download policy, save states, presets | Plugins |
| Cross-session persistence | Not implemented yet (the host provides the basic capability, policy belongs to plugins) |

Plugins do not need every I/O to go through the host: reading files and accessing the network use Node directly. The host file dialog is only a convenience service. Plugins are trusted; there is no permission sandbox.

```ts
// Opening a file: plugin behaviour
const path = await plugin.dialogs.openFile({ title: "Open Media" });
if (path) await plugin.player.open(path);

// Configuring a filter: the plugin gives a processing chain, the playback backend executes it
plugin.video.filter("blur").set([{ kind: "gblur", sigma: 3, steps: 3 }]);
```

## 5. How plugin UIs are integrated

- **Tool windows**: the host compiles the plugin's `.slint` in process with the interpreter into a separate window. Compiling needs no Rust compiler.
- **Bottom bar / sidebar panels**: the host imports the panel component into the main UI and compiles it as a whole. Mounting a panel that was not known beforehand for the first time requires rebuilding the main UI: the playback backend, plugin processes and cached UI properties are kept and playback is not interrupted, but there may be a short stall or flicker. Ordinary show / hide does not recompile.
- A hidden panel component is destroyed and rebuilt when shown again: state the plugin keeps in TS is restored, while state that exists only inside the component (focus, scroll position) is not kept automatically.
- Slint's `ComponentContainer` dynamic embedding interface is still behind the interpreter's internal feature and is not used for now.

## 6. Still to be designed and verified

| Area | Current state |
| --- | --- |
| Plugin failure recovery | When a plugin process crashes the host reclaims its resources and playback continues; automatic restart and notification are not designed yet |
| State persistence | Not implemented |
| API version policy | Official version `vestra/1` (switched over once from the experimental version, old values not compatible); incompatible changes will be released as a new major version; currently a single version, with no multi-version negotiation |
| Plugin management UI | The host can install / roll back, but there is no user-facing management UI yet |
| Hardware decoding and GPU rendering path | Currently libmpv software rendering |

The technical direction is settled; specific capabilities evolve with the needs of real plugins ([community workflow](../../agentic-workflow.md)).
