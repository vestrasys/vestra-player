# Plugin ecosystem: standalone SDK, plugin repository and Plugin Store

> **User ruling (2026-10-24): plugin categories**
> - **Official plugins are only the built-in plugins shipped in the player's main repository**, with ids `vestra.<name>`; the `vestra.` prefix is reserved for built-in plugins.
> - All other plugins **are third-party plugins**, including the plugins in the `plugins/` directory of the official plugin repository (vestra-player-plugins). They are only hosted in the official repository, with stricter review. Their ids follow the rule `<GitHub user or organization>.<name>`; the existing youtube and bilibili become `zysilm.youtube` and `zysilm.bilibili`, with zysilm as the author.
> - The player has not been released publicly, so the id change needs no migration.
> - Where the text below says "official plugin", this ruling applies; leftover older wording will be changed over time.


Date: 2026-10-21. This document collects the conclusions of the discussion so far and gives the implementation steps. The details of the Plugin Store are not final yet; the SDK split and the repository split are settled.

## 1. Conclusions (all settled on 2026-10-21)

### 1.1 Overall direction

- Follow the Dalamud model: no backend, no database, no account system.
  - The official repository is hosted on GitHub; authors submit plugins through PRs, and CI builds and publishes them.
  - Third parties can run their own repositories; users paste the repository address to use one.
- The client understands only one static JSON index, `index.json` (optionally with a signature `index.json.sig` next to it), and does not care where it is hosted. When adding a repository, the user pastes the repository root address and the client reads the `index.json` under it; pasting the full address of `index.json` also works.
- If we run our own server later:
  - it serves the same `index.json` at the same address, and the client does not change;
  - extra capabilities (server-side search, download statistics, update queries) are described in the `extensions` field of `index.json`; the client uses them when it finds them and falls back to static behavior otherwise.
- Author self-publishing, accounts and ratings are all on the server side; they will be done with GitHub OAuth when needed and do not affect the client protocol.

### 1.2 Division between the two kinds of metadata

| File | Written by | Content |
| --- | --- | --- |
| `manifest.json` inside the plugin package | The plugin author | The plugin's own information: `id`, `version`, `apiVersion`, `capabilities`, `entry`. Plus new optional display fields: `name`, `author`, `punchline` (one-sentence summary), `description`, `tags`, `icon` (path of a PNG/JPEG inside the package), `readme` (default `README.md`), `changelog`, `sourceUrl`, `license` |
| The repository's `index.json` | Generated by a tool or CI, normally not written by hand | Collects the display fields of each plugin's manifest and adds the information only the repository knows: per version `downloadUrl`, `sha256`, `size`, `published` (plus `apiVersion`, `minPlayerVersion`, `capabilities`, used by the store for filtering and the detail page), version history, public URLs of the icon and README, repository name, `official`, `revoked`, `extensions`, signature. No release channels and no download counts (1.6 items 8 and 9) |

- Authors publishing to the official repository write only `manifest.json`, and add or change the registry file `registry/<plugin id>.toml` (see 1.3a) in their PR, giving the source repository, commit and owners.
- Authors of their own repositories generate `index.json` with a tool (`vestra-repo build`, or the GitHub Actions template we provide).
- Authors who only want to publish one package need no repository: users paste the package link directly, or drag in the package file to install.

### 1.3 `index.json` draft (schema 1)

```json
{
  "schema": 1,
  "name": "Vestra Player official repository",
  "official": true,
  "plugins": [
    {
      "id": "vestra.youtube",
      "name": "YouTube", "author": "Vestra Player", "punchline": "…", "description": "…",
      "tags": ["online video"], "license": "Apache-2.0",
      "iconUrl": null, "readmeUrl": "…", "changelogUrl": "…", "sourceUrl": "…",
      "versions": [
        { "version": "0.2.0", "apiVersion": "vestra/1", "minPlayerVersion": "0.2.0",
          "capabilities": ["commands", "…"],
          "downloadUrl": "…", "sha256": "…", "size": 9370, "published": "2026-10-21T…Z" }
      ]
    }
  ],
  "revoked": [
    { "id": "someone.cool-visualizer", "versions": ">=1.0.0 <1.2.0", "reason": "…" }
  ],
  "extensions": {}
}
```

- Plugin-level fields come from the manifest of the latest version; fields the manifest does not set are `null` (`tags` is `[]`, `name` is the id). `versions` is ordered newest first.
- No `channel` and no `downloadCount` (1.6 items 8 and 9); download statistics from a future server go into `extensions`.
- `revoked` is a verbatim copy of the hand-written `revoked.json` in the repository; `versions` is an exact version or a range (comparators `<`, `<=`, `>`, `>=`, `=` joined by spaces, `||` between alternatives, `*`); the syntax is in the plugin repository's CONTRIBUTING.

- Integrity is guaranteed by `sha256`, independent of the host.
- The official repository's `index.json` is signed by CI; the signature is kept separately in `index.json.sig` in the same directory, so the JSON structure does not change; the client verifies it with a built-in public key.
- Third-party repositories are marked "unofficial" in the interface, and the repository a plugin comes from is shown.

### 1.3a Registry file of the official repository: `registry/<plugin id>.toml`

The official plugin repository has one registry file per plugin, named after the plugin id. Only the official repository's CI reads it; the player does not.

```toml
# registry/someone.cool-visualizer.toml
repository = "https://github.com/someone/cool-visualizer"
commit = "3f2a9c1…"
path = "."            # subdirectory of the plugin in the source repository
owners = ["someone"]
```

- To release a new version, the author changes only `commit`; the PR is usually a one-line change.
- No `channel` (1.6 item 8); all other unknown keys are rejected.
- It is not called `manifest.toml`: its purpose is completely different from the `manifest.json` in the plugin package, and similar names are easy to confuse (Dalamud uses `manifest.toml`). TOML is used because it is written by hand and can carry comments.

The division between the three files:

| File | Location | Read by |
| --- | --- | --- |
| `manifest.json` | In the plugin package | The player |
| `registry/<id>.toml` | In the source of the official plugin repository | The official repository's CI |
| `index.json`, `index.json.sig` | Under the published repository address | The store plugin |

### 1.3b Naming and references

"Static index + user-added third-party sources" is a common pattern, not unique to Dalamud: apt/yum software sources (index, checksums, signatures, third-party sources), Helm chart repositories (static `index.yaml`, the user enters the repository root address), the Jellyfin and Kodi plugin repositories, the Obsidian community plugin list (built by the authors themselves), Flathub and Homebrew (official CI builds from source). Following Helm, the index file is named `index.json`; the `repo.json` of the earlier draft was easy to read as repository configuration and has been renamed.

### 1.4 Client (player)

- The store is a plugin that extends the existing `plugins` plugin; it is not in the core.
  - The interface follows VS Code: list on the left, details on the right. The detail page renders the README and shows versions and the changelog (no download counts, see 1.6 item 9). Plugins without an icon show the Vestra Player logo.
  - Downloads use Node's `fetch`, check `sha256`, then call the existing `plugin.packages.validate(directory).install()` for hot installation. Hot uninstall, disable and rollback use the existing APIs.
  - Install sources: the official repository, third-party repository addresses (added in settings), plugin package links, dragging in a plugin package file.
- The core needs only two small changes:
  1. built-in plugins cannot be uninstalled but can be disabled;
  2. the host and SDK manifest validation accepts the display fields of 1.2 and checks their format.

  The index signature is first verified by the store plugin; moving this into the core can be considered later.

### 1.5 Standalone SDK

- The SDK is published to npm, and all plugins (including built-in plugins) reference it as an npm package: `import type { Plugin } from "@vestra-player/sdk"`. The `../../sdk/...` relative paths are no longer used, and the Plugin Workshop no longer copies the SDK.
- Contents of the npm package:
  - the plugin API types;
  - `TestHost` (`@vestra-player/sdk/testing`);
  - the command-line tools `vestra-plugin` (check / build / test / pack) and `vestra-repo build` (generates `index.json`);
  - read-only copies of the Slint widget library and theme (`@vestra/widgets.slint`, `theme.slint`), so authors can compile and preview in their IDE.
- Plugin template: `npm create vestra-plugin`.
- Version alignment: `@vestra-player/sdk@1.x` corresponds to `apiVersion: "vestra/1"`. Breaking changes bump the major version.
- **The runtime is not distributed with the npm package**:
  - At run time the player depends on two things: the Rust host program and Node.js. Each plugin is a Node process; the host runs `node runtime/runner.ts <plugin directory>`.
  - The runner, the SDK implementation code and `wire.ts` (the internal protocol between host and plugins) are distributed with the player, not published to npm, and carry no public promise.
  - Plugin build output references only types and contains no SDK code, so the split does not change how plugins run.

### 1.5a Plugin identity: the human-written id and the install-instance GUID (settled 2026-10-21)

**The human-written id** (`id` in the manifest)

- **The host does not change its rules**: it keeps the existing character check (letters, digits, `.-_`), enforces no namespace and reserves no prefix. The host gives no id special treatment; built-in plugins being impossible to uninstall or replace, and the official and unofficial marks, are all decided by **source** (installer package, which repository, whether signed), not by id. So a third-party plugin that writes its id as `vestra.xxx` gains nothing.
- **Uniqueness is guaranteed only by the official plugin repository** (CI plus review): a third-party registered id must be `<GitHub user name or organization name>.<plugin name>`, and the prefix must equal the owner of the source repository in `registry/<id>.toml`; after the first registration the id is bound to `owners`, and later PRs that change this registry file must be submitted by an owner. `vestra.` is only for the official plugins shipped in the plugin repository.
- Name clashes and impersonation between third-party repositories are the user's own responsibility (the user chose to add the repository); we do not coordinate them. Data is never overwritten across plugins; see the install-instance GUID below.
- SDK: `npm create vestra-plugin` fills in `<GitHub user name>.<directory name>` by default; `vestra-plugin check` only gives a hint, not an error, for ids without a prefix.
- After moving to the plugin repository, `youtube` and `bilibili` become `vestra.youtube` and `vestra.bilibili` (following the repository rule); `audio` (and `nes` until 2026-10-27, when it moved to the plugin repository as VestraNES, `zysilm.vestranes`), which stay in the main repository, become `vestra.audio` (and `vestra.nes`) for consistency (the host does not require it). Not released yet, so old settings are not migrated.
- Having the host enforce the format and reserve the `vestra.` prefix was considered and dropped: uniqueness, protection against overwriting, and the official mark are already handled by the official repository CI, the install-instance GUID and the source check; enforcing it in the host as well would only add a breaking change.
- References: Dalamud's `InternalName` has no namespace; uniqueness rests only on the official repository directory name and manual review. Flathub requires apps on GitHub to use `io.github.<user name>.*` and verifies the account. Chrome-style public-key ids were not adopted: they are unique and resist impersonation, but authors have to keep a key and the id is not readable, which does not pay off at the current scale.

**The install-instance GUID** (generated by the host, never seen by authors)

- Current state: the data directory is `plugin-data/<id>/`, so two plugins with the same id share it and overwrite each other.
- Each fresh installation generates a GUID. All local state hangs off the GUID: the data directory becomes `plugin-data/<GUID>/`, and the enabled state, source (which repository or link, sideloaded) and version are recorded in the host's install registry. Plugins still get the data directory through `VESTRA_PLUGIN_DATA_DIR`; plugin code does not change.
- Upgrades: the same source and the same id count as an upgrade, keeping the GUID and the data. The store accepts updates only from the original source; a higher version with the same id from another repository does not replace it automatically.
- Only one plugin with a given id runs at a time (commands, events and settings pages are divided by id). Installing a plugin with the same id from another source is a replacement: after the user confirms, the new plugin gets a new GUID and an empty data directory; the old instance's data is kept and can be picked up again when switching back.
- All changes are in the host (S4) and do not involve the SDK; not released yet, so the existing `plugin-data/<id>/` is not migrated.

### 1.6 Other decisions (settled 2026-10-21)

1. **Plugin package format**: `.vxp`, a zip file; the host or the store plugin unpacks it and then uses the existing directory installation.
2. **The official repository builds from source** (Flathub style): CI fetches the source according to `registry/<id>.toml` and builds it, so reviewers can see the source and the output is reproducible. Therefore the official repository accepts only plugins whose source is public.
   - The job that builds third-party source has no access to any secret; the signing job only reads the sha256 and the list of the build outputs and does not run plugin code (so a plugin build script cannot steal the signing private key).
3. **Signing** is in the first version: `index.json.sig`, with the public key built into the player.
4. **Trust model**: a plugin is a full Node process; `capabilities` only restrict the host API and cannot stop direct file access or network access. The official repository reviews the source manually; third-party repositories and sideloading get a clear warning in the interface; a sandbox comes later. The detail page lists the `capabilities` the plugin requests.
5. **Updates**: checked automatically, confirmed manually by the user; the manifest gains an optional `minPlayerVersion`; the user can roll back to the previous version.
6. **Built-in plugins stay in the main repository** (revised 2026-10-21, following VS Code: built-in extensions live under `extensions/` in the main repository and are built and released with the main program). The plugins under `src/plugins/` are built with the player; packaging builds `.vxp` files directly from `src/plugins` into the installer; they can only be disabled, not uninstalled; **in the first version they are updated only with player releases**, and the store does not update or replace built-in plugins (a VS Code-style "marketplace version overrides the built-in version" can be considered later if needed).
   - Exception: the two online video plugins `youtube` and `bilibili` move to the plugin repository and are installed through the store as official plugins, not shipped in the installer.
7. **Revocation**: `index.json` gains a `revoked` list (id plus version or version range). When the store finds an installed revoked version, it disables it and notifies the user.
8. **No separate beta and stable versions**: merging is releasing. The safety net is CI tests, user rollback and revocation.
9. **No download counts**: without a server this number can be inflated at will (anyone can inflate GitHub Releases counts, and a third-party `index.json` is generated by the author). The list is sorted by name or update time; a future server can provide counts through `extensions`.
10. **Store interface modeled on VS Code**: list, details (icon, name, author, summary, version, update time, source repository, license, requested permissions), with README and changelog tabs. Rendering the README needs a new **core Markdown display component** (common subset: headings, paragraphs, lists, code blocks, quotes, links, images, tables; no inline HTML; remote images are downloaded, cached and size-limited), which other plugins can also use (help pages, release notes).
11. **No dependencies between plugins.** Features needed by several plugins are proposed as core API through the bottom-up process.
12. **Node is bundled with the player**; users do not need to install it. Bundled Node 26 LTS (user ruling 2026-10-22, originally 24); during `vestra/1` the Node major version only goes up, never down, and security updates ship with player minor releases; the SDK type checks and `engines` are adjusted to this version. On macOS the bundled Node is signed with our certificate and notarized together with the `.app`. Size is about 30–40 MB per platform (compressed).

## S0 record (2026-10-21, API maintainer)

The SDK has been turned into the npm workspace package `@vestra-player/sdk@1.0.0` (corresponding to `vestra/1`) in this repository; all plugins, examples, the runner and tests reference it by package name, and the Plugin Workshop no longer carries a copy of the SDK. Plugin behavior is unchanged: apart from workshop, the `dist/` of all 18 plugins is byte-identical to before the change; workshop only lost `vendor/sdk`, and its `main.js` changed along with the engine change.

### Package structure

```text
src/packages/sdk/                 npm package @vestra-player/sdk (workspaces of src/package.json)
  package.json                    exports / bin / files; depends on typescript ^5.9, @types/node
  README.md                       for authors: install, minimal plugin, entries, CLI, Slint copies
  tsconfig.json                   build: src → dist (.js + .d.ts)
  tsconfig.check.json             type check of src + test (for the package's own CI after S1)
  scripts/build.mjs               clears and rebuilds dist/
  src/index.ts                    public entry: types only (export type * from plugin/types.ts)
  src/plugin/*.ts                 plugin API implementation (formerly src/sdk/plugin/), testing.ts is TestHost
  src/*.ts                        internal modules such as the wire client (formerly src/sdk/*.ts, including wire.ts)
  src/player-runtime.ts           ./runtime entry (for the player only)
  src/capabilities.ts             capability name table and API_VERSION (for the CLI and the host agreement test)
  bin/vestra-plugin.mjs           CLI (moved in from scripts/plugin.mjs and generalized)
  slint/palette.slint, slint/vestra/{theme,widgets}.slint   read-only copies of the widget library
  test/*.test.ts                  SDK unit tests (the SDK-only part of the former src/tests/sdk/) + cli.test.ts
```

What stays on the player side: `src/runtime/runner.ts`; `src/tests/sdk/` (`runner.test.ts`, `host-agreement.test.ts`: command limits, capability table, `apiVersion`, Slint copies identical to the host); `src/scripts/plugin.mjs` (shortcut that calls the CLI by plugin name; `npm run plugin -- …` usage unchanged), `sync-sdk-slint.mjs`, `stage-runtime.mjs`, `check-boundaries.mjs`.

### exports

| Entry | File | Content |
| --- | --- | --- |
| `@vestra-player/sdk` | `dist/index.{js,d.ts}` | All public types of the plugin API, no runtime values (`index.js` is an empty module), so a mistaken value import is rejected at build time |
| `@vestra-player/sdk/testing` | `dist/plugin/testing.*` | `TestHost`, `startPlugin`, `HostError`, `FakeWindow`, etc.; newly re-exports `COMMAND_LIMITS` (the reference documentation already described it as an SDK constant, but it was only reachable through an internal path) |
| `@vestra-player/sdk/runtime` | `dist/player-runtime.*` | `createPlugin`, `PluginInstance`, `PluginManifest`, `HostError`, `Json`, `Transport`, `CAPABILITIES`, `API_VERSION`, `COMMAND_LIMITS`. **For the player's internal use only** (runner and player tests); not part of the plugin API and not bound by semver |
| `@vestra-player/sdk/package.json` | | Lets the runner location resolve the package directory (used by the workshop) |
| bin `vestra-plugin` | `bin/vestra-plugin.mjs` | `check / build / test / pack` |

Difference from §1.5: the SDK implementation code (including `wire.ts`) is also in the npm package and is used by the player through `./runtime`, with no promise to plugins. This is the option in section 2, "the SDK repository exports a separate `runtime` entry for the player to package"; there is only one copy of the SDK source; the runner is still distributed only with the player.

`createPlugin` is in `./runtime`, not `.`: plugins should only use `import type`, and a public entry without values cannot be misused. Internal modules such as `wire.ts` are not in `exports`, so Node and TypeScript both reject deep-path imports; their `.d.ts` files are still in the package because the public types reference types such as `Json` from them.

### Publish format: compiled .js + .d.ts

- Node does not strip types from `.ts` files in `node_modules` (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`). The packaged runner loads the SDK from `Resources/runtime/node_modules`, so it has to be `.js`; the same goes for third-party plugin tests.
- Bundlers, editors and older TypeScript versions all read `.js` + `.d.ts` directly.
- The declaration files keep relative references with the `.ts` suffix (TypeScript's `rewriteRelativeImportExtensions` does not rewrite `.d.ts`); NodeNext resolution has been verified to work (type errors are reported and do not degrade to `any`), with no errors with `skipLibCheck` off either.
- In the repository: plugins, examples, the runner and player tests all use `dist/`, exactly what third-party authors see; the SDK's own unit tests run `src/` directly through relative paths. `dist/` is not committed (`.gitignore`) and builds in about 1 second: the root `prepare` builds it on `npm ci/install`, and `check`, `test:sdk`, `plugin`, `plugins:build` and `start` run `sdk:build` first; the package itself uses `prepack` (builds before `npm pack/publish`). `prepare` is not used because npm 11 blocks dependency install scripts by default and warns.
- The package depends on `typescript ^5.9` (the CLI ships its own compiler) and `@types/node` (the public `.d.ts` references `AbortSignal`, `Buffer`, `node:net`). A loose peer dependency is not possible: the latest `typescript` on npm is already 7.0 (the native compiler), which does not export `lib/tsc.js` and `transpileModule`, so the CLI cannot use it. There are no runtime dependencies at all (only Node built-in modules).
- `license` is set to `UNLICENSED` for now: **the user must choose a license before the S1 release**.

### CLI `vestra-plugin`

- Works per directory (current directory by default) and no longer assumes repository paths: type checking uses the nearest `tsconfig.json` in the plugin directory or above (up to the repository root containing `.git`; in this repository that is `src/tsconfig.json`, and the `jsnes` path mapping still applies), otherwise built-in strict settings; `typeRoots` collects every `node_modules/@types` from the plugin directory upward, plus the `@types/node` shipped with the SDK.
- New checks: the manifest's `apiVersion` must be `vestra/1` (the host already rejects other values). Any runtime reference to `@vestra-player/sdk` (any subpath) in the build output is rejected; this is now decided by parsing the syntax tree, not by regex (strings in the workshop engine contain `from '@vestra-player/sdk'`, which a regex flags falsely); when bundling (`bundle`) the SDK is marked external so this check can see it.
- `pack`: after building, packs `dist/` into `<id>-<version>.zip` (sorted entries, fixed timestamps, same input gives the same bytes) and prints the size and sha256, for the future `repo.json` (now named `index.json`, see 1.3). **This is a provisional format**: the host currently installs only from directories; the package format will be confirmed when S3/S5 are finalized. `*.zip` is not copied into `dist/` (list it in `assets` if needed).
- Windows: `npm ci` is invoked through the shell (`npm.cmd`).

### Boundary check (check-boundaries)

Plugins and examples may only reference: relative paths inside their own directory; `@vestra-player/sdk`; and, under `tests/`, also `@vestra-player/sdk/testing`. `/runtime`, deep paths and relative paths pointing into the SDK source are errors (verified with temporary files that both kinds of violation fail).

### Plugin Workshop

### Dependency approach: git tag + `prepare`

When npm installs a git dependency it clones the repository; if there is a `prepare` (or `build`, `prepack`, etc.) it installs dependencies in the clone, **but afterwards runs only `prepare`**, then packs according to `files`. The S0 package had only `prepack`, so a git install produced a package without `dist/`; hence S1 switched to `prepare`.

- npm 11's install script policy (`allowScripts`) counts the `prepare` of a git dependency as an install script: when not registered it only warns (with `--strict-allow-scripts` it is an error). The player's `package.json` registers this package by repository in `allowScripts`, and `npm ci --strict-allow-scripts` passes as well. This entry can be removed once it becomes an npm dependency (installing from the registry does not run `prepare`).
- The alternative compared: a release tag with `dist/` for every version in the SDK repository. It needs no build at install time, but the same version would have two commits, the source tag and the install tag would differ, and an extra set of release steps would be needed. The `prepare` approach has a single tag, and the install result is exactly the same as `npm pack` (`dist/` compared file by file), so it was chosen. The install-time build uses only the package's own dependency (TypeScript 5.9) and takes about 1 second.

- The version history is read from the previously published `index.json`, whose signature is verified with `keys/index-signing.pub.pem` before reading; if there is no `index.json` on Pages, it is treated as empty history only when the repository has no Release at all (first release); otherwise the run fails, so history cannot be silently lost.
- Build and signing are separate (1.6 item 2): the `build` job runs plugin code (`npm ci`, checks, tests, packing, and later third-party source builds) and has no secrets; the only step that uses a token (querying Releases, read-only) comes before `npm ci`. The `release-and-sign` job (environment `plugins-index`, secret `VESTRA_INDEX_SIGNING_KEY`) sparse-checks out only `scripts/`, `keys/` and the root files, does not run `npm ci` and does not execute plugin code; its scripts use only Node built-in modules. It checks: the index format, `revoked` equal to `revoked.json`, old version entries from the signed index kept verbatim, `downloadUrl` of new versions being the prescribed Release address, sha256 and size of each `.vxp` matching the index (for existing Releases, matching the Release asset), no extra packages in the output, asset URLs pointing to files inside the site; only after these pass does it create Releases, sign, verify, and upload the Pages artifact. The `deploy` job (environment `github-pages`) only runs `actions/deploy-pages`: by convention Pages deployment is attached to the `github-pages` environment (the Pages deployment branch restriction is also on this environment), and a job can have only one environment, so it was split out of the signing job; it checks out no code and touches no secrets.
- Third parties: parsing and validation of `registry/<id>.toml` are implemented (a TOML subset with keys `repository`, `commit`, `path`, `owners`; the id prefix must equal the source repository owner, `vestra.` is not allowed, no duplicates of official ids; the PR author of a new registration must be in owners, and changes or deletions must be submitted by an owner on base). Building third-party plugins from source is not done yet: `build-index` simply fails when there is a registry file, as stated in CONTRIBUTING.
- Revocation: `revoked.json` (`[{ id, versions, reason }]`), format-validated and copied verbatim into the index. The range syntax is an exact version or a combination of comparators (no `^` or `~`); the S5 store implements the same syntax (`satisfies` in `scripts/lib/semver.mjs`).
- Index version entries have `minPlayerVersion` and `capabilities` beyond the original 1.3 draft: the former was suggested in §6 of the S4 proposal, the latter lets the store detail page list permissions before download (1.6 items 4 and 10).
