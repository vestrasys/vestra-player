# Vestra Player 0.6.7 (unsigned test build)

Internal test build, not signed or notarized. Plugins now start when they are first needed, for everyone: the on-demand start that 0.6.5 and 0.6.6 kept behind a test switch is the normal behaviour, with the timings of Chrome's extension service workers, and the limits on how many plugin processes run at once now apply to every installation (the design: `doc/architecture/supervisor.md`).

## Plugins start when they are needed

- **Plugins start on first use and rest when idle.** The first time the player runs a plugin it starts it once to learn its menu items, keys, settings pages and the files and addresses it opens; after that, a plugin that holds nothing live (no playback listener, no open window or panel) is put in standby: no process runs, but everything it added stays in the menus and works. The first use starts it again, and it goes back to standby after 30 seconds without use. With 50 plugins installed, our test machine had about 3.6 GB less memory in use while they were idle.
- **A click on a resting plugin takes a moment.** In our tests a command of a plugin in standby ran about 0.2 s after the click (0.3 s for a large plugin); a built-in plugin was ready within 0.1 s, or within about 0.4 s when it runs in its own process. A plugin that needs longer shows "Starting *name*…".
- **Plugins that hold something live keep running.** A plugin that listens to playback, keeps a window or panel open, or otherwise holds something when it starts is never put in standby, even after it lets go of it.
- **More time to clean up.** Switching a plugin off, reloading, uninstalling or updating it, or putting it in standby now gives it up to 5 seconds to finish its cleanup (before: 0.3 s, and 2 s for standby). Quitting still takes at most about a second for all plugins together.
- **A plugin stuck starting is reported after 60 seconds.** In 0.6.6 it was reported after 15 seconds but tried up to 4 times, about a minute in all; now it gets one try of 60 seconds, a click waiting for it is answered "*Name* could not start", and the plugin then follows its usual rules (a built-in starts again after a pause, another plugin keeps its menu entries and starts again on its next use).
- **A plugin that leaves a request from the player unanswered for 5 minutes is stopped** and starts again on its next use, like after a crash. Work a plugin declares as busy (a long command, an open settings page) has no limit.

## Fewer plugin processes at once (new in this build)

0.6.6 was built before this part was finished, so it is new for everyone:

- **A cap on how many third-party plugins run at once**: 3 to 16 processes, depending on the computer's memory (14 with 8 GB, 16 from about 9 GB). Starting one past the cap puts the least recently used idle plugin in standby. A busy plugin (playing, resolving, showing a panel) is never put in standby for this, and built-in plugins are not counted.
- **When the computer runs low on memory**, idle third-party plugins go to standby at once (Windows: when less than about 1 GB of memory is available; Linux: from the kernel's memory pressure reading). Under critical pressure a click waits for a free place instead of starting one more plugin.

## What on-demand start already did in 0.6.6, now for everyone

- Many plugins starting at once start a few at a time, clicks first, without freezing the player.
- A plugin that fails to start or crashes keeps its menu entries: they show disabled with the reason during a short pause (1 s, then 2, 4 …), and the next use starts it again. After 5 crashes in 10 minutes it is listed as failed in Settings ▸ Plugins, as before.
- Clear answers instead of silence: "*Name* is busy", "*Name* could not start", "*Name* is disabled".
- A plugin that is still starting holds the clicks sent to it until it is ready.

Settings ▸ Plugins shows a plugin in standby as running and `idle`, as before. Nothing changes for plugin authors: plugins need no changes (the SDK documentation describes the timings).

## Installing an unsigned build

- **macOS** 15 or later, Apple silicon: open the DMG and drag Vestra Player into Applications. Gatekeeper blocks the first launch: open System Settings ▸ Privacy & Security and click **Open Anyway**, or run `xattr -dr com.apple.quarantine "/Applications/Vestra Player.app"`. Files downloaded with `gh release download` are not quarantined.
- **Windows** 10/11 x64: run `VestraPlayer-0.6.7-windows-x64-setup.exe`. If SmartScreen warns, choose **More info ▸ Run anyway**. It installs to `%LOCALAPPDATA%\Programs\Vestra Player` without administrator rights. Uninstalling keeps your plugins and settings in `%APPDATA%\Vestra` unless you choose otherwise. Or unzip the portable zip and run `vestra-host.exe` (the portable build adds no Open with entries).

## Known issues

- The first start after updating starts every plugin once (each plugin's first run, to learn what it adds); later starts are lighter.
- With very many plugins installed (a hundred or more), a background check of the plugin list every 0.2 s takes several milliseconds; on a 120 or 144 Hz display this may drop a frame now and then. This check is older than this build; a fix is proposed.
- Check for Updates… reports "no release information was found (HTTP 404)" until a release is published (not a draft) in a public repository; internal test builds cannot find each other.
- Japanese, Korean, German, French and Spanish are machine translations, reviewed once by an AI reviewer; a human review is still to come. Corrections are welcome.
- Numbers use "." as the decimal separator in every language (1.5×, 2.0 dB).
- This build is not signed or notarized (see above).
- macOS builds are Apple silicon only. Intel Macs and macOS 14 are not supported yet.
- Picture-in-picture is macOS only. GPU rendering on Windows is experimental and off by default.
