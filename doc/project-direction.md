# Vestra Player：项目目的、产品方向与架构原则

本文记录项目已经确定的原则与大方向架构，作为后续讨论、设计和实现的共同依据。它不是详细设计，也不是首版功能承诺。

> 技术选型更新（2026-10-04）：后续讨论已基本确定 Rust 宿主、Slint 原生 GUI 与 TypeScript 插件。本文早期的 Web UI 设想已被取代，具体技术决策、职责澄清及实验结论以 [技术选型文档](technical-decisions.md) 为准。

来源：[前期讨论记录](conversations/2026-09-29_08-22_conversation_before_md_response.json)，以及随后对架构的确认。整理日期：2026-09-29。

文中的代码均为 **usage examples（使用方式示例）**，用于说明未来开发者如何使用平台，不是现有实现或已经冻结的 API。命名、参数、包格式和通信细节仍可在设计阶段调整。

## 1. 为什么做这个项目

项目源于一个真实的日常需求：希望有一个开源播放器，具备参考播放器那样丰富而顺手的控制体验，同时拥有现代交互和可扩展的架构。

我们看重的不只是“视频能播放”，还包括：

- 播放列表可以方便地常驻侧栏，支持清晰的浏览和操作。
- 播放、视频、音频、字幕等功能能从菜单中发现，不要求用户先学配置文件和命令。
- 快捷键丰富、可搜索、可配置，常用操作路径短。
- 高级用户能够控制滤镜、shader、硬件解码、渲染和音视频输出等能力。

项目的价值集中在交互、功能组织和扩展能力。播放技术优先复用成熟基础设施，把开发精力投入用户实际感受到的体验。

前期讨论比较过多个现有播放器。这些比较是选题背景，不应理解为“没有任何开源竞品”，也不应把记录中的项目热度、版本和功能描述当作持续有效的市场结论。

## 2. 产品方向

**一个以 mpv 为默认播放引擎，具备现代交互、深度控制和插件生态的开源桌面播放器。**

参考播放器是控制体验与功能可发现性的参考；mpv 提供播放能力；VS Code 是插件架构的主要参考。Obsidian、foobar2000 等则提供可扩展产品形态的启发。

### 现代界面与高级能力并存

现代化不仅指视觉样式，也包括可搜索命令、清晰的侧栏、统一的设置入口，以及按需展开的高级控制。

界面可以采用渐进展开的方式：

```text
基础播放界面
    ├── 按需打开播放列表、字幕等面板
    └── 按需打开高级视频与音频控制
```

默认体验应当容易上手，高级能力也应有可发现的 GUI 入口。用户不需要知道 mpv 的命令名称，才能调整字幕延迟或配置视频处理。

### mpv-first

默认使用 mpv/libmpv 承担解封装、解码、音视频同步、字幕、滤镜和输出等播放工作。我们建立自己的播放后端接口，避免 UI 和普通插件到处直接调用 mpv。

滤镜、shader、渲染、硬件解码等属于产品方向；具体支持程度取决于后端、平台和设备能力。缺失能力可以通过扩展或向 mpv 上游贡献解决。

mpv 的处理管线与 DirectShow 组件生态并不等价。采用 mpv 不代表能够直接加载任意 LAV、madVR 等组件，也不构成兼容全部参考播放器内部组件的承诺。特殊原生集成需要单独验证。

第一阶段专注 mpv。后端接口保留边界，不因此提前实现多个播放引擎。

## 3. 最重要的思想：Everything is a plugin

**产品本身由插件组成。**

核心只保留让播放器运行、让插件协作所必需的基础设施。播放列表、字幕控制、音视频控制、历史记录、书签，以及复杂设置等用户功能，尽量由插件提供。

```text
小核心
    ├── 基础播放能力与后端接口
    ├── 状态、命令和事件
    ├── 配置与持久化基础设施
    ├── 插件生命周期与通信
    └── UI 外壳与扩展点
          ↑
          │ 通过公开 API 贡献功能
          │
    播放列表 / 字幕 / 高级视频 / 历史 / 第三方扩展
```

“Everything”表达的是功能组织原则，不要求把每一个基础设施模块都做成可动态卸载的插件。核心与插件的精确边界将在详细设计中确定。

### 官方插件与第三方插件使用同一套公开 API

官方播放列表插件与第三方扩展在功能 API 上遵守相同边界。默认附带、官方维护，不应成为绕过公开 API 的理由。

如果官方插件需要某项能力，而公开 API 无法表达，应完善公开 API，而不是访问内部对象、原始指针或隐藏接口。

这是验证插件 API 是否真正可用的标准：我们自己的功能也必须能够通过它完成。

### 用户选择功能组合

产品可以默认附带一组官方插件，形成开箱即用的体验。用户可以按需要启用、停用或安装功能插件；具体依赖约束由后续设计明确。

第三方插件的质量由其作者负责，用户自行选择安装。项目负责提供清晰、稳定的 API、生命周期和故障边界。插件商店不是架构成立的前提，可在生态产生实际需求后再考虑。

## 4. 与 Cameo 的关键区别

讨论中的 Cameo 指 Cameo Systems Modeler / MagicDraw 这一类 MBSE 软件。这里用它帮助理解插件与宿主的关系，不对它的全部内部实现作概括。

Cameo 的插件开发体验更接近：引入 SDK，使用公开应用对象、Action 和 Configurator 等机制，在应用中增加功能。它也有公开 API 和扩展机制。

我们的主要参考是 **VS Code 的能力 API、贡献点和 Extension Host 思路**：插件声明它提供什么、需要什么，通过平台协议工作，避免依赖宿主的内部对象结构。

| 对比维度 | Cameo 式 SDK 插件的理解方式 | 我们的方向 |
|---|---|---|
| 开发者面对什么 | 应用的公开对象模型与 SDK | 能力 API 与扩展点 |
| 怎样接入功能 | 实现 Action、Configurator 等接口 | 声明贡献内容，注册行为 |
| 怎样增加 UI | 通过 SDK 操作界面相关对象 | 向指定菜单、侧栏、设置等位置贡献内容 |
| 对宿主实现的依赖 | 需要理解相关对象与接口体系 | 无需知道内部窗口或后端控制器结构 |
| 产品怎样扩展 | 为应用增加功能 | 官方与第三方插件共同组成产品 |

差异不由 Java 或 TypeScript 决定，也不单由是否跨进程决定。核心是公开契约、扩展点和依赖边界。

### 同一个功能：将画面设为旋转 90°

下面是用于对照的“直接沿宿主对象查找控制器”的假想播放器写法，**不是 Cameo 的真实 API，也不是我们要提供的 API**：

```ts
const window = app.getMainWindow();
const controller = window.getCurrentPlayer().getMpvController();

window.getContextMenu().addAction("旋转 90°", () => {
  controller.setProperty("video-rotate", 90);
});
```

这种写法让插件知道窗口、播放器、mpv 控制器和菜单对象如何组织。

我们期望的使用方式是：

```ts
export function activate(ctx: PluginContext) {
  ctx.commands.register({
    id: "example.video.rotate90",
    title: "将画面设为旋转 90°",
    execute: async () => {
      await ctx.player.video.setRotation(90);
    },
  });

  ctx.ui.menus.contribute({
    menu: "video.context",
    command: "example.video.rotate90",
  });
}
```

插件只知道播放器能力和 `video.context` 这个扩展点。菜单最终如何绘制、播放后端如何执行，由宿主负责。这里设置的是绝对角度，并非每执行一次再累加 90°。

`ctx` 是 SDK 提供的能力入口，可以在内部封装通信；它不是 Rust 核心对象或 UI 对象的直接引用。示例中的回调留在插件运行环境里执行，不会把函数对象通过 IPC 传给 Rust。

## 5. 命令、贡献点与声明式扩展

### 同一个功能，共用一个命令

命令系统连接功能与不同操作入口。例如 `example.video.rotate90` 可以被右键菜单、快捷键、命令面板和工具栏引用，无需在每个入口重新实现播放逻辑。

```text
右键菜单 ────┐
快捷键 ──────┤
命令面板 ────┼──→ 命令 ID ──→ 对应处理函数 ──→ 播放器能力
工具栏 ──────┘
```

注册命令并不意味着它必须自动出现在所有菜单。各入口根据贡献声明和自身规则决定如何展示，但共享同一命令标识和行为。

### manifest 描述贡献，代码实现行为

另一种等价的使用方式是把静态贡献写入 manifest。以下示例与前面的动态注册示例是两种表达方式，不应同时重复注册同一命令。

```json
{
  "id": "example.video-tools",
  "name": "视频工具",
  "version": "0.1.0",
  "apiVersion": "1",
  "entry": "dist/extension.js",
  "permissions": ["player.control"],
  "contributes": {
    "commands": [
      {
        "id": "example.video.rotate90",
        "title": "将画面设为旋转 90°"
      }
    ],
    "menus": {
      "video.context": [
        { "command": "example.video.rotate90" }
      ]
    },
    "settings": [
      {
        "id": "example.video-tools.showRotationHint",
        "title": "显示旋转提示",
        "type": "boolean",
        "default": true
      }
    ]
  }
}
```

对应的插件代码只绑定行为：

```ts
export function activate(ctx: PluginContext) {
  ctx.commands.registerHandler("example.video.rotate90", async () => {
    await ctx.player.video.setRotation(90);
  });
}
```

宿主读取声明后即可知道插件提供哪些命令、菜单项和设置。激活时机、版本协商、注册资源回收和权限实施方式，留待详细设计。

manifest 中写了权限，不等于已经实现安全隔离；权限必须由运行时与宿主边界实际执行。

### 高级设置也是功能插件的贡献

一个高级视频插件可以同时贡献设置项、视频处理面板、菜单项和命令。设置页是承载这些贡献的入口，不需要把所有高级功能写进核心。

后端通过能力信息告诉插件当前支持什么。例如：

```ts
const capabilities = await ctx.player.getCapabilities();

if (capabilities.videoFilters) {
  ctx.commands.register({
    id: "example.video.enableDenoise",
    title: "启用降噪",
    execute: async () => {
      await ctx.player.video.filters.add({
        id: "example.video.denoise",
        type: "lavfi",
        filter: "hqdn3d",
      });
    },
  });
}
```

这里只展示“先查询能力，再注册功能”的思路。具体滤镜可用性、参数校验和错误处理仍由后续 API 设计明确；通用滤镜支持不保证某个具体滤镜必然可用。

## 6. TypeScript 与 Rust 的关系

**Rust 实现核心，TypeScript 实现 Web UI 与插件，两者通过明确的通信协议连接。**

| 层 | 主要职责 |
|---|---|
| Web UI（TypeScript） | 界面呈现、交互、菜单、侧栏、设置入口 |
| 功能插件（TypeScript 编写，编译为 JavaScript） | 功能行为，贡献命令、面板、设置，响应事件 |
| Extension Host | 执行插件逻辑，与核心通信，提供插件生命周期边界 |
| Rust Core | 权威播放状态、命令和事件协调、配置、插件管理、播放后端接口 |
| mpv 后端适配层 | 通过依赖库的安全 API 将播放器能力映射到 libmpv |
| libmpv 及其依赖 | 实际媒体播放与处理 |

TypeScript SDK 是插件开发者看到的契约。跨语言协议还需要明确可序列化的数据、错误和事件；仅有 TypeScript 类型不能替代 Rust 端的输入校验。

```text
Web UI（TypeScript）       插件逻辑（TypeScript → JavaScript）
        │                              │
        │                        Extension Host
        │                              │
        └──────── 请求 / 响应 / 事件 ───┘
                         │
                      Rust Core
             状态、命令、事件、配置、插件管理
                         │
                  Media Backend 接口
                         │
                    mpv 后端适配
                         │
                  依赖库的 safe API
                         │
                       libmpv
```

以上是职责与通信示意，不代表最终进程数量或线程布局。

### 一次暂停如何发生

插件开发者只写：

```ts
await ctx.player.pause();
```

概念上的调用路径是：

```text
TS SDK 发出暂停请求
    ↓
Rust 核心校验并交给播放后端
    ↓
libmpv 执行暂停
    ↓
后端报告实际状态
    ↓
Rust 更新权威状态并发布事件
    ↓
UI 与插件获知播放已暂停
```

请求完成与实际状态更新的精确语义将在协议设计中确定。界面不能只因按钮被点击就认定底层已经完成操作。

### 插件逻辑与插件 UI 需要分清

Extension Host 中的逻辑与界面进程中的面板不能直接共享函数、React 组件实例或原生窗口对象。

例如，面板可以按以下概念方式声明：

```json
{
  "contributes": {
    "panels": [
      {
        "id": "example.playlist",
        "title": "播放列表",
        "location": "sidebar",
        "uiEntry": "dist/playlist-panel.js"
      }
    ]
  }
}
```

这表示让 UI 宿主在适当环境加载界面入口，插件逻辑与面板通过消息交换数据。它不是把组件对象跨进程传递。

具体采用独立 UI 模块、声明式 UI，还是其他面板承载方式，尚未选定。上例只说明职责边界，不预先锁定方案。

## 7. Rust 与原生扩展的安全原则

### 自身 Rust 代码只使用 Safe Rust

所有第一方 Rust crate 应禁止 `unsafe`：

```rust
#![forbid(unsafe_code)]
```

这是最终原则，取代早期讨论中“在自身 mpv-backend 或平台模块里允许少量 unsafe”的建议。

我们通过依赖库提供的安全封装调用 libmpv、窗口系统等原生能力。依赖内部仍可能使用 `unsafe` 或 C/C++；原则约束的是本项目自身代码，不是宣称整个最终程序不存在原生不安全代码。

具体封装库尚需验证，尤其是嵌入渲染、窗口句柄、线程与生命周期接口。如果某条实现路线要求自身编写 `unsafe`，应先寻找符合原则的依赖或进程边界方案，不静默放宽原则。

Safe Rust 也不替代逻辑、并发和资源管理方面的验证。AI 负责主要编码、维护者审阅代码的开发方式，仍需配合编译检查和适当测试。

### 原生扩展走独立进程与 IPC

早期示例曾提出动态加载 native plugin，并直接调用 ABI。这不再是当前采用的方向。

特殊原生集成采用独立扩展进程，通过 IPC 与核心交互：

```text
Rust Core
    ├── IPC ── Extension Host ── JS 插件
    └── IPC ── Native Extension Process
                    └── 特殊原生能力
```

这样避免在自身代码中直接加载任意 DLL 并调用原始 ABI。独立进程还提供故障隔离边界，但不自动构成完整权限沙箱。

默认 libmpv 后端经由依赖库的安全封装接入，不代表所有播放代码都必须移到进程外。第三方原生扩展的 IPC 也不自动解决视频帧传输、GPU 资源共享或渲染器替换；这些集成需专门设计和验证。

第三方 JS 插件逻辑也应与核心分离。Extension Host 故障不应直接拖垮核心；基础播放在插件故障下如何继续、哪些界面功能会暂时失效，需要通过故障恢复设计落实。

## 8. 已确定的原则与后续设计空间

已经确定：

- 产品面向真实播放工作流，现代交互与深度控制并存。
- mpv-first，复用播放技术，建立自己的播放器能力 API。
- Everything is a plugin，小核心与功能插件共同组成产品。
- 官方与第三方功能使用同一套公开 API，不依赖内部对象开后门。
- 主要参考 VS Code 的贡献点、能力 API 与 Extension Host 架构。
- Rust 核心、TypeScript UI 与插件，通过明确协议协作。
- 第一方 Rust 禁止 `unsafe`；原生边界依赖安全封装或隔离进程。
- 示例服务于理解架构，不作为现成实现或固定 API。

后续需要具体设计与验证：

- 首发平台与首版功能范围。
- Web UI 框架、桌面容器及视频嵌入方式。
- Rust 的 mpv 封装库与实际能力覆盖。
- 核心和官方插件的最小职责划分。
- 插件运行时、UI 承载方式、生命周期和故障恢复。
- IPC 协议、类型契约、权限实施及 API 版本策略。
- 插件安装、依赖、升级与卸载方式。

后续设计应沿这些原则细化，不把尚未验证的库、协议或示例命名提前当作既定实现。
