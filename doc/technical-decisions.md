# Vestra Player：技术选型与实验结论

整理日期：2026-10-04。本文记录当前的技术选择、职责边界、选择理由及实验依据，不是详细架构设计或最终插件 API 规范。

依据：[项目方向与原则](project-direction.md)、[本轮讨论归档](conversations/2026-10-04_11-37_technical-selection-discussion.json)、[Slint 实验](experimental1/README.md)及其[验证记录](experimental1/findings.md)。对话中存在被修正或否决的提议，本文以最终确认的方向为准。

**当前基本确定：Rust 宿主 + Slint 原生 GUI + TypeScript 插件。** 项目方向文档中早期的“TypeScript Web UI”和“待选择 Web UI 框架”等表述已被本次选择取代；项目目的、插件原则和 Safe Rust 原则继续有效。mpv-first 仍是播放后端方向，但具体 Rust 封装及集成路线尚未验证。

## 1. 技术选型的目标与约束

项目希望提供类似 PotPlayer 的丰富控制体验，同时允许用户组合和扩展功能。主要投入是交互、功能组织与插件生态；解码、同步、渲染等尽量复用成熟基础设施。

选择必须服务于以下原则：

- **Everything is a plugin**：核心保留运行和协作必需的基础设施，用户功能主要由插件提供。
- 官方默认插件与第三方插件使用相同的公开功能 API，不因官方身份访问宿主内部对象。
- 插件作者无需理解 Rust 内部的类、窗口控制器或后端对象结构。
- Rust 核心不依赖 TS 实现自身职责；第一方 Rust 禁止 `unsafe`，原生能力通过安全依赖封装或进程边界接入。
- 降低插件开发成本，允许编写复杂、美观的原生界面，复用成熟 GUI 库，不另造通用 GUI 框架或布局语言。
- 默认插件组合成开箱即用的播放器，用户可以按需替换和扩展；插件商店不是架构成立的前提。

插件架构主要参考 VS Code 的能力 API、贡献点和 Extension Host 思路。Cameo 用于对照理解，不以暴露宿主内部对象结构作为扩展方式。

## 2. 当前确定的技术组合

| 技术或层 | 当前职责与状态 |
| --- | --- |
| Rust 宿主 | 播放后端接入、视频呈现、权威播放状态、插件通信、窗口与资源生命周期。已基本确定。 |
| Slint | 原生窗口、控件、布局、样式与插件界面，Rust 拥有播放器窗口。已基本确定。 |
| TypeScript 插件 | 用户功能、界面行为、命令与事件处理，通过公共能力调用宿主。已基本确定。 |
| TS 运行时 | 实验使用 Node 子进程直接运行可擦除类型的 TS；成品运行时、进程数量与隔离策略尚未冻结。 |
| 播放后端 | mpv/libmpv 是原有方向；实验实际使用 FFmpeg/ffplay。具体成品集成仍待验证。 |

因此，技术选择不是只有 Slint 与 Rust：TS 仍是插件开发语言；Slint 的 `.slint` 负责界面表达，TS 负责行为。

```text
Rust 宿主
  ├── Slint 窗口与视频显示
  ├── 插件界面承载与生命周期
  ├── 播放状态、公共能力与通信
  └── 播放后端接入
            ↑ 请求、响应、事件与界面状态
      TypeScript 功能插件
            + 原生 .slint 界面（按需）
```

这是职责示意，不规定最终包结构、线程数量或通信协议。

## 3. 为什么选择 Slint

讨论 Dalamud、ImGui binding 和代码生成器，是为了理解一种开发方式：宿主连接成熟 GUI 库，让插件作者直接使用已有界面能力，避免重新设计一套控件和布局 API。Dalamud 是参考材料，不意味着项目必须采用 C++ Dear ImGui。

当前选择 Slint，是因为可以直接使用其原生界面语言、布局、控件和样式，并由 Rust 管理原生窗口；插件行为则留在 TS。这样不必让核心转向 Web UI，也不必自建完整的 egui-to-TS wrapper。

React/Web UI、egui wrapper 等曾是候选路线，但不再是当前实施方向。本次只进行了 Slint 实验，没有通过同等实验比较所有候选，因此不把选择解释成对其他框架性能或复杂度的普遍结论。

一个需要明确接受的成本是：插件作者可能需要同时编写 `.slint` 与 TS，而不是只写 TS。跨语言属性和事件连接仍需宿主适配，Slint 并不会自动解决我们的插件系统。

## 4. 核心与插件的职责边界

“播放功能由插件提供”指用户发起和操控播放的产品功能由插件组织，并不要求把解码器、播放时钟或窗口生命周期移出核心。

| 能力 | 职责归属 |
| --- | --- |
| 解码、播放时钟、音视频同步 | 成熟播放后端承担，Rust 接入并提供能力接口。 |
| 当前媒体、位置、暂停状态及后端事件 | Rust 维护权威状态，插件订阅实际结果。 |
| 播放窗口、视频呈现、界面替换时维持播放会话 | Rust 宿主基础保障。 |
| 打开文件、播放控制界面、播放列表、字幕管理、历史等 | 功能插件，包括默认插件。 |
| 滤镜算法或 GPU 执行 | 播放后端或专门的原生处理能力；TS 配置与调度。 |
| 界面关闭或重建后保持当前播放 | 宿主责任，不要求用户安装额外插件。 |
| 退出应用后，下次启动自动续播 | 可由插件决定产品策略，宿主提供状态与持久化基础能力；尚未实现。 |

插件不需要每次通用 I/O 都经过宿主 API。讨论接受插件使用 TS 运行时的文件系统、网络等能力，宿主文件对话框只是便利服务，不是唯一读取文件的途径。实验 Node 插件拥有这些运行时权限，尚无权限沙箱。

对于宿主高层 API 未覆盖的后端能力，可以继续设计通用命令或后端扩展通道，以减少插件等待宿主更新的情况；其边界、版本和错误语义尚未确定。允许通用 I/O 不等于自动支持任何媒体源或传输协议。

以下都是 **usage examples**，只解释职责，不是实现任务或冻结的成品 API：

```ts
// 概念示例：插件提供打开文件的行为。
ctx.onAction("open", async () => {
  const path = await ctx.dialogs.openMedia();
  if (path) await ctx.player.load(path);
});

// 概念示例：TS 配置滤镜，不把每一帧拿到 JS 再计算。
await ctx.player.filters.setGaussian({ enabled: true, sigma: 3 });
```

公共接口中的回调留在插件运行环境执行，跨语言传递的是事件和可序列化数据。没有采用字符串注入 Rust 代码的方式实现滤镜。

## 5. 插件 GUI 的接入方式与限制

### 安装、启用与显示是不同阶段

产品期望的流程是：安装插件文件和元数据 → 注册菜单及功能 → 根据需要激活逻辑或显示界面。插件可以完全没有界面；菜单中出现功能，也不意味着已经在主窗口嵌入一个自定义组件。

当前实验没有真正的安装管理器：右键选择 manifest 后，读取插件、组合界面并启动 TS 进程。这个流程不能直接当成成品安装、更新和卸载规范。

### 当前稳定 API 路线：首次接入重建界面

实验固定 Slint 1.18.1，使用公开 interpreter 接口。对首次加载、事先未知的插件界面，宿主把插件组件 import 到新根文档，在进程内解析和编译 `.slint`，创建新窗口替换旧窗口。

**这不是编译 Rust；终端用户不需要 Rust、Cargo 或开发工具。** interpreter 随播放器打包。Rust 编译器只供开发和构建播放器使用。

重建过程中保留 Rust 播放后端、TS 插件进程及缓存的界面属性，不需要重启播放器。编译发生在 GUI 线程，可能短暂停顿；窗口替换可能闪动，焦点、全屏及组件局部状态还需补充恢复与验证。保留会话不等于界面加载完全无感。

仅将插件安装到磁盘，可以不触发界面重建。把首次显示延后，只是推迟重建时机，并没有解决动态嵌入限制。

### 已接入组件的隐藏与显示

播放列表实验采用 Slint 条件组件控制侧栏。隐藏和重显不重新编译宿主，也不替换播放器窗口；视频区域获得或让出侧栏空间。

条件隐藏会销毁侧栏组件，重显会重新实例化该组件。列表与当前页保存在 TS 中，因此可以恢复；焦点、滚动位置等仅保存在组件内部的状态，不会因此自动保留。

```slint
// 使用方式示意：组件在本次宿主文档编译时已经确定。
HorizontalLayout {
    Rectangle { /* 视频区域 */ }
    if PlaylistState.visible : PlaylistPanel { }
}
```

上述条件显示与“向现有窗口插入一个未知组件”是不同能力。

### 内部动态嵌入路线及尚未确定的规则

Slint 已有 ComponentContainer/ComponentFactory 机制，但 1.18.1 interpreter 的关键嵌入入口 `create_embedded()` 仍位于 `internal` feature 下。它是后续实验候选，当前代码未采用。相关资料包括 [Issue #2390](https://github.com/slint-ui/slint/issues/2390)、[维护者说明](https://github.com/slint-ui/slint/discussions/4620)、[2026 年关于 component factories 的讨论](https://github.com/slint-ui/slint/discussions/11820)和[固定版本源码](https://github.com/slint-ui/slint/blob/v1.18.1/internal/interpreter/api.rs)。这些材料提供推进方向，不提供明确稳定版发布时间。

本轮没有确定通用 placement、复杂 docking、默认操作栏替换或多个插件争用主窗口空间的协议。也没有采用独立的“向操作栏追加按钮”API，避免同时维护另一套 GUI 交互接口。

默认播放插件提供操作栏是当前实验与产品讨论的起点。后续试用发现普通工具面板会替换播放栏，因此新增实验挂载约定 `ui.region: "controls"`：一个常驻区域由声明它的插件提供，核心仅管理通用挂载与冲突，不识别播放插件名称或实现其按钮逻辑。音频等普通工具使用视频右侧可关闭区域，播放列表继续使用 sidebar；切换工具不会替换常驻组件。该扩展的契约见 [API-009](../src/sdk/api-requests.md)，验证结果单独记录，不视为最终布局定稿。

最终布局、其他插件能否修改操作栏、如何接入额外界面，仍需 usage 驱动设计。上述有限挂载点不构成通用 placement 或复杂 docking 的产品承诺，也没有引入“向操作栏追加按钮”的另一套接口。

## 6. 第一个实验及其证据

代码现位于 [src](../src/README.md)，实验说明与历史证据保留在 [experimental1](experimental1/README.md)。所有接口和实现安排均为实验版本，与最终 API 可能相差很大。

实验包含：

- Rust 拥有的 Slint 主窗口，以及右键加载插件入口。
- TS 文件播放插件：打开 MP4、播放/暂停和跳转。
- TS 高斯模糊插件：启停和调整参数，由 FFmpeg CPU `gblur` 执行。
- TS 播放列表插件：加入文件、去重、分页、选择播放，以及可隐藏侧栏。
- Node 子进程逻辑、JSON 请求/响应/事件桥和 Slint global 属性/回调连接。

视频帧只在 FFmpeg → Rust → Slint 路径中流动，TS 不收发逐帧像素。实验未使用 Slint Node GUI 绑定，也未让 Node 接管主窗口。

截至本轮验证：

| 项目 | 证据与范围 |
| --- | --- |
| 完整 Rust 构建及 Cargo check | Rust 1.92.0、Slint 1.18.1，通过。 |
| Slint 源码编译 | 空宿主及三个插件组合，通过。 |
| 插件协议 | 6 项真实 Node 子进程测试通过；其中宿主响应由测试端模拟。 |
| 媒体后端 | 1 项真实 MP4 测试通过，覆盖解码、暂停、跳转、滤镜预览和清理。 |
| 桌面窗口实验 | 实际显示窗口，走 Slint 回调、TS RPC 与 FFmpeg，验证侧栏隐藏重显及界面重建后的列表、播放状态保留。 |

窗口报告中，播放列表首次加载后编译次数和窗口代数均为 3；隐藏、展开仍为 3；再加载滤镜后变为 4，列表条目及展开状态保留。播放位置继续推进，没有因界面重建从头播放。详见[原始报告](experimental1/evidence/playlist-window-report.json)、[展开截图](experimental1/evidence/playlist-shown.png)与[隐藏截图](experimental1/evidence/playlist-hidden.png)。

边界同样重要：

- 当前是 FFmpeg 640×360、30 FPS 的 CPU 预览后端，不是 mpv/libmpv 集成或 GPU 性能验证。
- 音频通过独立 ffplay 粗同步，尚未实听验证。
- 窗口自动验证关闭音频，并以指定样本替代原生文件对话框返回值；没有验证所有鼠标、菜单、全屏与焦点交互。
- 复杂组件局部状态、长期运行、插件故障与升级兼容性尚未覆盖。

因此，这个实验支持继续采用 Slint 的基本方向，不证明完整播放器已经达到生产可靠性。

## 7. 生产实现需要补齐的能力

实验核心很小，说明职责划分可以精简，不说明生产代码也会保持相同规模。实验省略了可靠性、平台适配和完整生命周期工作。

下一步需要设计和验证：

- **播放后端**：mpv 的安全封装、视频嵌入、音视频同步、硬件解码、字幕和处理能力。
- **插件管理**：安装、更新、依赖、启停、卸载与注册资源回收。
- **运行与故障**：协议校验、异步错误、插件退出或无响应、恢复策略及资源清理。
- **状态与窗口**：持久化、播放会话、全屏、焦点、界面重建和局部状态恢复。
- **公开契约**：SDK、能力查询、后端扩展通道、版本兼容与运行时权限边界。

这些是设计议题，不提前规定包、类或最终 API。功能丰富度主要依靠默认与第三方插件增长，核心负责其可靠运行。复现 PotPlayer 的用户功能是渐进目标，不是兼容其全部内部组件的承诺。

## 8. 决策状态与下一步验证

| 状态 | 内容 |
| --- | --- |
| 已基本确定 | Rust 宿主、Slint 原生 GUI、TS 插件；成熟库复用；插件功能组织；官方与第三方使用同一公开能力边界；不自建通用 GUI 框架。 |
| 实验已验证 | 公开 interpreter 重建窗口路线；文件播放、滤镜配置、播放列表；侧栏日常隐藏重显；TS 中持有的列表与播放会话跨界面重建保留。 |
| 待设计或验证 | mpv 集成、最终运行时与 SDK、完整安装管理器、界面挂载与操作栏规则、故障恢复、状态持久化，以及是否值得采用内部动态嵌入。 |

继续采用 **usage 驱动设计**：先想象终端用户如何操作，再编写几个虚拟插件及其使用示例，评估 API 是否易懂、能力是否足够，随后反推 Rust 架构。

技术方向已基本确定，实验中的字段、进程安排、JSON 协议和挂载点仍是可替换的临时设计。后续实现应沿项目原则推进，并以实际使用场景和验证结果收敛。
