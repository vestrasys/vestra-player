# 插件候选与下一轮架构实验

日期：2026-10-17。本文是调研与实验建议，不冻结 core API、manifest 或插件划分，也不表示这些插件已经实现。技术方向仍见 [technical-decisions.md](technical-decisions.md)。

> 后续确认：先完成 PotPlayer 功能清单，再选择实验插件，不沿用本文最初提出的优先顺序。已完成的固定版本盘点见 [PotPlayer 功能清单](potplayer-feature-inventory.md)；其中的发行包证据取代下文版本未知的语言样本线索。

## 1. 实验应当回答什么

通过不同类型的插件迭代架构，而不只验证按钮能否点击。每个实验写出用户操作、插件 usage、需要的宿主能力与自动验收场景，并记录是否迫使 core 增加特定业务分支。

共同验收：启用/停用、失败恢复、资源撤销、窗口重建后的状态、两个插件同时修改同一能力、后端不支持某项能力时的行为。手工观察主要用于视觉效果和平台设备行为，协议与状态尽量自动验证。

## 2. PotPlayer 功能盘点的方法

目标是发现用户功能及操作入口，不是恢复 PotPlayer 的内部架构。优先顺序：

1. 固定一个版本的官方发行包，记录版本与 SHA-256；先读取语言、菜单和快捷键资源。
2. 对资源中缺失或含糊的部分，用 REA 的 PE 资源检查补充。只有层级、命令关联仍不明确时才做局部反编译。
3. Windows 上核对菜单、设置页和不同媒体状态的差异。静态文本无法证明动态条目、可用性条件或功能行为。
4. 输出“功能 → 菜单/快捷键/设置入口 → 候选插件 → 所需 core 能力”的映射，避免把菜单树直接当成插件树。

REA 是可用于这项工作的逆向工具库；不必为了用它而一开始全面反编译。当前没有选定官方 binary，也没有执行 PotPlayer binary 或 REA 反编译。

已实际读取一个[第三方仓库中的 English.ini](https://github.com/Onemeshnik/PotPlayer-Median-subtitles-installer/blob/master/%7Bapp%7D/Language/English.ini)：`[MenuString]` 包含 915 条带层级标识的文本记录。这个数量不是独立功能数：含父菜单、重复入口与辅助菜单。文件版本未知，不能当作最新完整菜单；亮度、对比度、色相、饱和度、均衡器及音量规范化等文本可作为初步线索。白平衡是我们的候选需求，不因这份文件就声称 PotPlayer 已提供对应功能。

## 3. 基础插件候选

以下是结合产品方向提出的功能分组，不是已验证完整的 PotPlayer 对照表；默认附带哪些仍待决定。

| 候选插件 | 主要用户功能 | 主要架构问题 |
| --- | --- | --- |
| 文件与来源 | 文件、目录、URL、外部音轨 | 来源处理器注册、打开方式分派、异步错误 |
| 基础播放控制 | 暂停、跳转、速度、逐帧 | 权威状态、命令、快捷键和界面的一致性 |
| 播放列表与队列 | 排序、搜索、循环、随机、侧栏 | 状态持久化、会话与 UI 的分离 |
| 画面调节 | 明暗、对比度、色彩、白平衡、预设和复位 | 多菜单贡献、参数组合、滤镜顺序与资源所有权 |
| 几何与显示 | 旋转、裁剪、宽高比、缩放 | 视频变换与窗口布局边界 |
| 音频处理 | 均衡、响度、延迟、声道与预设 | 音频图、实时参数及与其他插件组合 |
| 音轨与字幕 | 轨道选择、加载、样式与时间校正 | 媒体事件、后端能力差异 |
| 章节与书签 | 导航、标记及备注 | 时间轴贡献与媒体身份 |
| 历史与续播 | 最近记录、恢复位置 | 持久化策略与核心会话保障的区别 |
| 截图与片段导出 | 原始/处理后画面、字幕选择、导出任务 | 管线取样点、后台任务及进度取消 |
| 高级视频处理 | shader、降噪、去隔行、增强 | 可组合处理链、平台能力与 GPU 生命周期 |
| 信息与自动化 | 媒体诊断、播放结束动作、命令组合 | 状态查询、事件订阅、命令复用 |

一个插件可以拥有多个命令，并向不同菜单位置贡献入口；插件不等于一个子菜单或一个窗口。快捷键配置、窗口操作、设置入口也需要盘点，其核心/默认插件归属尚未在本轮确定。

优先实现画面调节与音频处理两个实验：前者跨菜单但共享参数，后者验证另一类数据管线。菜单与快捷键使用命令贡献机制；不另造按钮布局 API。

## 4. 扩展实验：DLSS 5 与模拟器

### DLSS 5 神经渲染

[NVIDIA 官方介绍](https://research.nvidia.com/labs/adlr/DLSS5/)描述的是带时间状态、运动信息等输入的神经渲染。第三方项目如 [OptiScaler DLSS 5](https://github.com/Skynizz/optiscaler-dlss5)表明存在游戏通用接入路线，但不能直接推出 mpv 视频可以无额外适配地调用。

需要核对具体采用的 SDK/第三方实现、平台、图形 API、模型输入、模型取得方式和渲染接入位置。视频没有游戏引擎原生运动矢量；若某路线需要它，就必须估计、替代或使用该实现提供的降级路径，并在跳转、切片、尺寸变化时重置时间历史。

实验目标是验证“可选原生视频处理提供者”：TS 提供配置，原生模块/进程执行，核心协调处理管线和资源。不要为某个品牌功能在 core 中硬编码专用业务，也不要把逐帧 GPU 数据序列化为 JSON 发给 TS。

macOS 可以开发 TS 行为、协议、能力检测、生命周期和模拟端验收；Windows/NVIDIA 或其他实际支持的环境才可验证对应实现。未测试的适配代码必须标注，不以模拟效果、占位函数或另一种放大算法冒充 DLSS 5 已实现。

### NES / 街机模拟器

选择成熟模拟器核心，插件负责文件类型、ROM 选择、设置和用户入口。先用自制/授权测试 ROM。NES 与街机后端不同，先做一种，避免同时扩大范围。

它的重要价值是验证“媒体来源不一定是视频文件”：模拟器产生画面与音频，还需要键盘/手柄输入、自己的运行时钟和存档。不能默认强塞入具备 duration/seek 的视频播放器模型；暂停、快进等也应按能力表达。

优先让模拟器拥有独立会话；是否共享主显示区域、如何与视频会话切换，由实验决定。其原生执行仍遵守项目的 Safe Rust/进程边界原则。

## 5. Pi 自动生成插件

这里暂按 Mario Zechner 的 Pi coding agent 理解。原 [badlogic/pi-mono](https://github.com/badlogic/pi-mono)当前指向 [earendil-works/pi](https://github.com/earendil-works/pi)，官方支持 SDK 与 RPC 集成。

建议把“AI 插件工坊”作为可选插件：它负责指令界面、提示词、Pi 会话、模型及生成策略。core 提供任何开发工具都能使用的公共包校验、开发加载、诊断、停用与回滚能力，不把 Pi 固化为核心依赖。

生成优化首先依靠可执行反馈，而不只是更长的提示词：

```text
用户要求
  → 当前实验 SDK、类型定义、示例与能力说明
  → Pi 在候选插件工作目录生成 TS / Slint / manifest
  → 类型与包校验、Slint 编译、协议测试
  → 独立会话加载并执行目标 use case
  → 将结构化错误反馈给 Pi 修改
  → 验收后安装或替换；保留旧版以便回退
```

测试失败不能仅让 agent 修改预期来制造通过；验收场景来自用户目标并独立于生成代码。模型调用失败、取消生成和候选插件崩溃应不影响现有播放。

Pi 官方说明它默认不提供文件、进程、网络与凭据权限沙箱。工作目录限定和工具白名单不等于 OS 隔离；生成插件的代码执行边界需要单独设计。不能因为支持生成代码，就给予其修改 core 或绕过公共 API 的专用通道。

## 6. 后续选材与评价

先完成固定版本的 PotPlayer 功能盘点，再从清单中选择几组有代表性的功能作为实验插件。暂不决定画面、音频、模拟器、Pi 或 DLSS 5 的实验顺序。

每次都比较：新增功能是否只改插件、core 新增的是不是通用能力、两个插件能否共存、能否自动撤销/恢复、API 学习和接入成本是否下降。不要为了“最通用”一次设计完整抽象，也不要只靠手工点击证明架构可用。
