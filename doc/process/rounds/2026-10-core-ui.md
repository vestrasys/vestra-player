# This round: core UI and input capability changes (step one, top-down)

Branch: `rebuild/core-ui` (from `rebuild/sdk-v2` 136de92). The process follows the [community workflow](../community-workflow.md) §5 (top-down). Before starting, every agent reads: this document, the community workflow, the [UI revision document](../../product/ui-spec.md) §2, §3, §6, §8, §9, §10, and the subsections relevant to its own work.

## 1. Goals

Do all the core changes listed in [UI revision document](../../product/ui-spec.md) §10 in one round: C1–C11 and C14 (C12 and C13 were decided against). Downstream plugins **update to the new interfaces without changing their interaction**; the interaction redesign is step two (revision document §11, bottom-up).

Decisions already made by the user are in revision document §1: D1 add a second color scheme (later removed), D2 keep separate tool windows, D3 save snapshots directly (done in step two), D4 remove the Commands button and do not build a macOS menu bar, D5 playback information plugin, D6 playlist can be detached and float.

## 2. Principles

- **Core does not bloat**: each capability gets only the minimal interface; old interfaces and special cases replaced by a new mechanism are deleted this round, **no compatibility layer is kept** (they may coexist briefly during migration and are deleted in P4). Do not build capabilities ahead of time that have no user (no user rebinding UI, no menu layout file, no control panel container).
- **Plugins do not talk to each other**: anything several plugins share becomes a core capability (e.g. C6 playback sequence, C7 sidebar state); plugins deal only with the core.
- **Behavior unchanged** (for downstream plugins): menu item positions, names, order, enabling conditions, shortcuts, windows and buttons are the same before and after migration. Changes to the host's own UI (C1, C2, menu style) are the expected changes this round.

## 6. Migrator tasks (P3)

### 6.1 Read before starting

This document, community workflow §5.2, `doc/architecture/core-ui-design.md` (especially the migration section), `doc/plugins/reference.md`, the reference migrations (the new versions of `src/plugins/playback/` and `src/plugins/playlist/`), and your own plugin's code and tests.

### 6.2 What to do

1. Move the plugin to the new style, **behavior unchanged**: menu item positions, names, order and enabling conditions unchanged; shortcuts unchanged (`shortcut` → equivalent `bindings`); windows, buttons and text unchanged.
2. Replace deleted or renamed interfaces with the new style.
3. Do not adopt the interaction redesign from the revision document (moved menu items, new shortcuts, on-screen display, visual changes); that is step two.
4. Do not add features or make new capability requests. When the new interfaces cannot express existing behavior, report a "migration blocker" per community workflow §5.2.

### 6.3 Done when

- `npm run plugin -- check|build|test <name>` all pass.
- The plugin source has no `shortcut:` and uses none of the old interfaces in the §5 "Delete" column.
- The menu snapshot matches this plugin's part of P0's `menus-before.json` (paths, titles, shortcuts); the coordinator re-checks with the same script.
