# 2026-10 round: interface languages

Started 2026-10-24. **This file is the only progress record for this round.**

## User rulings (2026-10-24)

- All interface text has **English as the source text**; Chinese becomes a translation.
- Interface languages: the English source + 6 translations — Simplified Chinese, 日本語, 한국어, Deutsch, Français, Español, 7 in total. **Traditional Chinese is dropped** (user: there are not many users in Hong Kong and Taiwan, and they can read English; users in Singapore use Simplified Chinese).
- The interface language can be chosen in Options; the default is "Follow system". When the system language is not supported, English is used.
- No separate Slint copy per language; use Slint's `@tr` with gettext catalogs, and TS text goes through the same catalogs provided by the SDK. Plugin authors decide which languages they provide.

- 2026-10-24, the three questions in the maintainer's proposal:
  - Traditional Chinese is dropped, so the fallback question no longer exists;
  - if stage 0 confirms that CJK glyphs are really wrong, it is **allowed** to set a system-provided interface font per language, for ja and ko only; this is an exception to the 10-22 ruling "do not set fonts";
  - live switching uses option B: the external Translator of Slint's internal library i-slint-core, wrapped in a single file `src/host/src/i18n/slint_bridge.rs`, with one more item on the upgrade checklist, and at the same time a request to Slint upstream for a public API; if it stops working, fall back to option A, i.e. rebuild the windows when the language changes.

## Revision (2026-10-24, user ruling; replaces the conflicting parts of the proposal below)

- **A language change takes effect only at the next start**; live switching is dropped. When the language is changed in Options, the hint "Takes effect after restart" is shown.
  - When loading plugins, the host uses Slint's public file loader to replace the source text in `@tr("source")` with the translation for the current language; Slint only does formatting.
  - So **there is no longer a dependency on the internal i-slint-core API** (the previous ruling "use the internal library" is void). Plurals only distinguish 1 and not-1.
- **Plugins write no translation code in TS when they support several languages**:
  1. Declared text (menu titles and paths, settings page titles, panel/tab names, window titles, the manifest's name/description) is filled with the English source, and the host translates it with that plugin's catalog;
  2. all text in windows is written in Slint with `@tr`; TS only passes data;
  3. for text that TS sends directly, such as OSD and dialogs, the API takes "template + arguments", e.g. `osd.show("Speed {}×", [rate])`, and the host looks the template up in the catalog.
  - Rule: sentences that users see are not concatenated in TS; `vestra-plugin check` detects this as far as it can.
- **SDK**: only a read-only `plugin.i18n.locale`; no `t()`, `onChange` or translation references.
- **Process**: top-down as in §5, assigned in two rounds; the concurrency limit for this round is raised to 8:
  - Round 1: the maintainer finishes the host, the SDK and the migration guide, and migrates preferences personally as the reference → the coordinator reviews, verifies on a real machine, merges, releases;
  - Round 2: all plugin authors migrate in one go, including writing `zh-Hans.po` along the way; 5 translation agents (ja, ko, de, fr, es) start at the same time once they have the `.pot`; the independent reviewer reviews, the coordinator takes the real-machine screenshots.

## Round 2 requests

### audio (R2-audio-1): command titles with template arguments

- **Requesting plugin / code location**: `src/plugins/audio/main.ts` `rebuildTracks` (the dynamic menu items 「声音 ▶ 音轨 ▶ <音轨>」 (Audio ▶ Audio Track ▶ <track>)), `model.ts` `trackTitle`.
- **User action and expected result**: a Chinese user opens 「声音 ▶ 音轨」 (Audio ▶ Audio Track); a track without title and language shows 「音轨 2 (opus)」, an external track shows 「3. movie.ac3 (ac3)（外部）」, the same as before the migration.
- **Why the current API cannot do it**: a command's `title` / `path` segments can only be source strings, and the host looks up the whole sentence in the catalog. A track title is made of data (number, codec) and words (「音轨 {}」 "Track {}", 「（外部）」 "(external)"), so there is no fixed source text to look up; SDK 1.5.9 has no `t()`, and TS must not concatenate sentences. Minimal repro: `plugin.commands.add({ id: "t", path: ["@audio", "Audio Track", "Track 2 (opus)"], run })`; under `startPlugin(..., { locale: "zh-Hans" })`, `display.path[2]` is still `"Track 2 (opus)"`, even if `zh-Hans.po` has `msgid "Track {} ({})"`. Windows and OSD already use templates (`@tr("Track {} ({})", …)`, `osd.show("Audio track: Track {} ({})", [n, codec])`); only menus cannot.
- **Desired usage** (consistent with `osd.show`, an optional field, does not break the existing contract):

  ```ts
  plugin.commands.add({
    id: `audio.track.${t.id}`,
    path: ["@audio", "Audio Track", "Track {} ({})"],
    args: [n, codec], // applies only to the last segment (the title); extract collects the template as usual
    run,
  });
  ```

- **Who owns state and resources; on failure or missing capability**: at registration the host translates the template with the plugin's catalog and then fills in the arguments (same rules as OSD; arguments are not translated); older players ignore `args` and show the unfilled template — so either `minPlayerVersion` goes up one more step, or the SDK formats the English first on older players.
- **Does it break the existing contract**: no, a new optional field. Plugins that may also use it: dynamic menus with suffixes like 「（外部）」 (external) or 「（无记录）」 (no record) (subtitles, history, etc., to be confirmed by their authors).
- **Minimal acceptance scenario**: under `locale: "zh-Hans"`, the `display.path` of an untitled track is `["声音", "音轨", "音轨 2 (opus)"]`, and an external track is `"3. movie.ac3 (ac3)（外部）"`.
- **Workaround this round**: in the menu these two cases show English (`Track 2 (opus)`, `… (external)`); other track titles are data anyway (`1. 日语 [jpn] (aac)`) and are not affected. See the limitations section of `README.md`.

### info: plain text the plugin generates itself (clipboard, saved files) cannot be translated (2026-10-25, info author)

- **Requesting plugin / code location**: `src/plugins/info/about.ts` `aboutText()` ("Copy Info"), `properties.ts` `pageText()` ("Copy to Clipboard" and "Save As…" in Playback Properties).
- **User action and expected result**: when a Chinese user clicks "Copy Info" in "About Vestra Player", or "Copy to Clipboard" / "Save As…" in "Playback Properties", the text they get is Chinese, the same as in the window (this was the case before the migration); English users get English.
- **Why the current API cannot do it**: the plugin assembles this text and hands it out: `clipboard.writeText(text)` only takes a string, and saving is done by the plugin itself with Node `fs`. The content is a number of "label: value" lines; labels, units (`字节` bytes, `核` cores) and status words (`运行中` running) are fixed words, values are data. The catalog exists only on the host side; the plugin cannot get translations and may not build sentences in TS. This is not one of the known r2-api cases (a [string] list in a window, nested arguments, saveFile's fileName): this text does not go through any host display interface and ends up as a string or a file. Minimal repro: `plugin.clipboard.writeText(\`版本 ${v}\`)`; after changing it to the English source, a Chinese user copies English, and there is no way to get the translation back.
- **Desired usage** (either works, the maintainer chooses):
  1. r2-api's translatable values can also be passed to `clipboard.writeText`, plus a read-only formatter: `const text = await plugin.i18n.format(value)`, which returns a string translated and formatted for the current language, used to write files.
  2. Only "host writes it for you" interfaces such as `clipboard.writeText(template, args)` and `dialogs.saveText({ fileName, text: template, args })`; content with a variable number of lines uses r2-api's list value.
- **Who owns state and resources; on failure, cancel, missing capability**: translation and formatting belong to the host, same as OSD templates; without a translation the English source is used; on old players (< 0.4.3) without this interface the plugin keeps writing English.
- **Does it break the existing contract, which plugins are affected**: new, does not break anything. Any plugin with "Copy as text" or "Export .txt/.srt/.csv" with fixed words would use it (info has 3 places; subtitles, bookmarks and playlist exports may too).
- **Minimal acceptance scenario**: `startPlugin(activate, { locale: "zh-Hans" })`, trigger `copy-info` in the About window; `host.clipboard.text` starts with `Vestra Player\n版本 0.1.0（构建 …）`; the first line of the saved Playback Properties file is `视频`.
- **One more point (please consider it in the r2-api design; no separate request)**: in the brief info (Shift+Tab), each line has to be truncated to the width of the video area (`fit()`, CJK characters count as two columns), and truncation must happen after translation and formatting. If the host formats r2-api's nested OSD arguments, the plugin cannot measure the width of the final text: either the host truncates by columns (e.g. `OsdPanel.set(value, { maxColumns })`), or the plugin first gets the string with `format()` from option 1 above.

**Current state**: the three texts above, the playback info overlay (Tab / Shift+Tab) and the lines of Playback Properties are all English for now, marked `// i18n: needs r2-api` in the code; the window's own text (title, tabs, buttons, status, labels of the About window, source and status words), menus and OSD messages can already be translated, and Chinese is the same as before the migration.

## Round 2 reply (API maintainer, 2026-10-25): text values

Each plugin author's round 2 requests are written in their own worktree's copy of this file (the subsections of "Round 2 requests"); this section answers all of them at once. Branches: host `i18n/r2-api` (based on `origin/i18n/round1`, with D1 `fix/ui-value-limits-main` merged in), SDK `feat/i18n-texts` (based on the SDK's `fix/ui-value-limits`, i.e. 1.5.10 D1, version **1.5.11**).

### Classification (§4.2)

All requests share one root cause: text that users see mixes fixed words with data, or is made of translated fragments, while TS can neither translate nor build sentences (user ruling). Per §4.2 item 5 they are merged into one design issue instead of adding fields one by one (e.g. no `args` on `commands.add` that applies only to the last segment, no separate `{text,args}` argument just for OSD, no separate control just for ComboBox). Why it belongs in the core: the catalog exists only in the host, rendering must happen in the host (§4.3 item 1), and more than a dozen plugins need it (item 4).

| Request | Decision |
| --- | --- |
| R2-audio-1 (+video, playback, subtitles, store, history, marks) | Accepted after rewrite: path segments / titles / reasons can be text values |
| capture request 1, R2-subtitles-1, R2-workshop-1 | Accepted after rewrite: any `string` position in property values can be a text value (including `[string]`) |
| R2-subtitles-2, R2-playlist-1, R2-store-1, capture observation, hotkeys mouse OSD | Accepted: arguments can be text values, nestable |
| R2-video-1 (+workshop's capability list) | Accepted: list values, with per-language separators |
| R2-playlist-2 (+hotkeys' fileName) | Accepted: `saveFile`'s `fileName` can be a text value; a string is still data |
| P-2 | Accepted: `BindingInfo.key` |
| capture observation (extract misses spread fields) | Fixed as a defect: spread fields are read by type; if they cannot be read, it is reported |
| R2-nes-1 | Accepted after rewrite: `plugin.i18n.error(…)`, no `ResolveError` class or `respond { args }` |

### Design

A **text value** is plain data, not a translation:

```ts
const { text, list, error, resolve } = plugin.i18n;
text("Track {} · {}", [7, "en"])   // → { $vestraText: "Track {} · {}", args: [7, "en"] }
list(["a.glsl", "b.glsl"])         // → { $vestraList: ["a.glsl", "b.glsl"] }
```

- Arguments are data (strings, finite numbers), or again text values (translated the same way); nesting up to 8 levels. Lists are joined by interface language: `list` `, ` / `、`, `clauses` `, ` / `，`, `semicolons` `; ` / `；`, `sentences` `. ` / `。`, `lines` newline (Japanese `、 、 ； 。`; French has a narrow space before `;`; the table is in the host's `i18n::text::SEPARATORS` and the SDK's `LIST_SEPARATORS`, and host-agreement checks they match).
- **Host rendering**: at display time the host looks up `source` in that plugin's catalog, then substitutes the rendered arguments (same rules as `@tr`); without a translation English is shown. There are no translation calls in TS; `text()` only builds data (an `Object.freeze`d `{ $vestraText, args }`, with limits checked at construction).
- **One mechanism, every display surface**: command `title` / each `path` segment / `reason`; the text and arguments of `osd.show` and `OsdPanel.set`; every field of confirmation dialogs; file dialog `title` and `saveFile`'s `fileName`; any position whose Slint type is `string` in window / panel / settings page properties; `TimelineLayer.set` titles; `subtitles.load` titles; `plugin.i18n.error(…)` thrown by resolvers.
- **Slint side**: Slint does not know about text values. At the start of `dispatch`, the host replaces text values in the arguments of `ui.open`, `ui.set`, `ui.mount`, `ui.setMount`, `settings.register`, `settings.set` (and `timeline.set`, `subtitles.commit`, and the `error` of `sourceResolvers.respond`) with strings, and only then takes the original path; `set_property` receives only strings, and `[string]` ComboBoxes need no change. `$vestra…` keys cannot clash with real struct fields (Slint identifiers cannot start with `$`; the same convention as `$vestraImage` and `$vestraMarkdown`).
- **D1 limits**: replacement happens before the limit check, so `UI_VALUE_LIMITS` counts the displayed strings. Text values have their own limits `TEXT_LIMITS`: nesting 8, 1024 nodes per value, 16 arguments, 256 items, 4096 bytes (template string arguments raised from 1024 to 4096 bytes).
- **Menu keys**: the key of a Text segment is its English rendering (`Track 2 (opus)`); menus merge by key and the bindings table `key` gives it; the display text is the translation. List values cannot be menu segments.
- **Protocol**: `vestra/1` only gains new shapes, which appear only when a plugin uses the new API; the semantics of strings and `args` for old plugins are unchanged. Plugin code runs on the SDK bundled with the player, so text values arrive with player 0.4.3; plugins that use them set `minPlayerVersion: "0.4.3"`.
- **Extraction**: `vestra-plugin i18n extract` collects the `source` of each `plugin.i18n.text(…)` / `error(…)` / `resolve("…")` (literals, both branches of conditionals, `as const` tables; both `plugin.i18n.text` and a destructured `text` are recognized, resolved to the `I18n` interface by the type checker), as well as `{ $vestraText: "…" }` literals; a `source` with only placeholders and punctuation (`"{} ({})"`) is also collected, because Chinese needs full-width punctuation `"{}（{}）"` (reported by the capture author, fixed 2026-10-25). Fields typed as text values are no longer reported as "not a literal". Fields spread into call options (`commands.add({ ...extra })`) are read by type; if they cannot be read, `… spread into Commands.add is not a literal` is reported.
- **TestHost**: renders the same way as the host: `FakeCommand.display` (new non-enumerable `display.reason`, so old tests with `deepEqual(display, { title, path })` are unchanged), `host.osd`, `host.osdPanel` (truncated by `maxColumns`), `host.confirmTexts`, the new `host.fileDialogs`, window/panel/settings page `props` (already replaced by strings; the raw form is in `host.sent(…)`), timeline and subtitle titles, the resolver's `TextError`, `BindingInfo.key`; invalid text values are rejected as `invalid` in the same way.
- **`resolve`** (the single exit point): returns a string synchronously; the SDK reads the same catalog in the plugin process (`locales/<lang>.json`, `.po` during development). Only for the clipboard and files; the interface always gets text values.
- **Truncation**: `OsdPanel.set(value, args, { maxColumns })`; after translation and formatting the host truncates each line with `unicode-width` (wide characters are 2 columns), ending with `…`.

### How to write each request

```ts
const { text, list, error, resolve } = plugin.i18n;
// menus of R2-audio-1, video, playback, store, history, subtitles

path: ["@playback", "Seek", text("Back {} s", [seconds])]  // playback (the player's "Back {} s" is the player's own entry; the plugin catalog needs this entry too)

// capture #1, R2-subtitles-1, R2-workshop-1: [string] models

// R2-store-1: permission list, source, reason

  detail: text("From {}, author {}.\n\n{}", [text(SOURCES[kind]), author,

(await plugin.bindings.list()).commands.find((c) => c.key?.join("/") === "Playlist");
```
