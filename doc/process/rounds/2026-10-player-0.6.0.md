## 2. Findings that led here (measured)

- **Every video picture relaid out the window** (host 0.5.24 fix, render-modes §11.7): the video `Image` had no x/y, so Slint merged its size into the window layout; with AccessKit active every dirty node was rebuilt per frame. VestraTube's sidebar (668 accessible nodes) showed 20 fps windowed in both CPU and GPU modes; paused or with the playlist tab it was 60.
- **Large playlists** (headless benches, scratchpad `biglist_bench.rs`, `playlist_pass_bench.ts`): cost depends on the rows sent to Slint (≤ 200, the playlist's window), not on the list length. All 200 rows are instantiated (`ScrollView` + `for`): idle redraw 7–8 ms vs 2.5 ms empty; pointer move over the list 2.7 ms; one changed row costs a whole-array JSON reconcile (2.5 ms), a window shift ~22 ms; each menu hover rebuilds the whole menu (~3 ms) plus a redraw. Pause delay: the UI thread busy (12–45 ms) plus `paused` waiting for the 100 ms state push. The shared runner is not the cause (p95 0.05 ms).
- **Upscaling "waits until other filters are off"**: the built-in video plugin's colour value 0.4 (slider looks centred) keeps an FFmpeg `eq` filter → copy-back decoding → upscaling reason `decoding`. VestraUpscale showed every `decoding` cause as "another filter is on".
- **Slint audit** (all .slint in the player, plugin repository and SDK): MUST — VestraTube sidebar, playlist sidebar, playlist drag marker `if`s, Options page list, About plugin list, Properties window (plus a hidden measuring loop), playback bar marks (8,192 rectangles), `MarkdownView`, the SDK panel-menu example. SHOULD — capture tasks, video shaders list and picture popup, audio workbench popup, four dropdown / five checkbox / four radio / four tab copies, the Slider's missing keyboard and accessibility, store's "⋯" menu. KEEP — `MenuView` (bounded), sidebar tabs, theme widgets, the hotkeys sortable header.

## 4.1 Open topics after 0.6.0

- **Capabilities written by hand** (user question 2026-10-31): closed — keep authors writing the capability list (user ruling 2026-10-31: Chrome precedent; not important now; no extra work while the player is being stabilised). No tooling change.
- **Automatic tracking of plugin async code** (user ruling 2026-11-01: after the current 0.6.0 work; record the design now). Purpose: authors never need `plugin.update()`.

  *Problem.* With P2 (SDK 1.5.45) the SDK knows when to re-run a bind in two ways: it tracks which host-state fields a bind read (a `paused` change re-runs binds that read `paused`; a `position` tick skips binds that did not read it), and it runs a full pass after plugin code it invoked itself (command `run`, view callbacks, listeners, `plugin.update()`). It cannot see a plugin's own variables changing in code it did not invoke: a promise continuation after the handler returned, `await` continuations, the plugin's own `setTimeout`/`setInterval`, stream and socket callbacks. Example: `setTimeout(() => myCounter++, 500)` in a command, or `player.chapters().then(c => { this.list = c })` (marks/chapters.ts). Before P2 the 100 ms full pass while playing hid a missing `update()` (≤ 0.1 s late; never refreshed while paused); with P2 the 1 s safety pass shows it ≤ 1 s late. The P2 review found six such places in built-ins (marks, playlist ×3, capture ×2), fixed with `update()`.

  *Design (runtime, not static analysis).* Node's `AsyncLocalStorage` (node:async_hooks) carries a value through every asynchronous continuation started inside `run()`: promise reactions and `await`, timers, I/O callbacks, event emitters bound with `AsyncResource`. The SDK runs each piece of plugin code it invokes inside `context.run(runtime, fn)` (activation included, so timers created at start-up are covered). Every continuation then runs with `context.getStore() === runtime`. When such a continuation finishes, the SDK schedules one full pass for that runtime (coalesced per microtask turn / per tick, so many callbacks in one turn cost one pass). Ways to detect "a continuation of this plugin finished": an `async_hooks.createHook({ after })` hook reading the store (simplest, measurable cost), or wrapping the scheduling primitives the plugin can reach (`setTimeout`/`setInterval`/`queueMicrotask`/`Promise.prototype.then` in the plugin's realm) — to be chosen by measurement. In the shared runner each plugin has its own runtime and store value, so one plugin's callbacks never trigger another's pass.

  *Result.* `update()` becomes unnecessary (kept as a no-op-safe explicit call); state changed in any plugin callback shows at once, also while paused (better than before P2). The ruling for synchronous `player.onChange` listeners that read only unchanged fields can stay (their pass is still skipped unless they changed something — the hook cannot tell, so they would get a pass; measure whether that matters for the playlist). A plugin timer running every 100 ms then causes a full pass every 100 ms — correct, since its code ran.

  *To verify before adopting.* Cost of the hook / wrappers in the shared runner with all built-ins loaded (per-callback overhead, GC); that the context survives every path plugins use (native addons, child processes, `EventEmitter` from Node core, the runtime's own IPC callbacks must not count as plugin code); interaction with the 1 s safety pass (can it be dropped?) and with lazy activation (a parked plugin has no runtime). SDK-internal, no API change; a patch release.
