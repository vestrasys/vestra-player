# 插件商城（`vestra.store`）设计与 API 缺口

日期：2026-10-22。作者：商城插件作者（生态计划 S5，[本轮](../process/rounds/2026-10-slint-store.md)步骤 2.1）。状态：**设计稿，待协调者决定（步骤 2.2）**，未实现。

依据：[生态计划](../product/ecosystem-plan.md) 1.1–1.6（尤其 1.3 索引格式、1.5a id 与安装实例、1.6 的 12 条决定、S3 后半记录）；[S4 提案](../architecture/store-api-proposal.md)；[store-changes](store-changes.md)；[API 参考](reference.md)；SDK `@vestra-player/sdk` 1.1.2 的 `types.d.ts`；插件仓库 `scripts/lib/{signing,semver,publishing,revoked}.mjs`、`keys/index-signing.pub.pem`；线上 `https://vestrasys.github.io/vestra-player-plugins/index.json` 与 `.sig`（2026-10-22 取得，用内置公钥验签通过，篡改一个字节后失败）。

## 0. 结论

- 商城是一个**独立的内置插件** `vestra.store`，放在 `src/plugins/store/`，随播放器发版（1.6 第 6 条）。它负责「发现 → 安装 → 更新 → 回退」；插件管理（`vestra.plugins`）继续负责「已安装插件的运行控制」。两者不互相调用，只通过公开的 `plugin.packages` 看到同一份安装库（§1.3）。
- 主界面是一个工具窗口：左边列表，右边详情（README / 更新日志 / 版本三个标签，右栏为信息与权限）；另有一个「选项 ▶ 插件 ▶ 插件商城」设置页管理第三方仓库与自动检查。
- 官方索引用内置的 Ed25519 公钥校验（Node 内置 `crypto`），包用 `sha256` 和 `size` 校验，安装走 `packages.validateArchive` → `install({ source, replace })`。
- **v1 不需要任何新的宿主或 SDK API**。证据见 §9.1。另列两条可选的改进（列表图标、工具窗口拖放）和一条契约澄清（同来源安装低版本），都不阻塞实施。

## 1. 定位与身份

### 1.1 插件身份

| 项 | 值 |
| --- | --- |
| 目录 | `src/plugins/store/` |
| id | `vestra.store`（与 `vestra.plugins`、`vestra.workshop` 同一规则；宿主不认 id，内置身份来自 `bundled` 来源） |
| `minPlayerVersion` | `0.2.0`（用 `validateArchive`、`install(options)`、`ui.markdown`） |
| capabilities | `commands`、`ui.window`、`ui.dialog`、`ui.osd`、`ui.drop`、`ui.settings`、`plugins.manage` |
| 显示字段 | `name: "插件商城"`、`author: "Vestra Player"`、`punchline: "浏览、安装和更新插件"`、`tags: ["插件"]`、`license` 与主仓库一致 |

不要 `events`、`playback.*`：商城与播放状态无关。`packages.list` / `onChange` 不需要能力。

### 1.2 入口

| 功能 | 主菜单路径 | 其它入口 | 行为 | 启用条件 |
| --- | --- | --- | --- | --- |
| 打开商城 | `插件商城…`（顶层，`order: 822`，`group: "windows"`，紧跟 820「插件工坊…」） | 有可更新的插件时标题改为 `插件商城（2 个可更新）…` | 打开窗口；索引超过 10 分钟就刷新 | 总是 |
| 安装插件包文件 | — | 把 `.vxp` 拖到视频区；商城窗口「从文件安装…」 | 校验 → 确认框 → 安装 | 总是 |
| 从链接安装 | — | 商城窗口「从链接安装…」 | 输入行 → 下载 → 校验 → 确认 → 安装 | 总是 |
| 仓库与自动检查 | — | 「选项 ▶ 插件 ▶ 插件商城」设置页；商城窗口「仓库…」按钮打开这一页 | 设置页 | 总是 |

- 顶层而不是放在「设置 ▶」下：它和「插件工坊…」一样是打开工作窗口的入口（[menus.md](../product/menus.md)「界面形式」把工坊列为工具窗口，`windows` 组 800–899），不是一个设置项。**加顶层菜单项需交互负责人批准**（[工作流](../process/community-workflow.md) §2.1），列入 §11 待决问题。
- 不设默认快捷键（VS Code 的 ⇧⌘X 在这里没有约定俗成的意义）；用户可以在「设置 ▶ 快捷键…」绑定。
- 改标题的方式：命令放在子作用域里，计数变化时释放再添加，`order` 不变（reference §4 的写法）。

### 1.3 与插件管理的关系：分开，不合并

生态计划 1.4 写的是「商城扩展现有的 `plugins` 插件」。按 1.6 第 11 条插件之间不能依赖，「扩展」只能是合并成一个插件或分成两个。**决定分开**，理由：

| 考虑 | 合并 | 分开（采用） |
| --- | --- | --- |
| 可停用 | 插件管理不能停用自己，合并后商城的联网检查也关不掉，只能靠设置项 | 不想联网的用户可以在插件管理里停用商城；插件管理不受影响 |
| 故障隔离 | 商城的网络、下载、Markdown 代码与插件管理在同一进程，商城出错会让插件管理一起失败 | 商城失败时插件管理仍能停用、卸载、回退 |
| 界面形态 | 插件管理是 440 宽的设置页，放不下「列表 + 详情 + README」 | 商城用工具窗口 |
| 所有权 | 两个作者改同一目录 | 各管各的目录（工作流 §1） |
| 重复代码 | 无 | 能力说明表、来源文字约 60 行，各自一份（插件之间本来就不共享代码） |

分工：

| 操作 | 商城 | 插件管理 |
| --- | --- | --- |
| 浏览仓库、搜索、README、权限、版本历史 | ✔ | — |
| 安装（仓库、链接、文件、拖入）、替换其它来源 | ✔ | — |
| 更新、安装其它版本、回退到上一版本 | ✔（回退只在详情页「已安装」状态显示） | 回退（已有，保留） |
| 卸载 | ✔（详情页，与 VS Code 一致，是安装生命周期的一部分；调用同一个 `packages.uninstall`） | ✔（已有） |
| 撤回处理（自动停用被撤回的版本） | ✔ | — |
| 停用 / 启用、重新加载、数据目录、数据大小、失败原因 | — | ✔ |

商城详情页对已安装插件显示一行提示：「停用、重新加载、查看数据目录：设置 ▶ 插件管理…」。商城不能直接打开插件管理的设置页（`settings.show` 只接受本插件的页面），这是插件独立的结果，不提请求。两边同时操作同一插件时，宿主的安装库是唯一真相：两边都订阅 `packages.onChange`，宿主对并发操作返回 `busy`。

- **列表**（宽 300，`ListView`，行高 52：名称 + 版本，作者 · 仓库标记 + 状态，一句话简介，省略号截断，悬停显示全文）。一行对应一个「（仓库，id）」；同一 id 出现在两个仓库就是两行，各自标明仓库。已安装但不在任何仓库里的插件（内置、链接、文件、工坊、其它仓库已删除）也列出，仓库标记写来源（「内置」「本地文件」「链接」「插件工坊」）。
- 列表**不显示每个插件的图标**：`ImageRef` 只能作为属性的整个值，不能放进列表行（reference §6.1）。详情页显示图标。见缺口 G1（可选）。
- **过滤**：「全部」= 各仓库的插件 + 已安装插件；「已安装」= `packages.list()` 里 `origin: "installed"` 的；「可更新」= 有可更新版本的（§3.6）。搜索不区分大小写，匹配名称、id、作者、简介、标签（子串，中文按字符）。标签下拉列出当前可见插件的全部标签。排序：名称（默认，按 `localeCompare("zh")`）或更新时间（最新版本的 `published`，新的在前）。不显示下载次数（1.6 第 9 条）。
- **详情**：图标（`iconUrl` 下载缓存后 `ui.image`；没有图标或失败时显示包里自带的 Vestra Player logo `assets/logo.png`）、名称、作者、仓库、简介、操作按钮、提示条；左边三个标签页，右栏信息与权限。
  - 「说明」：README（`readmeUrl`，或已安装插件包里的 README）；「更新日志」：`changelogUrl` 或包里的 CHANGELOG；没有时显示「作者没有提供说明」「作者没有提供更新日志」。
  - 「版本」：版本历史表（版本、发布日期、`minPlayerVersion`、状态：当前 / 不兼容 / 已撤回），每个可安装的旧版本行尾有「安装」按钮。
  - 右栏「权限」：manifest 的 capabilities 按 §2.4 译成人话，高风险项标琥珀色；末尾固定一行灰字「插件是完整的程序，以上权限只限制它使用播放器的功能，不限制它读写文件和联网。」（1.6 第 4 条）。
- 没有选中时右侧显示「选择左侧的插件查看详情」；列表为空时显示原因（离线且无缓存、过滤无结果）。
- 底部状态行：每个仓库的刷新结果，进行中的下载 / 安装进度与「取消」。
- 「从链接安装…」在列表上方展开一行 `UrlInputRow`（控件库已有，`confirm-text: "安装"`），Esc 收起。
- 打开 / 关闭：窗口关闭（`onClose`）只停止进行中的 README 加载；下载、安装、后台检查不受影响，下次打开回到上次选中的插件。焦点在打开时给搜索框。

### 2.2 Markdown 规则

| 项 | 规则 |
| --- | --- |
| 来源 | 仓库插件：GET `readmeUrl` / `changelogUrl`（≤ 256 KB，10 秒，规则同 §3.2 下载）；已安装且不在仓库：读 `info.directory` 里 manifest 的 `readme` / `changelog`（默认 `README.md` / `CHANGELOG.md`） |
| `base` | 仓库插件用 `readmeUrl` 本身（相对图片和链接按它解析）；本地 README 用包目录 |
| 远程图片 | **官方仓库开**（`remoteImages: true`）；**第三方仓库与链接关**，README 里有 `![…](http…)` 时详情页提示条显示「已阻止 N 张远程图片 [显示图片]」，点了只对这个插件在本次运行内重新渲染为 `remoteImages: true`。理由：远程图片会把用户的 IP 发给任意第三方服务器（跟踪像素） |
| 本地 README 的相对图片 | 位于别的插件的包目录，`ui.markdown` 只读本插件包与数据目录，所以显示替代文字。接受（侧载插件的 README 图片少见，不为此开放跨插件读路径，S4 §10 已有同样结论） |
| 链接 | `link-clicked(url)`：`http(s)` 用 `system.openUrl` 打开；`#锚点` 忽略（MarkdownView 没有目录跳转）；其它协议忽略并在状态行提示「不支持打开这种链接」 |
| 缓存 | README / CHANGELOG 文本按 URL 缓存在内存（本次运行），切换插件不重复下载 |

### 2.3 状态与按钮

状态按「这一行（仓库 R，id）」与安装库里同 id 的条目（`packages.list()`）比较得出；`v*` 是 §3.5 选出的「可安装的最新版本」。

| 状态 | 条件 | 主按钮 | 提示条 |
| --- | --- | --- | --- |
| 未安装 | 安装库里没有这个 id | 「安装」（装 `v*`） | 第三方仓库：琥珀色「非官方仓库：未经 Vestra Player 审核」 |
| 已安装（最新） | 同 id、来源 = R、版本 ≥ `v*` | 「卸载…」；有 `previousVersion` 时加「回退到 x.y.z」 | — |
| 可更新 | 同 id、来源 = R、`v*` 更高 | 「更新到 x.y.z」、「卸载…」 | 新版本新增了权限时：「新版本需要新的权限：…」 |
| 已从其它来源安装 | 同 id、来源 ≠ R、非内置 | 「替换…」 | 「已从 <来源> 安装 <版本>。替换后使用新的空数据，原数据保留」 |
| 内置插件同 id | 安装库里该 id `builtin: true` | 无（按钮禁用，悬停「内置插件随播放器更新」） | 「与播放器内置插件同 id，不能从这里安装」 |
| 不兼容 | 没有任何版本满足 `apiVersion` 与 `minPlayerVersion` | 无 | 「需要 Vestra Player ≥ x.y.z（当前 a.b.c）」或「需要更新的插件 API（vestra/2）」 |
| 已撤回（已安装版本） | 已安装版本落在 R 的 `revoked` 范围里 | 有修复版本时「更新到 x.y.z」，否则「卸载…」 | 红色「此版本已被撤回：<原因>。商城已停用它」（用户手动重新启用后改为「…你已手动重新启用」） |
| 全部版本已撤回 | 未安装且所有兼容版本都被撤回 | 无 | 「此插件已被撤回：<原因>」 |
| 进行中 | 本行有下载 / 安装 / 卸载在进行 | 「取消」 | 进度 |
| 只在本机（不在任何仓库） | 安装库里有，所有仓库都没有这个 id 或来源仓库已移除 | 「卸载…」，有 `previousVersion` 时「回退」 | 来源是链接 / 文件 / 工坊时：「侧载插件：未经审核，商城不会为它检查更新」 |

开发加载（`origin: "development"`）和试载不在「已安装」里，也不影响上表（它们本次运行优先，商城照常显示安装库的状态，并在提示条写「本次运行使用开发加载的版本」）。

### 2.5 确认框（`dialogs.confirm`）

安装前一律确认（1.6 第 5 条「用户手动确认」；下载前就列出权限，1.6 第 4、10 条）：

| 场景 | message | detail | confirm |
| --- | --- | --- | --- |
| 官方仓库安装 | `安装「YouTube」0.2.0？` | `来自 Vestra Player 官方仓库，作者 Vestra Player。\n\n它将可以：\n· 控制播放…\n\n插件是完整的程序，以上权限只限制它使用播放器的功能，不限制它读写文件和联网。` | 安装 |
| 第三方仓库安装 | `安装来自非官方仓库的「X」1.3.0？` | `仓库：Foo（https://foo.example/）。这个仓库未经 Vestra Player 审核，插件可能读取你的文件或联网。只安装你信任的作者的插件。\n\n它将可以：…` | 仍然安装（`destructive`） |
| 链接 / 文件（侧载） | `安装插件包「X」1.0.0？` | `来自 <链接或文件名>，未经任何仓库审核，也不会自动更新。…它将可以：…` | 仍然安装（`destructive`） |
| 更新（权限不变） | `更新「X」到 0.2.1？` | `当前 0.2.0。更新后可以在商城回退到 0.2.0。` | 更新 |
| 更新（权限增加） | `更新「X」到 0.3.0？新版本需要更多权限` | `新增：· 读写剪贴板 …` | 更新 |
| 安装旧版本 | `安装「X」0.1.0（旧版本）？` | `当前 0.2.0。` | 安装 |
| 替换其它来源 | `替换已安装的「X」？` | `当前的 X 0.2.0 来自 <来源>。替换后新插件使用新的空数据；原插件的数据保留，以后从原来源重新安装时接上。` | 替换（`destructive`） |
| 卸载 | `卸载「X」？` | `它的菜单、窗口和处理效果会立即撤销。` + 复选框「同时删除它的设置与数据」（默认不勾，与插件管理一致） | 卸载（`destructive`） |

`detail` 超过 2000 字符时把权限列表截成前 20 项加「等 N 项」。

## 3. 数据流

### 3.1 仓库与地址

- **官方仓库**：`https://vestrasys.github.io/vestra-player-plugins/index.json`，写在代码里，设置页里不能移除或关闭（官方仓库是商城存在的理由；不想联网的用户在插件管理里停用商城）。
- 用户输入的地址按 1.1 规范化：WHATWG 解析；只收 `https:`（另收 `http://localhost`、`http://127.0.0.1`、`http://[::1]`，方便作者测试自己的仓库，显示额外警告）；去掉 `#…`；路径以 `.json` 结尾就原样使用，否则补 `/` 再拼 `index.json`。规范化后的 `href` 就是 `PackageSource.url`（宿主再做一次同样的规范化后逐字比较，`package_manager.rs` `normalize`），所以「只从原来源更新」按这个字符串判断。
- `index.json.sig` 的地址 = 索引地址 + `.sig`。

### 3.2 HTTP（插件进程里的 Node `fetch`）

插件进程是完整的 Node ≥ 22.18（reference 开头：「可以使用 Node 标准库、文件系统、网络和 npm 依赖」），不需要宿主 API。所有请求经过一个函数 `get(url, limits)`：

| 规则 | 值 |
| --- | --- |
| 协议 | 每一跳都必须 `https:`（本机例外同 3.1）；跳到 `http:` 或别的协议即失败 |
| 重定向 | `redirect: "manual"` 手动跟随 ≤ 5 次（GitHub Releases 下载会 302 到 `release-assets.githubusercontent.com`，已实测） |
| 超时 | 连接 + 首字节 15 秒；整个请求：索引 30 秒，包按 `max(60 秒, size / 100 KB/s)` |
| 大小 | 流式读取并计数，超过上限立即中止；`Content-Length` 超过上限的直接拒绝 |
| 上限 | `index.json` 4 MB；`.sig` 1 KB；README / CHANGELOG 256 KB；图标 512 KB；仓库包按索引的 `size`（必须相等）；链接包 64 MB（与宿主 `.vxp` 上限一致） |
| 头 | `User-Agent: VestraPlayer/<app.version> vestra.store/<version>`；不带 cookie（Node fetch 本来不带）；条件请求用 `If-None-Match` / `If-Modified-Since` |
| 取消 | 每个请求一个 `AbortController`，窗口的「取消」、作用域释放（插件停用）都中止 |
| 并发 | 刷新时同时 ≤ 4 个仓库；同一时间只下载安装一个包（宿主同一 id 也只接受一个操作） |

### 3.3 签名校验

```ts
import { createPublicKey, verify } from "node:crypto";
// keys/index-signing.pub.pem（插件仓库），SPKI DER 的 base64；测试核对它的指纹。
const OFFICIAL_KEYS = ["MCowBQYDK2VwAyEA6DswGEDcZFAbqpeRjvANiIAI7aziHk6sYLnHRpW0pdY="].map((b64) =>
  createPublicKey({ key: Buffer.from(b64, "base64"), format: "der", type: "spki" }));

export function verifyIndex(bytes: Buffer, sigText: string, keys = OFFICIAL_KEYS): boolean {
  // 一个或多个签名，空白分隔（为换钥留余地，§6.3）；每个都是 64 字节的 base64。
  return sigText.trim().split(/\s+/).some((part) => {
    if (!/^[A-Za-z0-9+/]+={0,2}$/.test(part)) return false;
    const raw = Buffer.from(part, "base64");
    return raw.length === 64 && keys.some((key) => verify(null, bytes, key, raw));
  });
}
```

- 对**收到的原始字节**验签，验签通过后才 `JSON.parse`；绝不重新序列化、不做换行转换。
- 官方仓库：没有 `.sig`（404）、`.sig` 读取失败、验签失败 → 这次刷新失败，**继续使用上一份验证过的缓存**，状态行显示错误（§5）。
- 第三方仓库：v1 不校验签名（没有它们的公钥），即使有 `.sig` 也不读；界面一律标「非官方」（§4）。索引里自称 `official: true` 的第三方仓库**忽略这个字段**。「官方」只有一个判据：地址是内置的官方地址，且用内置公钥验签通过。
- 测试里注入测试密钥（构造函数参数，§8）；产品代码没有任何从设置、环境变量换公钥的路径。

### 3.4 解析与校验索引

按插件仓库 `publishing.mjs` 的 `indexProblems` 移植，但对**未知键宽松**（忽略），为 `extensions` 和以后的字段留余地；`schema` 必须是 `1`，否则整份拒绝（「仓库格式比这个播放器新，请更新 Vestra Player」）。

| 层 | 不合格时 |
| --- | --- |
| 顶层（`schema`、`name`、`plugins` 数组、`revoked` 数组） | 整份拒绝，用缓存 |
| 单个插件（id 规则同 reference §2；`versions` 非空；字段类型；URL 必须 `https:`） | 只丢这一项，日志一行 |
| 单个版本（`version` 严格 `x.y.z`；`sha256` 64 位小写十六进制；`size` 正整数且 ≤ 64 MB；`downloadUrl` `https:`；`capabilities` 字符串数组；`published` 可解析） | 只丢这个版本 |
| `revoked` 条目（id、`versions` 按 semver 语法可解析、`reason` 1–500 字符） | 只丢这一条（日志一行；官方索引在 CI 里已校验，正常不会发生） |
| 数量 | 插件 ≤ 2000、每个插件版本 ≤ 200、`revoked` ≤ 1000，超出部分忽略 |
| 显示字段长度 | 按 manifest 规则截断显示（名称 64、简介 120、描述 2000、标签 8×24），只当纯文本显示 |

重复 id：保留第一个。版本按 `versions` 原顺序（新到旧），客户端再按版本号排序一次，不依赖服务端顺序。

**回滚（冻结）防护**：对官方仓库，缓存里记下上一份已验证索引中每个插件的版本集合。新索引里某个仍然存在的插件**丢了已见过的版本**时（CI 的 `build-index` 保证旧版本条目原样保留，正常不会发生），判定为旧索引重放：拒绝这次结果、继续用缓存、日志一行。插件整个消失的情况接受（仓库可能删除插件）。这只是缓解，根本解决要索引带单调的生成序号，见 §11 问题 5。

### 3.5 版本选择

```text
compatible(v) = v.apiVersion === "vestra/1"
             && (v.minPlayerVersion === null || compare(app.version, v.minPlayerVersion) >= 0)
revoked(id, v) = R.revoked 中有 id 相同且 satisfies(v.version, versions) 的条目
v* = 按版本号从高到低第一个 compatible 且未 revoked 的版本
```

- `app.version` 来自 `plugin.app.version`（宿主 Cargo 版本，0.2.0），比较只取三段数字（与宿主规则一致，忽略预发布后缀）。
- `apiVersion` 写死 `"vestra/1"`：商城自己是 `vestra/1` 插件，能运行它的播放器就支持 `vestra/1`。将来播放器同时支持两个大版本时再按 §4 请求在 `plugin.app` 加支持列表；现在不需要。
- `satisfies` / `compareVersions` / `parseRange` 从插件仓库 `scripts/lib/semver.mjs` 原样移植成 `semver.ts`（同一语法：精确版本、`<`、`<=`、`>`、`>=`、`=`、空格连接、`||`、`*`；不支持 `^`、`~`）。测试用同一组用例。
- 「安装其它版本」列出全部版本；不兼容、已撤回的行禁用并说明原因。

### 3.6 刷新与更新检查

| 时机 | 动作 |
| --- | --- |
| 插件激活后 30 秒（不拖慢播放器启动） | 若「自动检查更新」开（默认开）且距上次检查 ≥ 6 小时：刷新全部仓库，计算可更新数 |
| 运行中 | 每小时看一次，距上次检查 ≥ 24 小时就再刷新 |
| 打开商城窗口 | 某个仓库的缓存超过 10 分钟（Pages 的 `max-age=600`）就刷新它；先显示缓存 |
| 「刷新」按钮 | 立即刷新全部，忽略时间 |
| 添加仓库 | 立即读取它（失败就不添加，§4） |

- **可更新** = 安装库里 `source.kind === "repository"`、`source.url` 等于某个仓库的地址、该仓库对这个 id 的 `v*` 高于已安装版本。其它仓库的同 id 高版本**不算**（1.5a「只从原来源接收更新」）。内置插件（来源 `bundled`）永远不算（1.6 第 6 条）。
- 有可更新时：菜单标题带计数；本次运行第一次发现时 `osd.show("插件商城：2 个插件可以更新")`（失败忽略）。**不自动安装**（1.6 第 5 条）。
- 自动检查关闭时，只在打开窗口和点「刷新」时联网（撤回检查也随之只在这时进行，设置页写明）。

### 3.7 缓存与离线

```text
<dataDirectory>/
  settings.json                  plugin.storage.json("settings")：仓库列表、自动检查、上次检查时间、已处理的撤回
  repos/<sha256(url) 前 16 位>/
    index.json  index.json.sig   原始字节（官方仓库只在验签通过后写入）
    meta.json                    { url, etag, lastModified, fetchedAt, versionsSeen }
  icons/<sha256(iconUrl)>.png|jpg   ≤ 512 KB，按内容判断 PNG/JPEG；总量 > 16 MB 时按访问时间淘汰
  downloads/<随机>.vxp(.part)       安装完成或失败后删除；启动时删除残留
```

- 写入都是「临时文件 + 改名」；Windows 上改名目标已存在时先删除（文件名每次随机，正常不冲突）。
- 启动时读缓存，官方缓存**再验签一次**才使用（防止数据目录被改）。
- 刷新得到 `304` 只更新 `fetchedAt`。网络失败时显示缓存并标明时间：「无法连接 <仓库名>，显示 <时间> 的缓存」。没有缓存又连不上：该仓库的插件不出现在列表里，列表顶部提示。
- 已安装插件的状态（已安装、来源、内置）任何时候都来自 `packages.list()`，不缓存。

### 3.8 安装：仓库来源

```text
1. 用户点「安装 / 更新 / 安装此版本」 → 状态检查（2.3） → 确认框（2.5，权限取自索引条目）
2. 下载 downloadUrl → downloads/<随机>.vxp.part，边下边算 sha256、计字节
3. 字节数 ≠ size 或 sha256 ≠ 条目 → 删除，失败「下载的文件与索引不符」
4. 改名 .vxp → candidate = await packages.validateArchive(path)
5. 核对 candidate.manifest：id、version 与条目相同，capabilities 与条目的集合相同 → 不同则失败「插件包与仓库描述不符」
   （用户同意的是条目上列出的权限；不让包里多出权限）
6. change = await candidate.install({ source: { kind: "repository", url: R.url } })
   - conflict → 替换确认框 → candidate.install({ source, replace: true })
   - unsupported → 「与播放器内置插件同 id，不能安装」
   - versionMismatch → 「需要 Vestra Player ≥ x.y.z」（索引写错 minPlayerVersion 时才会到这里）
   - busy → 「这个插件正在安装或回退，请稍后再试」
7. 跟随 change.onChange 直到 done：committed → osd「已安装 X 0.2.0」；failedDegraded → 「安装失败，已恢复原来的版本」；
   failed → 「安装失败：<message>」；cancelled → 「已取消」
8. finally 删除 downloads 里的文件
```

- **更新** = 对同一来源安装更高版本（宿主按同来源视为升级，沿用实例与数据，`previousVersion` = 旧版本）。
- **回退** = `packages.rollback(id)`，只在同一实例内回到 `previousVersion`（宿主契约）。按钮只在 `previousVersion` 非空时出现。
- **安装旧版本** = 同来源安装低版本的包。宿主 `install_instance` 不比较版本号，按同来源升级处理（旧的当前版本成为 `previousVersion`）；参考文档没有写明允许降级，列为契约澄清 G3。
- **取消**：下载阶段中止 `fetch`；安装阶段调用 `change.cancel()`（宿主可能答复 `tooLate`，按结果显示）。
- **替换与休眠**：替换时商城不需要知道 GUID 和休眠实例：宿主在新来源恰好有同 id 的休眠实例时自动接上它的数据（S4 §1.3「换回」）。确认框文案写明「原插件的数据保留，以后从原来源重新安装时接上」。

### 3.9 安装：链接、文件、拖入（侧载）

| 来源 | 流程 | `PackageSource` |
| --- | --- | --- |
| 链接 | `UrlInputRow` 输入 → 规范化（只 `https:`）→ 下载（≤ 64 MB，没有期望的 sha256）→ 同 3.8 第 4 步起，但第 5 步只核对「能解析」，权限取自 `candidate.manifest`（下载**之后**才知道权限，确认框在校验之后、安装之前） | `{ kind: "link", url }` |
| 文件 | 「从文件安装…」`dialogs.openFile({ title: "选择插件包（.vxp）" })` | `{ kind: "file" }` |
| 拖入 | `drops.provide({ extensions: ["vxp"], drop })`：拖到**视频区**的 `.vxp`；一次拖多个就逐个处理（每个一个确认框） | `{ kind: "file" }` |

- 文件与拖入不复制文件：直接 `validateArchive(原路径)`，宿主自己解压到临时目录。
- 文件对话框不能限制扩展名（`openFile` 只有 `title`）；选了别的文件，`validateArchive` 返回 `invalid`，提示「这不是有效的插件包」。不提请求（见 G4 说明）。
- 拖入时商城窗口没开：先打开窗口并选中这个包的详情（以 manifest 显示），再弹确认框。
- 链接与文件在宿主那里是同一来源（「手动安装」）：用新链接装同 id 的包是升级，不冲突（S4 协调者确认）。
- 侧载的插件商城**不检查更新、不处理撤回**（无从知道它对应哪个仓库条目）。
- 拖到商城窗口本身无效（宿主忽略工具窗口上的拖放，reference §6.7）。窗口里写一行灰字「也可以把 .vxp 文件拖到播放器视频区安装」。见缺口 G2（可选）。

### 3.10 撤回

1. 每次仓库刷新成功后，对每个已安装插件：若 `source.kind === "repository"` 且 `source.url` = R.url，且已安装版本 `satisfies` R 的某个 `revoked` 条目 → 撤回命中。
2. 命中且这个（id, 版本, 条目）**没处理过**：`packages.setEnabled(id, false)`，记入 `settings.json` 的 `handledRevocations`，再弹确认框：message `已停用被撤回的插件「X」0.2.0`，detail `原因：<reason>\n\n` + （有修复版本时）`可以在插件商城更新到 0.2.3。` ，confirm「打开插件商城」/ cancel「知道了」。同时有多个时合并成一个框。
3. 已处理过的命中不再自动停用：用户在插件管理里手动重新启用，商城尊重这个选择，只在详情页显示红色提示。
4. 对话框 `busy`（别的对话框开着）时等 60 秒重试；无界面 `unavailable` 时只记日志。停用失败（`busy` 正在安装）时下一次刷新再试，不记为已处理。
5. 撤回只作用于**同一来源**安装的插件：仓库只能撤回它自己发布的东西；第三方仓库因此不能停用官方插件或别的仓库的插件。内置插件不处理（`bundled`）。
6. 撤回条目同时影响安装：被撤回的版本不会被选为 `v*`，版本历史里标「已撤回」且不能安装。

## 4. 第三方仓库

1.6 第 4 条：第三方仓库和侧载在界面上明确警告。v1 发布的范围：

| 项 | v1 |
| --- | --- |
| 添加 | 设置页「添加仓库…」：输入行（`UrlInputRow`）→ 规范化 → 立即读取 → 解析成功才加入，并弹确认框：`添加非官方仓库「<name>」？` detail `地址：…\n其中的插件未经 Vestra Player 审核，可能读取你的文件或联网。商城会显示这个仓库的插件，但不会替你判断它们是否可信。`，confirm「添加」 |
| 移除 | 设置页列表每行「移除」；移除只是不再读取，已安装的插件不动（变成「只在本机」，不再检查更新与撤回），确认框说明这一点 |
| 数量 | 至多 16 个第三方仓库 |
| 显示 | 每行与详情都标「非官方：<仓库 name>」；仓库 name 取自索引（≤ 64 字符），后面带主机名防冒充（「Vestra 官方（foo.example）」这类名字一眼可辨） |
| 签名 | 不校验（没有公钥）；只靠 HTTPS 与每个包的 `sha256`（防止传输损坏与镜像替换，不防仓库作者自己） |
| 同 id | 与官方或其它仓库同 id：两行分别显示；安装另一来源的同 id 要走替换确认 |
| 不做 | 每仓库公钥、TOFU、仓库级「信任」开关、仓库排序优先级 |

TOFU 不做的理由：第三方仓库通常本来就不签名，TOFU 只能防「仓库地址被劫持」，而 HTTPS 已经做到；钥匙一换用户只能看到一个看不懂的警告。需要时以后给设置页加「公钥」一栏（固定公钥，不是 TOFU），客户端代码已按「一组受信公钥」写好。列入 §11 问题 4。

## 5. 错误处理与用户可见文字

原则：失败时什么都不改（宿主的安装是原子的）；错误写在详情页提示条或状态行，同时 `osd.show` 一次（失败忽略）；`message` 文本不用于判断，只按 `code` 判断（reference §13）。

### 5.1 仓库与网络

| 情形 | 文字（状态行 / 列表提示） |
| --- | --- |
| 刷新中 | 正在更新 <仓库名>… |
| 成功 | <仓库名> <HH:mm> 已更新 |
| 未变化（304） | <仓库名> <HH:mm> 已是最新 |
| 连不上 / DNS / TLS 错误 / 超时 | 无法连接 <仓库名>（<原因>），显示 <日期 时间> 的缓存 |
| 同上且无缓存 | 无法连接 <仓库名>，暂时看不到它的插件 |
| HTTP 4xx/5xx | <仓库名> 返回错误 <状态码> |
| 官方签名缺失 | 官方仓库缺少签名文件，已忽略这次更新 |
| 官方签名不符 | 官方仓库的签名校验失败，可能被篡改，已忽略这次更新 |
| 回滚检测 | 官方仓库返回了旧的索引，已忽略这次更新 |
| 不是 JSON / 顶层不合格 | <仓库名> 的索引格式不正确 |

## 6. 安全审查

### 6.1 恶意或被篡改的索引能做什么、不能做什么

| 攻击 | 能否得逞 | 防线 |
| --- | --- | --- |
| 篡改官方索引（Pages、CDN、GitHub 账号被入侵但签名私钥未泄露） | 否 | Ed25519 验签；失败用缓存 |
| 重放旧的官方签名索引，隐藏撤回或更新 | 部分缓解 | 版本集合不许倒退（3.4）；撤回列表倒退仍可能（§11 问题 5） |
| 第三方仓库冒充官方（`official: true`、名字写「官方」） | 否 | 「官方」只认内置地址 + 内置公钥；界面带主机名 |
| 索引里写别的包的 `downloadUrl` | 否 | `sha256` 与 `size` 必须与条目一致；包 manifest 的 id、版本、权限必须与条目一致 |
| 条目少报权限，包里多要 | 否 | 第 5 步核对权限集合，不一致不装 |
| 超大索引 / 包 / README、慢速连接 | 否 | 全部有大小与时间上限（3.2），流式计数中止 |
| zip 炸弹、路径穿越、符号链接 | 否（宿主） | `validateArchive` 在解压中强制上限并拒绝（reference §12） |
| 替换内置插件 | 否（宿主） | 对内置 id 的任何 `install` 都 `unsupported` |
| 静默替换别的来源装的同 id 插件 | 否 | 宿主 `conflict`，商城必须问用户 |
| 第三方仓库撤回、停用官方插件 | 否 | 撤回只作用于同一来源（3.10） |
| 显示字段注入（超长、控制字符、HTML） | 否 | 截断、纯文本显示；Markdown 由宿主解析且丢弃内嵌 HTML |
| README 里的 `javascript:`、`file:` 链接 | 否 | 只打开 `http(s)`，且要用户点击；`system.openUrl` 也只收 `http(s)` |
| README 远程图片跟踪 | 官方：可以（我们自己的仓库）；第三方：默认否 | 第三方默认不下载（2.2） |
| 不经用户确认安装或更新 | 否 | 每次安装都有确认框；自动检查只计数 |
| 用户确认后安装恶意插件 | **能** | 信任模型（1.6 第 4 条）：插件是完整的 Node 进程，权限只限宿主 API。防线只有官方仓库的源码审核、第三方与侧载的警告、撤回 |
| 已安装的恶意插件改商城的缓存 / 设置 | 能（任何插件都能读写用户文件） | 官方缓存使用前再验签；超出商城能防的范围 |

### 6.2 固定公钥，不用 TOFU

官方仓库用内置公钥（生态计划 1.6 第 3 条）。TOFU 的第一次连接没有保护，正好是新用户最需要保护的时候；固定公钥在播放器发版时就确定，商城作为内置插件随播放器发版，换钥成本相同。

### 6.3 换钥

- 商城内置的是**一组**受信公钥（现在一把）。`.sig` 允许多个以空白分隔的签名，任一把受信公钥验过即可（3.3 的代码）。插件仓库现在的 `verifyIndex` 只认一个签名；客户端从第一版起就接受多个，所以将来不用同时改两边。
- 计划内换钥：① 发版的播放器内置 `[旧, 新]`；② 等大多数用户升级后，CI 同时用两把签（`.sig` 两行），再过一段只用新钥；③ 之后的播放器去掉旧钥。
- 私钥泄露：发一个只信新钥的播放器版本，CI 立即换新钥。还没升级的播放器上，商城认为新索引签名不符，继续用最后一份可信缓存（看不到新的更新与撤回）；而且它仍然信任旧钥，**会接受攻击者用泄露的旧钥签的索引**。这是固定公钥方案的固有代价，只能靠尽快发版；撤回列表由同一把钥签，没有带外的撤销渠道。
- 这些步骤需要插件仓库 CI 支持多签名，属于 S3 的后续工作，列入 §11 问题 5。

### 6.4 其它

- 签名私钥只在插件仓库 CI 的签名 job（S3 已隔离）；测试一律现场生成密钥对，仓库里不放任何私钥。
- GitHub 账号被入侵且能触发签名 job 的情况，签名挡不住（签名 job 会签任何通过检查的索引）。这一层靠 GitHub 环境保护规则，不在商城范围。
- 商城不保存凭据，不需要 `secrets`。

## 7. 跨平台（工作流 §1.5）

| 项 | 做法 |
| --- | --- |
| 系统命令 | 不调用任何系统命令；打开链接 `system.openUrl`，网络 Node `fetch`，校验 `node:crypto`，文件 `node:fs`。`npm run portability` 应为 0 处 |
| 路径 | 一律 `node:path` 拼接；缓存文件名用十六进制摘要（不受大小写不敏感文件系统、Windows 保留名影响）；数据都在 `dataDirectory` 下，路径短 |
| 改名 | Windows 上目标存在时 `rename` 会失败：下载文件名随机；设置文件用 `storage.json`（SDK 已处理） |
| 删除 | Windows 上宿主可能还开着刚校验的文件：删除失败不报错，启动时清理 `downloads/` |
| 换行 | 签名对原始字节；不把索引写成文本再读回。测试夹具在测试里生成，或以 base64 写在 `.ts` 里，不受 git 的换行转换影响 |
| 确认框 | macOS `NSAlert`；Windows 任务对话框——带复选框的「卸载」在 Windows 上变成确认后再问一次是否删除数据（reference §7），文案两边都通顺；其它系统 `unsupported`：商城显示「此系统不支持确认框，无法安装」，不绕过确认 |
| 拖放 | 视频区拖放两系统一致；修饰键不使用 |
| 证书与代理 | Node `fetch` 用 Node 自带的根证书，不读系统证书库，也不读 `HTTPS_PROXY`。企业代理 / 自签名根证书的网络里两系统都会连不上 GitHub。这是 runner 级的配置（Node 24 的 `--use-system-ca`、`NODE_USE_ENV_PROXY`），影响所有联网插件，不在 v1 解决，列为 G5（以后） |
| 时间显示 | `Intl.DateTimeFormat("zh-CN")`，不依赖系统区域格式 |

## 9. API 缺口

### 9.1 结论：v1 没有阻塞性的缺口

逐项对照商城需要的能力：

| 需要 | 现有做法 | 依据 |
| --- | --- | --- |
| HTTP 请求、大小与时间限制 | Node `fetch` + 流式计数 + `AbortSignal` | reference 开头：插件进程可使用网络；S4 §5.3 的 Markdown 下载也是这样做的 |
| 下载到临时位置 | `dataDirectory/downloads/` + `node:fs` | reference §3.4 |
| Ed25519 验签 | `node:crypto` `verify(null, …)` | 已用线上索引与内置公钥实测通过（篡改后失败）；`check-boundaries` 只限制相对路径与 SDK 导入，`node:` 内置模块不受限 |
| 播放器版本 | `plugin.app.version` | reference §3.5 |
| 安装 `.vxp`、来源、替换 | `packages.validateArchive`、`candidate.install({ source, replace })` | reference §12 |
| 更新 / 回退 / 卸载 / 停用 | `install`（同来源）、`rollback`、`uninstall`、`setEnabled` | reference §12 |

## 11. 需要协调者决定的产品问题

1. **菜单位置**：顶层「插件商城…」（`order: 822`，紧跟「插件工坊…」），还是「设置 ▶ 插件商城…」（与「插件管理…」相邻）？我选顶层（打开工作窗口的入口，与工坊一致）。需交互负责人批准（工作流 §2.1）。
2. **商城是否提供卸载、回退**：我选提供（VS Code 一致，安装生命周期的一部分），停用 / 重新加载 / 数据目录只在插件管理。若希望严格不重叠，去掉商城的「卸载…」，提示改为「卸载：设置 ▶ 插件管理…」。
3. **撤回后用户手动重新启用**：我选尊重用户、只自动停用一次（3.10）。另一种是每次检查都再停用（更安全，但用户无法坚持使用）。
4. **第三方仓库的信任**：v1 只标「非官方」，不支持为第三方仓库配置公钥，也不做 TOFU；第三方 README 默认不加载远程图片。可接受吗？
5. **索引的单调序号与多签名（插件仓库 S3 的后续）**：建议插件仓库给 `index.json` 加 `"generated": "<ISO 时间>"`（或递增序号，商城拒绝比缓存旧的索引，彻底防重放），并让 `verify-index` / `sign-index` 支持 `.sig` 里多个签名（为换钥过渡）。客户端两样都已兼容（未知键忽略、多签名接受），所以不阻塞 S5；是否做、何时做由协调者决定，属于插件仓库的改动。
6. **自动检查频率**：激活后 30 秒、之后每 24 小时、默认开（可在设置页关）。若希望更保守（只在打开商城时检查），撤回检查也会随之变少。
