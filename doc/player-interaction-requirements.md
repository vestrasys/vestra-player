# 播放器重做：产品交互要求

> 流程纠偏：本文的产品行为要求属于实现与最终验收目标，不意味着所有公共能力先验收再允许插件编码。开发准入与按插件闭环规则见[工作流](plugin-probe-workflow.md)。

## 2026-10-18 用户范围与执行顺序修订（优先于下文旧门槛）

本节是用户最新指示，覆盖本文及历史设计中冲突的范围和前置验收要求；保留旧记录用于追溯，不将旧门槛继续作为延期理由。

- NES 本轮只要求真实模拟器能够运行并向播放器输出游戏音画；暂不要求键盘/焦点/菜单交互、快速按键、存读档及其完整交互验收。已有通用输入接口保留，供未来插件绑定键盘和播放进度等场景；不为本轮继续完善 NES 交互而阻塞插件开发。已发现的欠载等问题如实记录，不冒称无故障。
- 存档格式、序列化、ROM 校验、文件读写、复位和恢复策略属于 NES 插件。审查公共 API 与宿主，删除 NES 身份判断、按钮映射或存读档业务；通用输入释放、音视频队列与旧数据失效机制可以保留，但不得暴露 reset/loadState 等 NES 特化原因。清理后需同步 SDK、源码、usage 与必要检查。
- 新增两个独立产品插件：YouTube 视频播放及下载；Bilibili 视频播放（本轮未要求 Bilibili 下载）。原八个组件扩为十个。播放列表能够选择/加入 YouTube 视频并播放；播放列表与 YouTube 插件不得互相读取实现、导入代码或使用专用消息通道。通过公共来源描述、提供者能力及来源状态协作；站点解析、网络请求和下载策略留在站点插件，Rust 不增加站点业务。新增插件先补最小入口/菜单/失败行为设计并集中审查，不重开全部旧方案设计。
- 当前先完成通用试载、安装和回退：真实激活与必要 UI 完成、试载资源清理、成功版本持久提交、失败恢复旧版及明确的恢复失败、可查询的取消/结果；不能把 load/spawn 当安装成功。
- 随后完成公共 API 的 NES 特化清理和可执行性检查，记录可用能力及已知缺口，发布供插件实现使用的共同工作基线，立即分派独立插件 agent 编码。不得继续等待全部公共能力的完整产品验收后才允许插件开发；插件 usage 暴露的缺口按维护者请求/迁移流程迭代，最终产品验收仍检查实际完成情况。
- 保留 Rust 公共设施、TypeScript 插件业务、Slint 原生界面职责，插件独立性、第一方 safe Rust 和禁读旧实现约束不变。原生 UI 工具绑定问题保留为验收缺口，不成为所有实现工作停滞的理由。

## 1. 菜单按用户领域组织

参考参考播放器的功能领域组织思路，先建立整个播放器的菜单结构，再分配插件入口。插件划分不等于菜单划分；不能因为不同 agent 实现了不同模块，就让入口各自生长。

- 视频参数、视频预设及相应复位统一归入视频领域。
- 音频参数、均衡器、延迟、音频预设及相应复位统一归入音频领域。
- 字幕来源、轨道、样式、同步与翻译统一归入字幕领域。
- 截图、片段导出等入口必须在前置设计中明确归属；不得把同一个功能重复分散到多个顶级菜单。
- 播放、文件、播放列表、模拟器、插件管理与工坊等功能同样先明确归属，再交插件实现；不预先为尚无需求的分类建立空菜单。

上述领域可以有子菜单和多个命令，不要求一个插件只有一个入口。不要将“同一插件可注册多个命令”解释成可以随意跨领域散放命令。例如“复位音频”应留在音频领域，不能另挂在通用工具菜单。

同一命令可以同时有合适的按钮或快捷键，但必须共享状态与行为，不能形成两套互相矛盾的设置。全局菜单表记录唯一主菜单路径和其他必要入口；确有重复菜单需求时须说明用户场景，经统一审查后才能加入。

## 2. 界面与功能归属

播放行为及播放操作栏由默认插件提供；Rust 核心管理窗口、公共播放设施、组件挂载和生命周期。常驻不意味着必须把功能实现放进核心。

打开音频等工具界面不能替换播放操作栏；用户在工具显示时仍能执行设计承诺的播放、暂停和进度操作。工具的显示、隐藏、关闭与插件安装、运行、停用是不同事件，不能将关闭工具界面等同于撤销处理效果。

各插件先设计适合自身用途的界面形式，再汇总审查主画面、常驻控件、工具与侧栏能否合理共存。具体采用嵌入面板还是独立窗口、尺寸及焦点策略，尚待前置设计形成；旧实验的 `controls`、`sidebar` 字段或固定宽度不是新实现必须继承的接口。

统一交互规则由产品设计表达，核心不能通过识别某个插件的名字提供专属布局或业务后门。复用 Slint 的布局、控件和样式能力，不自建另一套通用 UI 框架。

## 3. 播放连续性是实际需求

- 连续拖动画面或音频参数时，不能把每次参数事件都实现为重启整个播放会话；参数的提交、等待和失败行为要明确。
- 展开或停留右键菜单不能导致声音继续而画面冻结。
- 显示/关闭工具界面不应擅自暂停、跳转或清空播放状态。
- 文件选择、安装首次界面等可能影响事件循环的操作，必须在设计中说明播放和状态保存行为，并在后续实现中据实验证。

这些属于前置设计和共享播放设施必须满足的约束。离线滤镜输出正确、单次请求成功或界面能编译，不足以证明这些要求成立。新播放后端和 GUI 的接入方式需围绕这些实际行为设计，不能仅复刻旧实验的进程调用方式。

## 4. 本轮交付与审查

协调者登记完整插件与宿主范围，包括基础播放等默认组件、画面、音频、字幕、截图/导出、NES 与插件工坊；每项都要有明确责任人，不能只让六个探针参与设计而遗漏基础功能。

执行顺序是：API maintainer 先按项目原则和基本使用场景实现最小可运行宿主、初版 API 与 usage examples，给交互设计提供能力基础；随后完成统一产品交互设计和各插件设计，审查并调整 API 后发布共同开发基线，最后统一分发插件实现任务。初版 API 尚未冻结，不能反过来限制已经确定的产品要求；维护者在设计和实现阶段都持续参与。

交互设计与审查阶段至少交付：

1. 全局菜单树及功能归属表。
2. 主窗口及各类界面共存的示意，含显示/关闭和焦点规则。
3. 每个插件的入口与界面设计、usage examples、失败/取消行为及独立运行前提。
4. 汇总审查记录、公共能力缺口，以及对应设计版本的验收矩阵。

这些产物经过交互负责人和 API maintainer 的相应审查，并与 SDK、宿主形成共同基线后，作者才能进入对应插件实现；不阻止最小宿主和初版 API 的先行实现。设计冲突先在全局层面解决，不能靠插件相互引用或核心按插件身份特判来弥补。

## 5. 旧实现隔离与技术原则

旧实现保留在 `temp/`，新实现使用新的 `src/`。后续重新启动全新 sub-agent；禁止读取 `temp/`、Git 历史旧实现、旧源码/测试/API 类型副本，也不得复用携带旧实现上下文的作者。允许参考的是整理后的产品目标、Rust/TS/Slint 职责原则及独立撰写的使用场景，不是照搬旧接口。

Rust 负责宿主、公共播放能力、原生界面及资源生命周期；TS 插件负责功能策略和交互行为，Slint 描述原生界面。第一方 Rust 禁止 `unsafe`，通过成熟组件的安全接口接入底层能力；不为控制代码行数而牺牲模块边界、错误处理或资源清理。
