# 插件社区实验工作流复盘与纠偏

2026-10-18。依据当前工作流、P1和execution记录审查；不读取旧实现。用户指出公共API阶段持续两天却没有开始插件实现，本次不以增加文档或探针数量解释为正常进度。

## 结论

主要问题是流程门槛及协调执行，不是仅仅缺少并发或参考资料。原先希望“插件作者写真实插件→遇到缺口→维护者调整公共API”，实际变为“汇总全部插件设计→维护者先实现并证明所有共享能力→全部通过才允许作者开工”。后者取消了社区实验最关键的真实消费者反馈。

当前产品组件原为8个，最新范围为10个；尚无正式产品实现分派、验收完成0。SDK有58个不同RPC名称，不能据方法数判断全部可用。已经完成的真实能力实证保留，不推倒重写，但也不算产品完成。

## 具体失效点

| 问题 | 当前记录中的依据 | 后果与修正 |
| --- | --- | --- |
| 开发准入和最终验收混在一起 | P1第7节将实时处理、原生UI、来源竞态、复杂快照等放在产品实现前；第8节M4仍要求八方案共享能力齐备 | 阶段D吸收了原本属于产品开发/验收的工作。改为可运行工作基线和逐插件依赖，M1–M4保留能力台账，不要求全绿才开工 |
| “必要共享能力”没有范围边界 | execution不断追加暂停重绘、旋转、非零origin、音频填尾、ACK、输入FIFO等独立探针 | 很多验证有价值，但没有区分局部阻塞与全局阻塞。必须关联具体插件/路径；只阻塞依赖它的部分，不能自动延期所有作者 |
| 维护者成为全部业务的预实现者 | NES真ROM、输入策略及Pi工具循环长期由前置实验验证，产品作者仍未获实现任务 | 从概念设计直接推导完善API，缺少真实插件可用性反馈。后续作者必须先交产品纵向切片，插件业务不由核心代做 |
| 审查结束点不断后移 | 每次局部通过仍不足发布共同基线，转向下一更细实证；原生输入连续两轮不能绑定窗口 | 没有有限的下一交付和路线复核。第二次同路径失败必须明确修复/换方案/局部待验或升级决定，不自动追加探针；工具问题不冻结其它工作 |
| 单点集成误变单人串行产出 | sole maintainer承担宿主/SDK/协议及大量消费者，插件实现阶段未进入 | 保留单点契约和集成/设备调度，按文件与接口委托共享模块，让可用槽位服务实际插件作者 |
| 汇报指标偏离用户目标 | 大量报告强调test、artifact和有限通过，产品实现数量仍为0 | 以后汇报必须给出分派数、可运行产品切片数、验收数及公共阻塞的影响范围；连续两次无新切片时由协调者复核前置条件 |

其中责任在协调者：旧工作流并非要求穷尽所有边界，但我把“不冒称验收通过”错误执行成“不允许开始产品开发”。也没有在维护者持续扩张工作时及时改变调度。不能归咎于插件作者或用量限制；限制只解释当前停顿，不能解释此前流程失效。

## 恢复后的有限执行顺序

1. 核对当前activation实际结果及未收尾进程/构建，接续已经产生的新代码，不从头建立另一套基础API。
2. 完成用户指定的通用试载→安装→失败保旧→回退闭环，以生产JS和普通Slint计数器为有限真实消费者。保留必要清理、摘要/版本、持久提交及结果查询，不扩成包商店、依赖求解或任意状态恢复平台。
3. 清除公共协议中的NES特化语义，保留通用输入/音视频能力。NES本轮仅真实运行音画，存档和键盘交互不再阻塞。
4. 发布与实际宿主/SDK一致的共同工作基线及能力/缺口清单。现有8份设计不重写，YouTube/Bilibili补最小领域入口设计；随后按槽位分派产品作者，优先基础播放与播放列表形成真实主界面闭环，再轮换其它作者；维护者持续处理实际请求。
5. 每个插件先实现并运行一条实际用户路径，再扩展该插件其它要求。路径失败归属插件或公共能力，按受影响范围修复/复验；最终独立验收仍检验用户已确认范围，不能用准入放宽冒充完成。

## 这次明确不再作为全局开工条件的事项

NES键盘/焦点及存档完整交互、所有导出时间戳变体、全部原生对话框与焦点组合、所有滤镜逐项感官/像素验收，不再先全做完才能开始任一插件。这些按最新范围分别暂缓或进入产品实现/验收台账；播放连续性等仍是产品要求，不能带着已知必要缺陷宣布最终完成。

本复盘已经对应修改工作流、P1顶部门槛说明、产品要求及execution；它不等于试载安装已完成，也不等于共同基线已发布或产品作者已经开工。Goal恢复后按此调度，无需用户逐次批准例行任务。
