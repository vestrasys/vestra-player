# 社区插件实验工作流纠偏（2026-10-18）

本记录针对当前重建过程：前置公共能力建设持续过久，插件使用者未能足够早地参与验证。目标是用实际插件反推边界，不是先做完整插件平台再验证。本文的执行纠偏优先于旧流程中要求全部公共能力验收后统一开工的串行门槛；不取消最终验收与项目原则。

## 问题与责任

1. **验证目标倒置。** 原流程把初版 API、全部产品设计、全部能力补齐和一致基线串联起来，随后才统一发放实现任务。所谓初版实际承担了接近完整平台的职责，没有可执行的停止条件。
2. **开发准入与交付验收混用。** 包安装回退、持久化、异常恢复和真实设备等最终必要能力，被同时当成所有插件开始实现的前置条件。某一能力未完成会阻塞完全不依赖它的插件。
3. **维护者形成单点排队。** API 设计、宿主实现、集成构建和各种验证集中在一个维护者；插件作者过晚拿到实际编写机会。单写者适用于共享文件，不意味着所有设计、编码和检查必须串行。
4. **没有让真实调用及时约束 API。** 以推测需求扩展公共能力，缺少最早的真实插件切片来证明必须性、命名和职责边界；插件特有需求容易进入核心。
5. **缺少有效的等待处置。** 当前另有可直接观察的 FileProvider 故障：文档、依赖被标记 dataless，读取或复制长期没有输出。下载请求成功返回不等于文件可读。这是环境问题，但持续等待、把缓存历史 hash 文档读取也当运行前置，是调度问题。

上述流程和调度由主协调者负责，不能归咎于用户没有继续启动 goal，也不能用工作量大来解释所有延期。

## 可执行的停止条件与开发准入

最小宿主只需证明：真实 libmpv 播放；一个真实 TS 插件启动与停止；一次公共命令调用；一个普通 Slint 插件窗口可以显示。先发布带版本和已知限制的开发基线，立即进入插件切片。以后只有具体切片证明缺少的能力才新增；安全 Rust、插件隔离、无身份特判和真实后端不作妥协。

开发准入、单插件验收、组合交付验收分开登记。安装管理的局部缺陷不阻塞不依赖安装的音频或画面功能编写；最终交付仍必须验证安装、回退、清理和相关恢复行为。现有候选和公共能力保留，不为纠偏重写一轮宿主。

## 调整后的推进方式

1. 统一交互规范只冻结领域归属、菜单位置、窗口类型和不得打断播放等约束；不等待每个细节与公共 API 一次定稿。
2. 插件作者立即写一条完整使用路径：菜单入口 → 实际插件代码 → 公共调用 → 可见结果。首切片可提交集成，不等待整套功能完工。
3. 维护者优先处理正在阻塞真实切片的请求。请求须附具体调用例子、现有接口为何不足、影响范围；可暂用插件内部实现的业务不进入公共 API。
4. 兼容新增直接发布版本及示例；破坏性变更集中迁移、保留明确兼容期或统一迁移点。不因单个作者误用旧版本立即改 API，不让其他作者追逐未发布接口。
5. 独立作者并行拥有各自目录；维护者串行集成共享修改和需要独占设备的测试。无需先让所有插件共同通过，才能集成一个插件。
6. 每轮记录可运行切片、实际失败、归属和下一个可验证动作。只有文档、探针数量或测试数量增长，而没有新切片，不视为有效迭代完成。

## 当前立即执行的决定

- 已发布的 development-2026-10-18.1 是开发基线，不重新开启全局前置建设。
- 基础播放和播放列表已有候选；画面与音频已有首切片源码。它们都不等于最终验收通过。
- 优先编译、启动和验证这些真实候选；其他产品按空闲实现席位接续，不等待全局完美。
- 对本轮可信、已实际运行的本地 SDK/runtime 缓存，可记录来源和现算 hash 后用于开发集成；无法读取旧 hash 文档要如实标记，不得虚称已比对，也不再阻塞开发。
- 长时间无输出先辨别实际进程、阻塞文件和是否已启动宿主。确认是云文件阻塞后改变缓存/传输方式，不重复发下载请求并将其当成功，也不盲目启动重复测试。

## 何时请用户裁决

只有触及项目原则、明显改变产品交互或功能范围、需要放宽隔离/安全约束、引入重大不可逆成本，或有最小复现证明技术路线不能满足需求时，提交证据与可选方案。普通 bug、兼容 API 扩展、插件内部设计和环境缓存不要求用户再次批准。技术路线争议不得通过无限增加前置任务掩盖。
