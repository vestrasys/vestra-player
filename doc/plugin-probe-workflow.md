# 插件社区实验：多 agent 设计、实现与验收工作流

## 工作流纠偏：开发准入与最终验收分离（2026-10-18）

本节替代下文及 P1 中“所有共享场景先验证完，才能分派产品编码”的串行门槛。根因与执行证据见[流程复盘](rebuild/workflow-retrospective.md)。用户已经要求的试载/安装/回退和 NES 特化清理仍须先完成；本节不绕过这项顺序，也不宣称已发布工作基线。

### 开发准入只检查实际依赖

共同工作基线是一个可用、可追踪的开发版本，不是全产品验收证书。准入只需：宿主/SDK构建及必要类型检查通过；真实播放、插件加载、菜单和Slint最小调用可运行；本次交付接口有usage、能力与已知缺口清单；本轮用户指定的安装回退及特化清理完成。不得追加NES键盘、全部导出变体、全部原生交互等为所有插件的开工条件。

已存在的公共能力不为发版再完整重跑旧绿色套件；有修改时跑受影响检查。缺口按插件/用户路径标注：已实现待验、已验证可用、缺失、真实阻塞。能力缺失不得返回假成功，但不妨碍作者编写并运行该插件不依赖它的部分。

### 按插件闭环实现，不再等维护者包办所有实验

1. 全局菜单与领域归属先统一；每插件的最小设计通过后，即可在共同工作基线上领取实现任务。新插件只补其受影响设计，不重开所有旧方案。
2. 每位作者第一项交付必须是自身目录的真实产品纵向切片：入口→插件逻辑→公共调用→可观察结果；随后扩展功能。探针脚本不计产品完成数，不能无限以新脚本代替插件。
3. API请求必须关联正在实现的插件、具体代码位置/usage及最小失败。维护者先确认现有接口或插件/第三方库能否完成；确需公共能力才做最小扩展，不承包插件的存档、解析、下载、预设等业务。
4. 一条请求以请求插件的实际调用和必要公共回归闭环；其它插件继续。完整边界组合与原生产品验收在阶段E进行，不逐项前置为全局基线门槛。
5. 出现同一路径第二次失败时，协调者必须决定：修复明确缺陷、改变实现方案、标记仅影响该路径的待验项，或存在原则取舍时升级用户。不得自动追加下一套更细探针；这不是重试上限，也不允许带已知必要缺陷宣布最终完成。

### 并发与检查责任

单点维护契约与发布，不等于全部代码单人串行写。共享模块可按明确接口/文件独占委托；仅构建、集成和原生设备时段集中调度。四并发槽通常分配为协调者、API维护者、两位插件作者；独立验收按切片或完成批次轮换，暂不占槽的任务有明确下一步。维护者忙于一个模块不能使全部作者长期空闲。

每次状态汇报必须给出产品插件“已分派/已有可运行切片/验收完成”的数量、当前公共阻塞对应哪些插件、接下来解除它的具体交付。连续两次调度检查仍没有新产品切片时，协调者必须审查并移除无关前置条件，不能仅报告测试/文档数量增长。

作者自测确认功能后，独立验收检查当前切片；共享组件已经有可靠证据时可引用其修订，不机械重复全部检查。原生工具不可用时保留真实未验项，继续其它实现与可执行验证，不用后台结果冒充交互，也不让工具问题冻结整个社区。

- 保留 Rust 公共设施、TypeScript 插件业务、Slint 原生界面职责，插件独立性、第一方 safe Rust 和禁读旧实现约束不变。原生 UI 工具绑定问题保留为验收缺口，不成为所有实现工作停滞的理由。

启动时不继承含旧实现的历史上下文；使用支持的隔离上下文选项（当前为 `fork_turns: "none"`），并在初始任务中明确可读设计文件、新源码目录、禁读范围及文件所有权。API 维护者和验收者同样遵守，不能通过委派另一个 agent 绕过。新一轮开始后产生的新源码、测试和公共契约按角色正常读取。

历史[验收矩阵](probe-acceptance.md)与报告保留其原来的有限范围，不是本轮新实现的通过证据。后续按第 0 节先建立最小宿主、初版 API 和工程规范，再完成交互设计与审查，发布共同开发基线和验收矩阵；不直接沿用旧实现的 API 基线。

## 0. 执行顺序：最小 API → 交互设计 → 审查与基线 → 插件实现

### 阶段 A：最小可运行宿主与初版 API

主协调者先登记本轮所有交付组件，包括基础插件、探针及共享宿主，明确用户场景、非目标与不可改变的原则。不能只登记新探针而漏掉默认自带插件，也不能由插件作者各自决定整个产品的菜单与窗口结构。

API maintainer 根据已有产品目标、架构原则和最基本使用场景，先实现最小可运行宿主及初版 API，给后续交互设计提供真实能力基础。当前播放器需要先打通播放后端、Rust/TS 通信、插件加载与生命周期、Slint 界面接入，以及这些最小场景实际需要的公共调用；不等全部插件交互设计完成才开始共享基础实现，也不凭空预建完整平台。

此阶段交付工程规范、可运行的最小宿主、初版 SDK/契约、usage examples、启动方式，以及已实现能力和已知缺口。界面接入例子只说明能力，不提前决定整个产品的菜单树或固定所有布局。

初版 API 是供设计使用的工作版本，尚未作为并行插件开发的稳定基线发布。记录修订和实际能力，后续可根据交互设计与 usage 调整，不能把尚未实现的声明冒充可用能力；初版可运行也不等于插件功能已经验收。初版 API 与最小宿主就绪后，才进入统一产品交互设计阶段。

### 阶段 B：统一产品交互规范

由交互设计负责人基于初版 API、可运行宿主及产品要求形成产品级规范，至少包括：

- 全局菜单分类、功能归属、入口命名，以及重复入口和快捷操作的规则。
- 主界面、常驻界面、工具界面、侧栏和系统对话框各自的用途；哪些形式实际需要支持，由产品场景决定，不预建全套窗口框架。
- 显示、隐藏、关闭、焦点、窗口尺寸变化，以及操作界面时播放应保持的行为。
- 共享状态的权威来源、等待/失败/取消反馈，以及需要避免的跨插件冲突。

产物建议为 `doc/design/product-interaction.md` 和全局“功能 → 主菜单入口 → 所属插件 → 界面形式”表。它们属于本轮具体设计；本文只规定必须先完成这些工作，不固定某种产品的菜单名称或布局。

设计不能被初版 API 限死。遇到产品要求与现有能力不一致，记录能力缺口并交维护者评估，不能为了不改初版 API 而牺牲已确定的用户行为。API maintainer 在此阶段持续参与设计、修正共享能力和说明限制，不进入等待状态。

### 阶段 C：各插件提交设计，不先写插件实现

每位插件作者在统一规范下提交自己的交互方案，建议放在 `doc/design/plugins/<id>.md`。不能在收到插件名称后直接开始编码，也不能自行添加新的顶级菜单或全局挂载规则。

此阶段先发设计任务；通过设计的作者在共同工作基线准入后按可用并发槽立即进入该插件实现，不等待其它插件的完整功能验收。最小宿主/API 的先行实现不受“插件先设计再编码”这一门槛限制。

每份方案至少包含：

```text
插件职责、场景与非目标
每项功能的主菜单路径、命令及其他必要入口
每个入口直接执行什么，或打开什么界面
界面草图/控件排布、默认是否显示、显示与关闭方式
常驻控件、工具窗口/面板与主画面的关系
播放中、暂停中、无媒体时的行为；连续拖动等交互是否影响播放
状态来源、异步等待、失败、取消和恢复行为
独立运行的前提；与其他插件共存时的约束
公共 API 的 usage examples 与能力缺口
可以观察到结果的验收场景
```

插件作者可以提出修改全局规范的建议，但不能把个人方案直接当成批准结果。不同插件共享的是公开宿主能力，不是互相引用对方的实现。

### 阶段 D：合并审查与共同开发基线

交互设计负责人汇总全部插件方案，检查功能归属、菜单重复、命名、窗口/面板冲突和用户操作是否一致；API maintainer 检查实现所需能力、Rust/TS 边界与资源生命周期。逐插件审查之外，必须再看一次完整菜单树和所有界面同时存在时的布局。

审查结论记录为通过、需修改或待裁决，并明确责任人。API maintainer 按顶部开发准入条件发布共同工作基线，列出实际可用能力、契约/SDK/宿主修订、usage及缺口。通过设计的插件立即按槽位分派实现；公共能力在真实插件使用中按请求补齐，不等待所有设计场景或验收矩阵通过。普通设计问题由团队解决；只有第 3.2 节的原则或产品取舍才交用户裁决，不增加例行确认环节。

这不是审查结束后才从零搭宿主，而是在已运行的最小基础上收敛契约、补齐必要能力。插件实现期间仍可按第 3 节请求扩展，基线不意味着必须提前完成所有未来 API。如果底层尚不能满足连续播放、实时调参等已承诺行为，不能用不满足该行为的替代后端宣布插件场景通过。

### 阶段 E：并行插件实现、持续维护与独立验收

后续按本文的 API 维护、独立开发和独立验收流程执行。API maintainer 持续处理能力请求、宿主缺陷、版本发布、迁移协调与公共回归，不是发完 SDK 后坐等插件完成。新增入口、改变菜单归属、替换常驻界面或改变播放行为，先提交设计变更，再由交互负责人和必要的 API 维护者审查影响；同步更新全局设计、相关插件方案和验收矩阵。小范围变更只重审受影响部分，不要求所有插件重新设计。

设计基线不是限制插件功能的隐藏业务接口。核心按公共契约挂载组件和路由命令，不按插件身份编写特殊业务；产品入口的分类属于产品设计约束，不能被硬编码为特定插件的核心逻辑。

## 1. 目标与范围

通过六个独立插件的实现、API 变更和独立验收，迭代出一套能够支持这些真实 use case 的实验架构。通过本轮不意味着找到全局最优架构或已经达到生产质量。

本流程模拟一个插件社区：插件作者是依赖公共契约的独立消费者，不是随时配合核心改动的内部模块作者。实验既检验功能能否实现，也检验 API 是否容易理解、变更是否可控、旧消费者能否继续工作，以及维护者能否在不加入插件专属后门的条件下处理不同需求。

六个探针已获确认：

| 探针           | 本轮必须覆盖的边界                                        |
| -------------- | --------------------------------------------------------- |
| 画面调节       | 视频领域内多个入口共享状态、预设与复位、与其他画面处理共存 |
| 音频工作台     | 音频处理、实时参数、延迟、处理链所有权与撤销              |
| 字幕工作台     | 外部字幕、样式/同步、异步翻译与切换媒体后的结果隔离       |
| 截图与片段导出 | 原始/处理后画面取样、字幕选项、任务进度、取消与来源快照   |
| NES 模拟器     | 自定义文件类型、音视频生产、输入、独立会话/时钟与存档     |
| AI 插件工坊    | 插件自身接入 Pi，生成、校验、试载、修复、安装与回退       |

DLSS 5 搁置，不属于本轮完成条件。每个探针在实现前写出有限、可验证的使用场景，不以功能名称笼统承诺完整产品。

新实现位于仓库根目录 `src/`，旧实现保留在 `temp/`，不作为新作者的输入。`doc/experimental1` 保留历史说明与证据。所有新源码及文档仍注明实验性质、API 可能与成品相差很大；使用 `src/` 不代表生产版本。第一方 Rust 禁止 `unsafe`，通过成熟组件的安全接口接入底层能力；核心保持精简、职责清晰，资源所有权与清理明确。不因实验或追求代码短小而放宽这些原则。

## 2. 角色与文件所有权

### 主协调 agent

负责目标、调度、集成、工作记录与最终证据汇总；维护每个探针的状态、API 请求状态、已知限制和检查结果。协调 agent 不代替独立验收者宣布验收通过。

负责执行第 0 节的阶段门槛、向全新 agent 分发不含旧实现的上下文，并避免同时由多个 agent 操作同一个原生窗口。

### 交互设计负责人

维护产品级菜单与界面规范，汇总和审查各插件设计，对完整产品的交互一致性负责；不把这一职责分散给各插件作者自行决定。可由主协调者承担，也可单独安排新 agent；不是必须新增一个常驻进程。涉及公共能力时与 API maintainer 协同，不擅自修改共享接口。

### API maintainer agent

维护共享 SDK、manifest、协议、宿主分发、公共生命周期及必要的 Rust 能力实现，并对这些共享目录拥有写权限。维护者负责端到端契约，不是只增加 TS 方法签名。

重做轮次先负责第 0 节阶段 A 的最小宿主与初版 API；随后参与产品和插件设计，在集中审查后发布共同开发基线，插件并行实现期间继续维护与演进。

维护者制定并执行代码规范：明确类型、错误与取消语义；清晰的所有权和清理；没有插件名分支或单一探针专用业务泄漏；没有不必要的抽象层；接口和例子可读。宿主可以按注册的能力/来源路由，但不能硬编码六个探针的身份。

代码规范必须形成文件与可执行检查。格式、类型检查、依赖边界、构建等由工具检查；可读性和抽象是否合理由人工 agent 审查，不能用“优雅”二字代替依据。

### 六个插件开发 agent

每个探针由不同 agent 负责，独占自身设计、插件及对应测试目录。开发者先读产品交互规范并提交方案，通过审查后再依据本轮公共契约实现；不修改 SDK、宿主或兄弟插件。缺能力时向 maintainer 提交请求，并继续不依赖该请求的工作。

允许依赖成熟第三方库和本插件自己的原生模块，但必须遵守既定进程与 Safe Rust 边界。不得把本应使用公共 API 的逻辑搬进共享文件来绕过审核。

### 验收 agent

不负责六个插件的实现，也不由 API maintainer 兼任。可以从开发阶段提出问题，最终独立读取源码、执行命令并检查产物，不接受“其他 agent 说通过了”作为证据。

验收失败形成可复现的问题记录，交回对应作者；修复后重新验收受影响范围。API maintainer 不能修改验收预期来让自己的 API 通过。

验收者同时对照全局菜单树、各插件交互方案与验收矩阵，不只检查单个命令有没有返回成功。菜单归属混乱、工具替换常驻播放栏、拖动参数打断播放等违反设计的行为，均属于必要缺陷。

## 3. API 契约与变更请求

先建立最低可用规范，包括 manifest 校验、能力发现、命令与菜单贡献、会话状态、事件、错误、取消、资源释放和实验版本标识。按 use case 增长，不预建完整通用平台。

每个变更请求至少包含：

```text
请求 ID / 提出探针
用户操作与预期结果
当前 API 为什么无法完成
建议的 usage example
状态、资源和生命周期归谁
失败、取消与能力缺失时的行为
是否破坏现有契约、涉及哪些消费者
最小验收场景
所用契约版本 / 最小复现与实际诊断
```

maintainer 可批准、修改建议或拒绝。拒绝须给出原因与可实现的替代用法，不能让开发者私自增加隐藏入口。只有一个消费者的能力可以合理进入核心；关键是职责是否属于基础能力，不强求先有两个消费者，也不因为只有一个需求就无限泛化。

批准后按第 3.1 节执行兼容扩展或受控迁移；提出请求不等于批准，更不等于所有消费者立即迁移。

既有实验中的 `setGaussian`、`gaussianEnabled` 等是历史临时字段，不自动成为新接口。也不能把每个新效果都照样扩成专名方法；使用探针判断该抽象应是参数能力、处理提供者还是后端扩展。

### 3.1 固定基线与受控迁移

1. **固定开发轮次的基线。** maintainer 发布契约版本及对应代码修订，SDK、协议、宿主和示例必须一致；每个插件记录所用版本与能力要求。已发布的基线不可悄悄改写。尚未实现版本协商时，在同一集成分支保留旧用法，或安排明确的统一切换，不假装宿主已经支持多版本运行。
2. **先分类再设计。** maintainer 将请求区分为实现违反契约、文档/使用问题、能力缺口或破坏性设计调整。已有契约的回归优先修复，不能让作者通过追加 API 请求绕开故障；重复请求关联原议题。
3. **兼容扩展及时交付。** 新可选参数或独立能力经过契约检查、现有消费者回归后发布增量版本；不使用新能力的插件不必修改。增加必填字段、改变默认行为、错误语义、资源归属或生命周期同样可能破坏兼容，不能只看 TS 签名。
4. **破坏性变更集中切换。** 将候选方案、受影响消费者和迁移例子记录后，再确定下一轮基线。切换前当前轮次的旧契约继续可用；相关合入暂停范围仅限受影响契约，其他工作继续。maintainer 负责实现、迁移协调和回归闭环，不能只改 API 再让各作者自行发现失败。
5. **保留真实消费者证据。** 公共修改必须执行受影响插件的契约与集成测试，并验证公共 usage examples。迁移完成须证明旧基线回归得到解释、新基线消费者全部通过，SDK/文档/宿主一致；不能用只改测试预期来掩盖行为变化。
6. **阻止连续补丁循环。** 多个请求指向同一能力，或一项变更接连引发新的破坏性请求时，协调者暂停该部分新变更，合并成设计议题，比较共同需求、抽象边界与替代方案，再由 maintainer 决定。先记录已经通过的版本及失败复现，避免相互猜测。

兼容层只为明确的迁移服务，记录支持范围、责任人、退出条件及删除所在轮次；不为验收无限累加旧接口。必要重构仍然允许，但必须显式发布和验收。请求数量多本身不构成向用户升级的理由。

### 3.2 何时请求用户裁决

以下事项在尝试复现、澄清契约和比较可行方案后，交给用户决定：

- 请求改变已确定原则，例如插件直接依赖、核心包含特定插件业务，或放宽第一方 Safe Rust 边界。
- 存在无法同时满足的产品需求，需要取舍自由度、学习成本、性能或交互体验，工程测试无法确定优先级。
- 探针需要明显扩张核心或原定范围，引入新的平台支持、许可证义务、收费服务或其他外部条件。
- 实验有证据表明 Slint、TS/Rust 职责边界等既定技术路线无法满足关键场景。
- maintainer 与独立验收者在补充复现和证据后，仍对必要契约或验收行为存在实质分歧。

普通 bug、文档澄清、兼容扩展和已授权范围内的实现选择由团队解决。升级时提交具体问题、复现证据、可选方案及代价、推荐方案、受影响工作与需要用户决定的一句话问题；仅暂停依赖该决定的工作，其他独立工作继续。等待时间不代表用户同意，不因等待而缩减验收范围。

## 4. 插件独立性

本轮必须保证：

- 插件之间不互相 import，不读取其他插件目录、内部对象或私有状态。
- 插件之间不使用直接消息、共享文件、专用网络连接或定制中转消息互相通信。
- 公共 SDK、公开宿主状态/事件与成熟第三方依赖可以共享；测试公共帮助代码不能包含业务实现。
- 每个插件可在其他五个不存在时加载、运行、停用并释放资源。需要播放器设施时由统一测试宿主提供，不借用另一个功能插件作为隐藏前提。
- 多插件可以共同作用于同一播放会话；协调通过 core 的公共契约完成。共享播放状态不等于直接插件通信。
- 停用某个处理插件只撤销自己的资源，不清空其他插件的效果、事件订阅或设置。

工坊生成的是新的插件包，通过公共管理能力校验/安装；它不 import 生成包的实现，也不对六个手写探针进行直接调用。验收生成包时使用一个独立、有限的示例需求，避免递归生成工坊本身。

## 5. Pi 与 mock 模型

插件工坊是可选 TS 插件，Pi 接入与编排留在插件侧；Rust core 不依赖 Pi、模型供应商或 BYOK 配置。本轮不调用付费 LLM，不要求使用者提供 API key。

优先在 Pi 的模型调用边界接入可替换的 mock provider，保留真实的 agent 编排与生成—诊断—修复流程；具体接缝以选定 Pi 版本的实际 SDK 为准，不臆造 Pi 接口。

mock 不只是返回“成功”：应能输出文件生成动作、接收编译/验证诊断，再输出修复。使用确定性场景覆盖正常生成、初次错误后修复、取消和失败回退。测试必须证明生成的 TS/Slint/manifest 真正经过校验、执行并产生预期行为，而不是只比对文件存在。

当前 Codex 可以在开发时编写或更新候选插件，并把可重放的交互用作 mock 场景素材；没有现成授权桥时，不把当前聊天会话当成可调用的 LLM HTTP endpoint。若以后增加 Codex 开发桥，应显式适配同一模型调用边界，最终 BYOK 实现也走这个边界。模拟验证不等于真实供应商协议已测试。

工作目录限定不是权限沙箱。生成结果先在候选目录验证，不直接覆盖当前可用插件；执行、安装与回退遵守同一公共生命周期，不获取工坊专用的宿主后门。

## 6. 自动验收与真实性

验收分层：

1. **契约和静态边界**：TS 类型、Rust 构建、Slint 编译、manifest/协议校验，跨插件依赖和越界访问审查。
2. **每个插件独立运行**：使用真实插件进程和宿主边界，验证用户 use case、错误与资源回收。
3. **真实处理证据**：画面像素变化、音频样本变化、字幕时间与译文绑定、有效截图/片段文件、NES 实际 ROM 执行与输入响应、工坊生成包实际加载。
4. **组合与生命周期**：单独安装、改变安装顺序、停用一个继续运行其他、播放切换、界面重建、任务取消和进程异常。
5. **独立质量审查**：职责、命名、模块独立性、公共 API 一致性及是否出现探针专用宿主分支。

6. **完整产品交互**：在同一实际程序中加载本轮全部插件，逐项操作设计中承诺的菜单、窗口、按钮和连续交互；检查布局共存、焦点和播放连续性。物理操作、系统文件面板、回调场景、headless 和 mock 的证据分别标注，不能互相冒充。底层参数处理正确不证明拖动时没有卡顿；菜单可展开不证明展开期间画面仍更新。

NES 用自制或明确授权的 ROM；成熟核心负责模拟，不为通过测试手写一个假游戏画面。原生渲染、音频或设备无法在当前环境验证时，明确标为未验收，不以 mock 结果冒充真实实现。

刻意设计的关键场景：

- 画面效果与其他处理并存，停用一个不影响另一个。
- 字幕翻译未完成时切换媒体，旧结果不能污染新会话。
- 导出开始后切换播放来源，任务仍绑定原来源与参数快照。
- NES 不具备普通视频时长时，宿主不强制其伪造 duration/seek。
- 工坊产生错误代码后，根据真实诊断修复；失败不能破坏已安装版本。
- 连续拖动画面/音频参数时，播放行为符合设计，不因每次参数事件重启整个播放会话。
- 展开和停留右键菜单时，画面、声音及播放状态保持一致；工具显示/关闭不替换常驻控件。

每项保留命令、退出码、测试输出和必要产物。验收测试由既定需求驱动，不能镜像实现或只断言作者给出的成功标记。无需穷举所有排列，但必须覆盖被本次变更影响的契约和风险。

## 7. 并发、记录与收敛

角色数量不等于同时运行数量。当前并发上限为 4（含主协调）：先安排 maintainer 实现最小宿主与初版 API；就绪后安排交互与插件设计，发布共同基线后再轮换并行实现者，验收者在释放的名额中运行。不能为了占满并发名额让插件作者跳过前置设计或提前依赖未发布的接口。每个插件保持自己的作者与目录责任，关键变更和请求记录到文件，不能只留在易丢失的 agent 消息里。

工作记录至少包含：角色与目录所有权、探针状态、API 变更请求及分类/决策、当前基线与候选版本、每个消费者的目标版本、迁移责任与退出条件、验收矩阵、失败记录和已知限制。共享 API 由 maintainer 单点修改；插件作者可并行工作。

一般恢复已有轮次时，先核对其设计/API 基线、消费者依赖和未收尾请求，再继续受影响的回归。当前重做轮次是例外：按照用户要求隔离旧实现，先建立新设计与新契约，不要求新 agent 读取旧 API 请求或恢复旧代码。历史成果只保留为历史记录，未执行的检查不能追认为通过。

最后一次 API 修改后，对六个探针进行集成回归和独立验收。如果发生修改，重新检查受影响范围；没有新增问题时停止，避免在“更优雅”的名义下无限重构。

## 8. Goal 的完成条件

以下是后续 goal 的通用目标模板，具体组件范围与交互规范由本轮设计文档补充；不是现在启动 goal 的指令：

> 先登记全部交付组件，由 API maintainer 根据项目原则和基本使用场景在 src/ 建立最小可运行宿主、初版 API 与 usage examples；在此基础上制定统一产品交互规范，各插件提交入口、界面、状态与公共能力的使用设计。跨插件汇总审查后调整初版 API、补齐必要共享能力，发布一致的设计/API/SDK/宿主及验收共同基线，再统一分发插件实现任务，模拟真实社区。maintainer 在设计与实现期间持续维护能力、处理请求，按固定基线、请求分类、兼容扩展和受控破坏性迁移管理公共 API，保留消费者版本、迁移和真实回归证据；开发中交互变更同步经过设计审查。共享基础设施必须满足所承诺的实际用户行为，独立验收者对照设计检查全部组件的独立运行、组合运行、真实交互和资源清理，提交可复现报告与 API 演进结论。原则冲突、产品取舍、范围扩张或有证据的路线障碍按第 3.2 节请求用户裁决；不得以替代后端、回调或 mock 的局部成功冒充实际用户场景通过。

本播放器轮次的范围包括基础播放等已登记组件与六个探针；工坊仍使用真实 Pi 循环和 mock 模型完成生成、真实校验、诊断修复、加载与回退。具体入口及排布由前置设计形成，不写死在通用 goal 中。

只有以下条件全部成立才可完成：

- 本轮登记的全部插件均实现事先定义的场景，且独立运行、组合与清理检查通过；本播放器轮次包括六探针与基础组件。
- 全部交付组件有经过审查的交互方案；完整菜单树、界面组合和验收矩阵一致，基础插件没有被漏验。
- 设计承诺的实际用户路径和连续交互有对应证据；没有被局部自动测试掩盖的播放中断、画面冻结或入口冲突。
- 本轮含工坊时，在无付费模型调用的条件下完成生成、真实校验、诊断修复、加载和回退闭环。
- API、SDK、协议与宿主实现一致，没有未解决的必要变更或验收阻塞项。
- 独立验收 agent 已给出通过报告，主协调者已确认其证据与当前代码一致。
- 文档记录最终实验契约、API 演进理由、被拒绝的方案、平台边界及未覆盖的生产问题。
- 社区变更记录可追踪：消费者目标基线明确，破坏性变更有影响清单、迁移和回归结果，临时兼容层有退出条件；没有未解决的必要迁移或待用户裁决事项。

若工具、平台或运行预算不足，应如实保留未完成状态及阻碍，不缩减原定验收标准来宣称完成。不因本轮通过就宣称 API 已是最终版本或已完成真实 BYOK/供应商互通验证。

历史六探针轮次的有限验收见[独立审查](probe-review.md)和[架构结论](probe-design-findings.md)；后续真实操作暴露了未覆盖的问题，不能称为新一轮的完成结果。本文修改不启动 agent、测试或新 goal，也不改写旧证据。后续启动前以用户确认的范围和第 0 节产物形成目标；若工具不能修改已有 objective，将新约束持久化记录，并按工具实际支持的生命周期处理，不能虚报旧目标完成来另开目标。
