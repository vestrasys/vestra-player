# Internationalisation (i18n) design

Status: implemented. Round 1 (player 0.4.3, SDK 1.5.9) first shipped in player 0.5.0 with seven interface languages; round 2's text values (§7.1) are in SDK 1.5.11. Rulings and progress are in the [2026-10 round record](../process/rounds/2026-10-i18n.md); plugin authors read [Translate a plugin](https://vestrasys.github.io/vestra-player-sdk/documents/Translate_a_plugin.html), [Translations](https://vestrasys.github.io/vestra-player-sdk/documents/Translations.html) and [Migrate a plugin to English source text](https://vestrasys.github.io/vestra-player-sdk/documents/Migrate_a_plugin_to_English_source_text.html).

## 1. Principles

- All UI text has **English as the source**, and other languages are translations. There are 7 interface languages: `en`, `zh-Hans`, `ja`, `ko`, `de`, `fr`, `es` (`i18n::LOCALES`, SDK `LOCALES`; consistency is checked by the host-agreement test). There is no Traditional Chinese.
- **The language is decided only at startup** and does not change while running; changing the language in the options takes effect at the next start. So no Slint runtime translator is needed, and nothing depends on i-slint-core internal interfaces.
- **Plugin TS contains no translation code**. Text the user can see appears in only three places, and the player translates it with the plugin's own catalog:
  1. Declarations: command `title`, each segment of `path`, `reason`, settings page titles, panel/tab titles (including floating sidebar window titles), and the manifest's `name`, `punchline`, `description`, `tags`;
  2. Slint: `@tr("…")`;
  3. Sentences the plugin hands to the player for display: `osd.show(template, args?)`, `OsdPanel.set(template, args?)`, `dialogs.confirm({ …, args })`, the `title` of file dialogs.
  4. When fixed text cannot be separated from data: **text values** (§7.1) `plugin.i18n.text(source, args)`, `list(items, style)`, which are data, not translations, and can be placed in all of the places above as well as in property values, timeline titles, subtitle titles and parser errors, and are rendered by the player.
- Untranslated text shows the English source (templates still substitute their arguments).

## 2. Deciding the interface language

`main()` calls `i18n::init(i18n::resolve(preference, system))` once, after `Host` is built (the UI state file has been read) and before host commands are registered and any plugin is loaded:

1. The environment variable `VESTRA_LANGUAGE` (for development and testing; same values as below);
2. Otherwise the UI state file's `ui_state.appearance.language`: `"system"` or a locale; a value this player does not recognise is treated as `"system"` (not written back);
3. For `"system"` or nothing: `platform::preferred_languages()` (sys-locale: the language list in macOS System Settings, the Windows user display language, Linux `LANGUAGE`/`LC_*`/`LANG`), taking the first supported one; if none is supported, `en`. Headless mode (`--headless`) does not read the system language; unless `VESTRA_LANGUAGE` is set it is `en`, so diagnostic output is the same on every machine.

Tag mapping (`i18n::match_tag`, the same as SDK `matchLocale`): case, `_` and POSIX suffixes (`.UTF-8`, `@euro`) are ignored; `zh` with `Hans` or with no script, and a region other than TW/HK/MO → `zh-Hans`; with `Hant`, or a region of TW, HK or MO → **`en`** (user ruling: Traditional Chinese users see English; the next language is not tried); otherwise by primary language subtag; unsupported languages are skipped and the next one is tried.

The plugin process gets the current language from the environment variable `VESTRA_LOCALE`; the runner passes it to the SDK (`Transport.locale`) → `plugin.i18n.locale`. The `window.state` reply carries `language` (the saved choice) and `locale` (the language of this run).

Saving the choice: `appearance.setLanguage({ language })` (needs `ui.theme`, as part of appearance together with the palette) writes `ui_state.appearance.language` (`"system"` writes no field), broadcasts `appearance.changed { theme, language }`, and **does not change the language of this run**.

## 3. Catalogs

The format is gettext. The files plugin authors write (`locales/messages.pot`, `<lang>.po`, and the packed `dist/locales/<lang>.json`) are described on the SDK documentation site, [Translate a plugin → Files](https://vestrasys.github.io/vestra-player-sdk/documents/Translate_a_plugin.html#files). Below is how the player reads them:

- The key is the `msgid`, or `msgctxt` U+0004 `msgid` when there is a `msgctxt`. Only translated, non-fuzzy, non-obsolete entries are included.
- Plurals only distinguish 1 and not-1 (the same as Slint without a translator): `msgstr[0]` is used for n == 1, and `msgstr[1]` (or `msgstr[0]` if absent) for everything else. The Chinese, Japanese and Korean `.po` files use `nplurals=1` and only fill `msgstr[0]`.
- Loading (`i18n::load_locale`): first `locales/<lang>.json` (an installed package), otherwise `locales/<lang>.po` (`--plugin` development loading runs the source directory directly); `en` never has a catalog; a broken file writes one log line and is treated as absent. Catalogs are loaded when the plugin process starts (`Plugin.catalog`) and registered with the Slint file loader by package directory (§4), and unregistered when the plugin stops.
- The parser `src/host/src/i18n/po.rs` uses only the standard library, and `build.rs` also uses it (§6). The SDK's `src/i18n.ts` is a TS implementation of the same rules (used by TestHost and the CLI).

### 3.1 Machine translation markers and review

In round 2 the five languages `ja`, `ko`, `de`, `fr` and `es` (for the player and all built-in plugins) were machine translated by a translation agent. The markers and review process (`#, x-machine` on each entry, `# Reviewed by an AI reviewer` in the file header, markers removed after human review) are described on the SDK documentation site, [Translate a plugin → Machine translations and review](https://vestrasys.github.io/vestra-player-sdk/documents/Translate_a_plugin.html#machine-translations-and-review). On the player side: the parsers (host `i18n/po.rs`, SDK `parsePo`) only recognise `fuzzy`, so `x-machine` entries are compiled and displayed as usual; `zh-Hans` is the human-written text from 0.4.2 and earlier and has no such marker; the player's own `.po` files do not go through `extract`, so their header comments are not lost.

## 4. Slint: rewriting `@tr` at load time

The player has no Slint translator. `ui::view::compiler()` sets `set_file_loader` on every compiler: after each imported `.slint` file (a plugin's, or from the `@vestra/` library) is read, if it contains `@tr` and the package the file belongs to has a catalog (`i18n::catalog_for`: the longest prefix among registered package directories; the `ui/` directory uses the player's own catalog), the source literals inside `@tr` are replaced with their translations before the file is passed to Slint; Slint only does formatting (`{}`, `{0}`, `{n}`) and chooses the plural form. The source at the root of a compilation (`build_from_source`) does not go through the loader and is handled the same way by `ui::view::translate` / `composition::build` (plugin windows, panels, settings pages, the shell, the options window).

- Only the literals themselves are replaced: the two literals `id` and `plural` of `@tr("ctx" => "id" | "plural" % n, args…)`; the context, arguments and `%` expression are kept as is. A catalog entry whose singular/plural does not match the call (a singular entry for a plural call, or the reverse) is treated as untranslated.
- The lexer only knows the Slint it needs: `//`, nestable `/* */`, strings and their escapes (`\" \\ \n \u{…}`), string interpolation `"\{…}"`; `@tr` inside comments and strings is not touched; invalid calls are left as they are for Slint to report.
- Output escaping: `\` → `\\`, `"` → `\"`, newline → `\n`, other control characters → `\u{…}`; `{{` and `}}` are kept as is (they are braces when Slint formats).
- Shared cases: `src/host/tests/fixtures/slint-tr.json`. The host's `i18n::tests::slint_tr_cases_shared_with_the_sdk` and `tests/sdk/host-agreement.test.ts` (using the installed SDK's `scanSlint`/`rewriteSlint`) run the same file; `test/fixtures/slint-tr.json` in the SDK repository is a copy.
- In English no file is read or changed (there is no catalog, and the loader returns `None`).

## 5. Declarations and menus

- When a command is registered (`commands.register`): first `commands::normalize` turns the path into the **key** used for merging (`@video` → `Video`; old Chinese titles of the player's own menus → English keys, see the table below), then `Declaration::localize_declared` computes the display text `display { title, path }` with the plugin's catalog: the player's own submenus use the player's words (`commands::host_group_label`), and the other segments are looked up in the plugin's catalog by **the source text as declared** (old Chinese titles keep displaying as they are). `reason` is translated with the plugin's catalog on every update.
- The menu tree groups and sorts by key; `MenuNode::Group` carries a `label`: the player's word for the player's submenus, otherwise the display text of the first command in the group (in menu order). Menu rows and the binding table (`title`, `path` of `bindings.list`) all carry display text; the user's binding overlay is stored by plugin id + command id and is independent of the path.
- The keys of the player's own commands (fullscreen, quit, the 14 core actions) are English, and their display text comes from the player's catalog.

The player's menu keys and old title aliases (`MENU_ANCHORS`, `LEGACY_MENUS`, the same as SDK `MENU_KEYS`, `menuKeys`):

| id | key | Old Chinese title (still accepted) |
| --- | --- | --- |
| `@open` | Open | 打开 |
| `@playback` | Playback | 播放 |
| `@subtitles` | Subtitles | 字幕 |
| `@video` | Video | 视频 |
| `@audio` | Audio | 声音 |
| `@screen` | Screen | 屏幕 |
| `@settings` | Settings | 设置 |
| `@reset` | Reset | (none: added after English keys; shown as 复位) |
| | Playback ▸ Speed | 播放 ▸ 速度 |
| | Playback ▸ Seek | 播放 ▸ 跳转 |
| | Settings ▸ Appearance | 设置 ▸ 外观 (transitional: preferences has migrated, visualizer migrates in round 2) |

Aliases only change segments that have a next level (submenus), not leaves. After all plugins migrate in round 2, submenus shared by several plugins merge because everyone writes the same English key; the submenu keys declared by the built-in plugins are on the SDK documentation site, [Reference: Commands → Submenu keys in use](https://vestrasys.github.io/vestra-player-sdk/documents/Commands,_menus_and_bindings.html#submenu-keys-in-use) (SDK `BUILTIN_SUBMENUS`, checked by the player's tests).

Other declarations: settings page titles and panel titles (including the manifest `name` used as the default) are translated at registration and stored; each item of `packages.list` gains `display { name, punchline, description, tags }`, translated with each package's own catalog (catalogs of packages that are not running are read on demand).

## 6. The player's own text

- The source is English, written in code: Rust uses `i18n::tr("…")` and `i18n::tr_args("Back {} s", &json!([n]))`; the player's `.slint` files (`ui/`) and the Slint source it generates (the options window) use `@tr("…")`.
- Catalogs: `src/host/locales/messages.pot` (all source text) and `zh-Hans.po` (Simplified Chinese = the UI text of 0.4.2 and earlier, word for word). `build.rs` compiles `locales/*.po` into `$OUT_DIR/locales/<lang>.json` (a broken file fails the build) and generates `$OUT_DIR/host_catalogs.rs`: `HOST_CATALOGS` lists every compiled language with its `include_str!`, and `i18n::host()` takes the current language from it. Adding a language only needs a `.po` (and `LOCALES`), no code changes; `every_interface_language_has_an_embedded_host_catalog` checks that `HOST_CATALOGS` and `LOCALES` (minus `en`) are exactly the same, so a missing `.po`, or an extra `.po` without a language setting, fails; `host_strings_show_in_every_language` looks up one string per language.
- `i18n::tests::the_host_template_lists_exactly_the_strings_the_player_uses`: scans the `tr(` and `tr_args(` literals and `@tr` in `src/` (the part of each file before `#[cfg(test)] mod tests`), and `@tr` in `ui/`, which must match `messages.pot` exactly; every `.po` has the same entries as the template, and the placeholders of each translation are the same as the source. `the_simplified_chinese_catalog_keeps_the_old_texts` checks that the core action notices and other texts are word for word the same as the old version.
- Error messages returned to plugins that used to be Chinese and are shown directly to the user by plugins ("没有视频" (no video), "侧栏已被 … 使用" (sidebar already used by …), "全屏时不可用" (unavailable in fullscreen)…) are translated as well; English developer messages are not translated.

## 7. Templates and arguments

`osd.show`, `osd.panel`, and the `message`/`detail` of `dialogs.confirm` accept `args`: an array (`{}` takes them in order, `{0}` by index) or an object (`{name}`), with at most 16 strings or finite numbers (`i18n::valid_args`; SDK `templateArgs` checks the same). The player first looks up the translated template in the plugin's catalog, then formats it (`i18n::format`, with the same rules as Slint: `{{`/`}}` are braces, placeholders without a matching argument are kept as is; integers have no decimals). **Without `args` there is no formatting**, so old plugins' text displays as is. Length limits (OSD 200 characters, the confirmation dialog fields) count the displayed text. The button and check box text of the confirmation dialog is only translated, not formatted; the default cancel button is the player's "Cancel".

Arguments are data and are not translated. When an argument is itself a word from a fixed set, write one whole-sentence template per value (`theme === "x" ? "Palette: X" : "Palette: Y"`), or use a text value (§7.1).

### 7.1 Text values (round 2, SDK 1.5.11)

The requests from plugin authors in round 2 shared one root cause: user-visible text mixes fixed words with data (the menu item "音轨 2 (opus)" (Track 2 (opus)), the drop-down "无声音 / 音轨 7 · en" (No audio / Track 7 · en), "下载失败：连接超时" (Download failed: connection timed out), lists of file names, several clauses), and TS can neither translate nor build sentences. The design and point-by-point replies are in "Round 2 replies" in the [round record](../process/rounds/2026-10-i18n.md).

- **Wire shape** (`src/host/src/i18n/text.rs`): `{"$vestraText": source, "args"?: [...] | {...}}`, `{"$vestraList": [...], "style"?: "list"|"clauses"|"semicolons"|"sentences"|"lines"}`; arguments are strings, finite numbers or text values. No other fields are allowed. The same convention as `$vestraImage` and `$vestraMarkdown`: Slint struct fields cannot start with `$`, so this never collides with real data.
- **Rendering** (`Texts::render`): `source` is looked up in the plugin's catalog (English if absent), arguments are rendered first and then formatted per §7; a Text is always formatted (the same as Slint `@tr`). Lists are joined by `text::SEPARATORS` (one separator per language per style, the same as SDK `LIST_SEPARATORS`, checked by host-agreement).
- **Semantics**: a string is still translated as a whole sentence (declarations) or used as a template (sentences); a text value used as a sentence carries its own arguments, and giving `args` outside it as well is `invalid`. A Text segment of a command: key = the English rendering (`Texts::english()`, used for menu merging and the binding table `key`), display = the translation (`Declaration::show_texts`); a TextList cannot be a menu segment.
- **Where rendering happens**: at the start of `dispatch`, text values in the arguments of `ui.open`, `ui.set`, `ui.mount`, `ui.setMount`, `settings.register`, `settings.set`, `timeline.set` and `subtitles.commit` are replaced wholesale with strings (later value limits and length checks count the displayed text), and likewise the `error` of `sourceResolvers.respond` (the backend thread has no plugin catalog); `osd.*`, `dialogs.*` and `commands.*` render during their own handling.
- **Limits**: `TEXT_LIMITS`; values on the SDK documentation site, [Reference: Limits → Text values](https://vestrasys.github.io/vestra-player-sdk/documents/Limits.html#text-values) (host `i18n/text.rs`, checked by host-agreement).
- **Truncation**: `maxColumns` (8–1000) of `osd.panel` truncates each line by `unicode-width` after translation and formatting (wide characters take 2 columns).
- **`resolve`**: the SDK in the plugin process renders synchronously with the same rules and the same catalog (`loadPackageCatalog`), only for text that leaves the player (clipboard, files). The player side needs no cooperation.
- **Compatibility**: `vestra/1` only gains new shapes; plugin code runs on the SDK bundled with the player, so text values arrive together with player 0.4.3, and older players have no `plugin.i18n.text` (plugins write `minPlayerVersion`).

## 8. Fonts (CJK glyphs)

Each window uses the system UI font, and Slint falls back per character. The same code point has different customary glyphs in Chinese, Japanese and Korean (骨, 直, 角), and system fallback may pick the Chinese glyph. The user allows, **only for ja and ko**, when phase verification confirms wrong glyphs, setting a system-provided UI font per language (an exception to the 10-22 "do not set fonts" ruling). Not implemented in this round; only the interface is kept: `i18n::ui_font_family(locale)` currently returns `None` for every language; when needed, the window font is set from it in `theme::apply_fonts`.

**How to check in phase verification** (coordinator screenshots on a real machine): start with `VESTRA_LANGUAGE=ja` (then `ko`), open a UI that mixes Japanese/Korean with Han characters (the menus and options window after the plugins are translated; or temporarily load a test window whose `@tr` says "骨 直 角 刃 化 写 誤 説 갈 값"), enlarge the screenshot, and compare with the same text in System Settings; it passes if the glyphs match the Japanese system font (Hiragino Sans / Yu Gothic) or the Korean one (Apple SD Gothic Neo / Malgun Gothic); otherwise record which characters on which system, and then decide whether to fill in `ui_font_family`.

## 9. Menu width estimation

`menu::text_width` estimates by Unicode East Asian Width: wide characters (W/F: CJK, kana, hangul, full-width) are about one font size wide, others (Latin, Latin with diacritics, Cyrillic, symbols) about half, and combining marks take no width. So long German and French menu items are no longer measured as if they were Chinese.

## 10. SDK (1.5.9; 1.5.11 adds text values)

The SDK side (`plugin.i18n`, text values, `appearance.language`, the `vestra-plugin i18n extract` and `i18n check` commands, and the TestHost's `locale` option) is documented once, on the SDK site: [Translations](https://vestrasys.github.io/vestra-player-sdk/documents/Translations.html) (reference, including what `extract` and `check` do and how tests load a catalog) and [Translate a plugin](https://vestrasys.github.io/vestra-player-sdk/documents/Translate_a_plugin.html) (how-to). One rule that matters for the player: without a `locale`, the TestHost shows the player's own text as the Chinese of SDK 1.5.8, so tests written before the round are unchanged.

## 11. Known limitations

- Changing the language needs a restart.
- Plurals have only two forms; languages with more forms such as Russian, Arabic and Polish are not supported.
- Numbers in templates are written the JS/Rust way (`1.5`), not by language convention (German `1,5`).
- Error messages the SDK generates itself and plugins display directly ("无法打开此媒体" (cannot open this media) and others in `player.ts`, `stream.ts`, `subtitles.ts`) are still Chinese and have no catalog; round 2 must decide: change them to English and ship a small catalog with the SDK selected by `locale`, or turn them into error codes that plugins express with their own templates.
- Plugin READMEs / CHANGELOGs (the store's details page) have no per-language versions.
- `vestra-plugin i18n extract` loses the file header comments before `msgid ""` when rewriting a `.po` (the `# Reviewed by an AI reviewer` of §3.1); the SDK's `parsePo`/`writePo` need to keep header comments.
