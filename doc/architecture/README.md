# Architecture overview (maintainers)

A map for API maintainers: how the components divide the work, how plugins are loaded and stopped, what protocol the SDK and host speak, and where the code is. Plugin authors should read the [SDK documentation site](https://vestrasys.github.io/vestra-player-sdk/); the SDK's design trade-offs are in [sdk-design.md](sdk-design.md); the project principles are in [doc/product/](../product/direction.md).

## 1. Components

```text
┌──────────── Host process (Rust, src/host) ────────────┐
│ Slint native UI: main window, bottom bar/sidebar mounts, tool windows, menus │
│ libmpv playback backend, processing chain, subtitles, snapshot/export workers │
│ Plugin management: load, stop, install/uninstall, reclaim owner resources    │
└───────────────▲───────────────────────────────────────┘
                │ JSONL over stdin/stdout (wire: vestra/1)
┌───────────────┴──── Node processes ───────────────────┐
│ Built-ins: one shared runner (shared-runner.ts)       │
│ Others: one runner each (runner.ts); both use boot.ts │
│ SDK  @vestra-player/sdk (separate repository, npm dependency): plugin/ handle API → wire client (internal) │
│ Plugin src/plugins/<name>/: main.ts + .slint          │
└───────────────────────────────────────────────────────┘
```

- The **Rust host** only provides shared facilities: playback, UI composition, processing chain, subtitles, export, plugin lifecycle. It does not recognise plugin identities and contains no plugin business logic (site resolution, save states, presets and so on are all in plugins). First-party code forbids `unsafe`.
- **TypeScript plugins** are the only place for business logic. Plugins are fully independent of each other and cooperate only through public host state.
- **Slint** is the only form of plugin UI: tool windows (separate windows) or panels mounted in the bottom bar/sidebar, compiled and composed by the host.

## 2. Loading and stopping plugins

- **Development loading**: `vestra-host --plugin <directory>` (can be repeated) runs the entry `.ts` directly (Node 26 type stripping; the installed package uses the bundled Node, see `src/host/src/process/runtime_paths.rs`).
- **Managed installation**: `packages.validate` → `install`; `uninstall`; `setEnabled` (there is no rollback since 2026-10-26); a first install runs, an update or reinstall keeps the enabled state (a disabled plugin is installed without running) unless `install`'s optional `enabled` says otherwise ([store API §1.3](store-api-proposal.md#13-rules)); packages are stored in `VESTRA_PACKAGE_STORE`, built-in plugins run in place from the installation. Only build output is accepted (`dist/`, entry is `.js`, manifest has `version`).
- **Processes**: built-ins the host trusts by provenance (`Host::trust`: listed in the installation's `builtin.json` schema 3 with a matching package digest) share one Node process, `node --max-old-space-size=1024 shared-runner.js` (`process/shared_runner.rs`); every other plugin, every development load and a built-in whose digest does not match (or with `VESTRA_SHARED=0`), and a built-in moved out after a fault (quarantined for the run, or all of them after the third runner restart within a minute) runs in its own, `node --max-old-space-size=512 runner.js <package directory>` (development loads without the heap cap). Both hand the plugin's life to `src/runtime/boot.ts`. Packaged players run the runners as `.js` (`stage-runtime.mjs`), a development build runs the `.ts` sources (`runtime_paths.rs`).
- **Activation, stopping, faults**: `runtime.ready` once `activate` returned and its registrations succeeded, else `runtime.failed`; stopping revokes everything the plugin owns by owner, then sends `runtime.stop` and gives the plugin its stop grace (5 s for a disable, reload, uninstall, upgrade or standby; 300 ms after a failure; at quit 1 s for all plugins together, 300 ms after a lost graphics device; [supervisor §6](supervisor.md#6-timings)): an own process is then killed; a shared-runner member still cleaning up after 300 ms is counted as leaked, and the runner abandons its cleanup after 5 s; each run gets a new owner generation, so late messages of an old run never reach a reloaded plugin. The timings, the shared runner's per-member faults, heartbeat and restarts are described from the host's side in [How the player runs and talks to plugins](https://vestrasys.github.io/vestra-player-sdk/documents/How_the_player_runs_and_talks_to_plugins.html).
- **Stop reasons** (player 0.6.4, SDK 1.5.54 `StopReason`): `runtime.stop` carries `{"data":{"reason":"<r>"}}` (a shared-runner member: `{"g":N,"event":"runtime.stop","data":{"reason":"<r>"}}`; the player quitting sends the shared runner one `{"g":0,"event":"runner.stop","data":{"reason":"quit"}}` for every member). Players up to 0.6.3 sent `"data":null`. The runner passes the reason to `PluginInstance.dispose({ reason })` (`src/runtime/boot.ts`), which gives it to `plugin.stopReason` and every `onDispose` cleanup's `DisposeInfo`. The host picks it where it stops the plugin (`Host::stop`/`disable`, `process::StopReason`; a plugin dropped with the host is `quit`):

  | Reason | Where the host stops it | Delivered? |
  | --- | --- | --- |
  | `quit` | The player quits: every plugin process is stopped at once with one deadline ([supervisor §9](supervisor.md#9-quit-and-device-loss): the shared runner one `runner.stop`, each own process its `runtime.stop`; killed at 1 s, 300 ms after a lost GPU device; recordings written first). Also a restart after a lost GPU device, except when its teardown is stuck: the process is then ended at once (`platform::exit_now`, 5 s after the event loop ended or 15 s after the restart, `host/restart.rs`), and every plugin whose stop had not run yet reads `host-lost` (its pipes close) | Yes, until the one deadline (1 s; 300 ms after a device loss), then killed |
  | `disable` | `packages.setEnabled(id, false)` of a running plugin; an install with `enabled: false` over a running version (the new version is committed disabled and does not start). Such an install cancelled while `preparing` restores the old version: it was stopped for `disable` and is started again (a new instance, which later stops with its own reason) | Yes |
  | `uninstall` | `packages.uninstall` of a running plugin; also a first install (no previous version) cancelled while the new plugin activates | Yes (its data is removed after the process is gone) |
  | `reload` | `packages.reload` of a running plugin | Yes |
  | `upgrade` | An install over a running package that runs on stops the old version: an update, a reinstall of the same version, and a `replace` from another source (fresh data) alike (an update of a disabled package has no process to stop); also a new version stopped because its install was cancelled while the previous version comes back | Yes |
  | `idle` | The supervisor puts it in standby: 30 s idle, the end of a first run that holds nothing live, the process budget or memory pressure ([supervisor §4](supervisor.md#4-standby-and-wake)) | Yes (the same 5 s grace as a disable) |
  | `failed` | A malformed request; an oversized (> 1 MiB) or unparsable line from an own process; an oversized line from a member; a failed or timed-out activation; an uncaught exception the shared runner attributes to a member (the runner retires it with `failed` itself, before the host's stop); a full input queue of an own process; its stdin write failing; its process exiting | Partly, see below |

  `failed` is truthful only where a stop line can still reach the plugin. Delivered: a malformed request, a bad or oversized line (the host reads and drops the rest of that process's stdout and still writes its stdin), an activation timeout, an attributed uncaught exception. **Not delivered, the process is only killed**: an own process whose input queue is full (the stop line cannot be queued either) or whose stdin write failed; a process that already exited; an own process whose activation failed (the runner exits with code 1 without running cleanups). A shared-runner restart (a hang, an unattributed fault, an unparsable line from the runner, a member's full queue, the runner exiting) kills the runner first, so its members get no stop and their cleanups do not run. When the idle shared runner (no member left) is let go, its `runner.stop` carries no reason.

  A process that ended by itself (its stdout closed: an exit, a crash, V8's heap abort) gets no `runtime.stop` at all: the host cleans up after it and the reaper only waits for the process.
  The runner adds `host-lost` itself: its stdin closed or its stdout broke before any `runtime.stop`/`runner.stop` (the player crashed or was killed). The first stop wins: stdin closing after a stop keeps that stop's reason. So the host never closes a runner's stdout early: its reader threads (`process::read_plugin`, `shared_runner::read_lines`) read to the end after a fault and after the host stopped listening (at quit the GUI's event receiver goes before the plugins are dropped), only dropping what they read, so a plugin that writes during that time does not see a broken pipe and stop as `host-lost` ahead of its `quit` or `failed`.
- **Plugin process supervisor**: when each plugin's process exists is decided by one component, a pure core (`src/host/src/supervisor/`) and its adapter (`src/host/src/host/supervisor/`); the rules, timings and limits are in [supervisor.md](supervisor.md). In short: a plugin's first run is recorded (commands in registration order, bindings, settings pages, drop targets, resolvers, wake-event subscriptions); a plugin that holds nothing live is then put in **standby** (no process, its entries replayed from the recording) and started again by their first use or by a wake event (`WAKE_EVENTS` in `capabilities/events.rs`); 30 s idle puts it back; a plugin that holds something live at its ready never stands by. Third-party starts are limited and ordered (built-ins first, clicks before events before background starts); triggers wait for the plugin's ready, at most 64 per plugin, and one that cannot be delivered is answered (an OSD for a command, a failed open for `source.resolveRequest`). A plugin stays up while a `source.resolveRequest` sent to it is unanswered (a fault after 5 min) or while it has declared work (a busy command, a settings page compiling or shown, a host dialog, a package RPC, a source state request waiting for the playback worker; no cap). Crashes restart a built-in or a resident plugin after a growing pause, a recorded third-party plugin waits in standby for its next use; 5 crashes in 10 min leave it failed. At most `clamp(physMiB / 2 × 0.30 / 85, 3, 16)` third-party processes run at once, and memory pressure puts idle third-party plugins in standby. A plugin in standby is listed as `running` with `process: "idle"`.
- **Test switches** (`host/supervisor/probe.rs`, read in any build, not passed to a player restarted after a device loss): `VESTRA_TEST_REGISTRY=<file>` writes each plugin's registries (commands, bindings, settings pages, drop providers, wake events) at its ready, standby, replay, wake and at quit; `VESTRA_TEST_PARK=all` puts every installed plugin in standby, resident ones too (only what a recording can hold is recorded; **isolated profile only**: its recordings are marked `testPark` and ignored by any run without the switch); `VESTRA_TEST_WAKE=<ms>` wakes every plugin in standby that many milliseconds after the host started; `VESTRA_TEST_EXECUTE=<id>/<command>@<ms>[,...]` runs a command as a click would. `VESTRA_IDLE_MS` shortens the idle time; `VESTRA_TEST_PHYS_MIB` and `VESTRA_TEST_PRESSURE` (`host/supervisor/memory.rs`) simulate the memory size and pressure. `tests/lazy_activation.rs` `every_built_in_keeps_its_registry_through_park_replay_and_wake` diffs the registries for every built-in (ignored; headless covers the built-ins without a panel mount).

Manifest rules are in [Manifest](https://vestrasys.github.io/vestra-player-sdk/documents/Manifest.html), capabilities in [Capabilities](https://vestrasys.github.io/vestra-player-sdk/documents/Capabilities.html). Capabilities are a contract declaration that the host uses to reject undeclared calls (`code: "capability"`); they are not a security sandbox.

## 3. Wire protocol

- Framing, message shapes, owner generations and why the runner sets no client-side timeout are on the SDK site: [The wire protocol](https://vestrasys.github.io/vestra-player-sdk/documents/How_the_player_runs_and_talks_to_plugins.html#the-wire-protocol). Protocol details (revision numbers, source generations, operation ids, event sequence numbers) stay inside the SDK ([sdk-design.md §5](sdk-design.md#5-how-protocol-details-are-absorbed)).
- Wire methods exist only to serve the SDK. Methods the SDK no longer calls should be deleted from the host, not kept for hypothetical callers (old interfaces deleted on 2026-10-20: `host.capabilities`, `playback.state/open/seek`, the properties of `playback.set` other than volume/mute, `window.state` (RPC)/`setFullscreen`, `commands.snapshot/execute` (RPC), `plugins.list/load/activation/disable`, `jobs.list`, `subtitles.upload.status`, and the `playback.state`, `plugins.changed` and `host.error` events).
- The events a plugin can subscribe to are `EVENTS` in `capabilities/events.rs` (the capability each needs is in `capabilities.json`). Events the host pushes to a particular plugin without a subscription: `commands.execute` (a menu or binding triggered its command), `ui.callback`, `sequence.step` (when it is the playback sequence provider), and others.
- The host merges `sequence: { next, previous }` (the playback sequence provider's flags) into the data of `source.state` (event and RPC reply); when the flags change, the host resends the current source state once with the same `eventSequence`, and the SDK accepts a state with "the same sequence number, different content".
- `producer.declareInput` and the physical input subsystem are kept: the SDK does not expose keyboard input yet, but this is the ready-made capability for emulator keyboard input.

## 4. Slint composition and input

- Compilation: the host, panels, tool windows and package validation share one compiler configuration (`compiler()` in `ui/view.rs`): library path `vestra` → `ui/vestra/` (`@vestra/theme.slint`, `@vestra/widgets.slint`, `@vestra/markdown.slint`, `@vestra/icons.slint`), style `fluent-dark`. The palette (`theme.rs`) is written by the host into each instance's `VestraPalette` (`ui/palette.slint`, not part of the plugin library): 22 colours, `accent-fill` (copied from the per-palette gradient constants in the same global, because Slint's Rust API cannot construct gradients) and `color-scheme`; the latter is two-way bound to the std-widgets' `Palette.color-scheme`, so the light palette `vestra-light` switches the std-widgets compiled with `fluent-dark` to light at run time, without recompiling. Fonts are in the next item.
- Fonts (user ruling 2026-10-22): the host does not set the font of any window; each window uses the system default font, and missing glyphs (Chinese in a Latin font, Chinese in `font-mono` Menlo) fall back per character in Slint 1.18 to a system font that has the glyph (parley/fontique; confirmed on a real macOS machine and with a headless probe; Windows awaits S6 on a real machine). Chinese fonts shipped with each system: PingFang on macOS, Microsoft YaHei on Windows, usually Noto CJK on Linux distributions, the system font on Android/iOS. The injection that forced Hiragino Sans GB / Microsoft YaHei in the 1.16 era (`platform::ui_font`, `ui::view::font_import`, `default-font-family` on the window root, the `// VESTRA-FONT` marker in `host.slint`, `VESTRA_FONT_FALLBACK`) has been deleted; the old code is in `ui.rs`, `composition.rs` and `settings_window.rs` at 2f8e6ab.
  - CJK fallback chain (2026-10-24, fixing boxes on Windows): Slint gives fontique only one fallback key per script (script, no language), and on Windows fontique asks DirectWrite for **one** font family with an empty language; the answer depends on the system language (it may be a Japanese/Korean UI font that lacks Simplified Chinese characters, or nothing), so Chinese shows as boxes. `ui_fonts::install` (in `main.rs`, after the backend is chosen and before the first window) uses `slint::fontique_011::shared_collection()` (`unstable-fontique-011`) to set a chain for each of Hani, Hira, Kana, Hang and Bopo: the installed system fonts from `platform::ui_cjk_fallback_families` (table in `platform/fonts.rs`, Windows only: Microsoft YaHei, JhengHei, Yu Gothic/Meiryo, Malgun Gothic, etc., ordered by interface language), then the system's own choice, and finally the Noto Sans CJK SC already bundled for subtitles (`font_asset::bundled_bytes()`, zero-copy, no increase in installer size; `platform::ui_bundled_cjk_fallback`: yes on Windows and Linux, no on macOS). It only adds fallbacks and does not change the default font: Latin text still uses the system UI font, and the window's `default-font-family` still comes first. All Slint windows on the same UI thread (main window, panels, tool windows, plugin windows, options window) share this collection. macOS is unchanged (CoreText fallback). `VESTRA_DEBUG_FONTS=1` prints each chain at startup; when a script has no system font, a one-line notice is always written to stderr. The chain is ordered by interface language: `ui_fonts::install(i18n::locale())` is called after `i18n::init` (`ja` puts Japanese fonts first, `ko` Korean, everything else Simplified Chinese).
  - Italics: no system Chinese font has italics, and FemtoVG and the software renderer do not synthesise italics, so Markdown italics still get an extra colour (`EMPHASIS_COLOR` in `ui_markdown.rs`).
- Slint is pinned to `=1.18.1` (`Cargo.toml` and `unsafe/render`). Private interfaces depended on, to retest on every upgrade: `parse_markdown` in `ui_markdown` (Markdown with placeholder arguments); `WindowInner::ensure_tree_instantiated` in `ui::view::settle_layout`; and, for the main-window swap below, slint-interpreter's `internal` feature (`ComponentDefinition::create_with_existing_window`) and `WindowInner::try_component`/`set_component`/`show`/`window_item` in `ui::view::ShownTree` and `replace_shell` (tests `ui::view::tests::shell_swap_*`). The reason for the latter: since 1.17, `if`/`for` elements are created and deleted in a pass before each frame render and each input event, not when layout is read, so geometry read after the host switches a condition such as `sidebar-visible` and before the next frame is stale; the host calls it before reading the video area and window size (window tick, picture-in-picture positioning, `window.setVideoArea`, drop location).
- **Slint upgrade checklist**: besides the private interfaces above, selectable Markdown (`ui/vestra/markdown.slint`, SDK 1.6.0) relies on `TextInput`'s `anchor-position-byte-offset` and `cursor-position-byte-offset` properties (Copy copies the whole block when they are equal, that is, when nothing is selected). Check that both still exist and behave so after any Slint upgrade.
- Main-window composition changes (a panel mounted or unmounted: a plugin installed, enabled, disabled or uninstalled, the shared runner restarting; `prepare_mount_tick`) compile a new shell but keep the native window, the way browsers and IDEs swap content (`ui::view::replace_shell`): the new component tree is created inside the old shell's window (`composition::compile_json_in`, as Slint's live preview reloads), the window's fullscreen/maximized/minimized flags (kept by Slint on the tree's root `Window` element) are carried over, and `show()` on the new shell only moves the window's strong reference; the old shell is dropped, never hidden. So the window does not fade, move or resize, keeps its focus and z-order, and its rendering notifier, reused video texture, frame pacing clock, native window id and title bar stay; what pointed at the old shell is retargeted (`Host::retarget_shell`: `video_target`, the GPU renderer's redraw requests and current image, `frame_pacing::follow`). The window's single winit event hook is set for the new shell's generation only once it is shown (`Host::bind_window_events`). If building fails after Slint attached the new tree, the old tree is shown again with the window's strong reference and the video area's focus (`ShownTree::restore`, `focus-video`), and a shell built outside the main window is refused. Emulator key capture is not revoked by a swap (the window is neither hidden nor unfocused). Only `host.shell` holds the main shell (the event loop runs with `slint::run_event_loop`, not the first shell's `run()`), so a replaced tree is freed. Before 0.5.11 each change opened a new native window and hid the old one (on Windows the DWM hide/show animation showed the desktop for about half a second, and the window came back unmaximized or a few pixels off).
- Cover art of a leased audio file (`cover-art-files`, which libmpv would derive from the path; `source_backend::cover_art`) is listed on its own thread (`playback::cover_listing`), not on the backend thread: the load waits up to 200 ms for it; a folder listed more slowly (a huge network folder) loads the file without it, and once the listing answers the same pictures are added to that load with `video-add` (`albumart`, asynchronous, one at a time so the tracks keep the listed order), the first that opens selected unless the file's own picture is shown (`audio-display=embedded-first`). At most 4 folders are read at once: a load from a folder already being read or queued (the next song of the album) shares that read, other folders queue for a free reader newest first, so the file playing now waits for its cover art instead of going without and is not held up by older requests; a folder whose loads all ended meanwhile (quick skipping through a slow share) is dropped from the queue unread. A reader that panics gives its place to the next queued folder; one that cannot start tries the next. The `video-add` replies carry the entry id (`cover_listing::reply`), so a reply for an earlier entry is not taken for the current one's; a backdrop mounted before the pictures come leaves them all out (one mounted while they are being added stops the rest). Before 0.5.12 the backend thread listed the folder itself, so a huge network folder stalled playback requests until it finished.
- Tool windows: a plugin `.slint` file exports exactly one component; the host compiles it with slint-interpreter and forwards callbacks according to the callback allowlist registered by the SDK.
- Panels: the file exports one component and one global (the bridge object for properties and callbacks); the host imports it into the main UI under the owner alias (the insertion marker in `host.slint`) and forwards all callbacks on the global. Main window shell: the video column (video + bottom bar) on the left, a 3px splitter and the full-height sidebar on the right; in fullscreen the bottom bar overlays the bottom of the video and hides according to the idle rules of `window_state::Policy` (not while the pointer rests on the bottom bar), and an attached sidebar becomes a pop-up layer at the right edge.
- Floating panels (C14): on detach the host compiles a separate window that imports the same component and bridge global; there is one global per window instance, so the host initialises the floating window from the saved `Mount.properties`, and from then on each `ui.setMount` writes both the main window and the floating window; callbacks from both are forwarded as `$mount`. On attach only the floating window is closed; the main window is not rebuilt.
- Input: the outermost layer of the main window and each of the two panels is wrapped in a FocusScope. Slint gives a key to the focused control first, and unaccepted keys bubble up level by level; the panel layer looks up "panel + global", and the outermost layer looks up global (`bindings.rs`). The lookup runs synchronously on the UI thread (`Rc<RefCell<InputShared>>`, without borrowing Host); if bound, it returns accept and sends `Event::Binding`, and the main loop then checks the enabled state against the registry and executes. The table keeps a mirror of the registry's disabled commands (synced each pass by registry revision): a disabled command yields the key to the next command for the same input; when only disabled commands remain, one with a `reason` shows the reason on the OSD, and one without does not accept the key. Video-area mouse input (double-click, middle button, wheel) works the same way; the side buttons (X1/X2) are window-level since host 0.6.0: the window's winit hook resolves them wherever the pointer is, except over an open menu. Toggle, Enter and Leave Fullscreen, Quit and Toggle Sidebar are the host's own commands (owner 0), in the same table and menu tree as plugin commands.
- Menus: `commands.rs` builds the tree by `order` (a submenu takes the order of its first command), `menu.rs` projects it into a panel list (separators, radio items, shortcut text, row positions), and `menu-view.slint` only draws it. Panel context menus (C11) reuse the single-level form of the same projection and pop up in whichever window the panel is currently in.
- Command palette (host 0.7.4, menu redesign §6): `host/palette` (Ctrl+Shift+P; ⌘⇧P too through `CTRL_ACCEPTS_CMD`) opens it in the main window as a menu mode (`MenuMode::Palette`), so it pauses bindings, counts as an obstruction and closes like a menu. `command_palette.rs` lists every registered command but `focus: "panel"` ones and disabled commands without a reason (placeholders such as No Audio Tracks; as VS Code hides a command whose `when` is false, so unbinding a key never hides one), names each `Category: Title` (`CommandOptions.category`, else the menu path above it, else the plugin's name; the player's own commands and the core actions carry categories in the built-in plugins' words, `core_actions::CATEGORIES`: Playback, Seek, Speed, Audio, Window, File, Help), matches each typed word fuzzily against the row, its English keys, the menu path and the plugin, ranks the 8 most recently run (`ui-state.json` `paletteRecent`) first, and projects a fixed 12 rows that `command-palette.slint` draws in place (no element is created or destroyed while typing or moving). Enter runs and closes, Shift+Enter runs and stays open with the cursor on that command wherever it now sorts, a disabled row shows its reason and does not run, and the palette's own command run from it just closes it.
- Emulator input capture (`producer.declareInput`) intercepts keys first at the winit layer; keys bound to host commands (fullscreen etc.) are let through.
- Monospace font: `Theme.font-mono` reads `VestraPalette.font-mono` (`ui/palette.slint`, default Menlo); whenever the host sends the palette to a view (main window, floating panels, tool windows, options window), it also sets it to `platform::monospace_font(SYSTEM)` (Menlo on macOS, Consolas on Windows, DejaVu Sans Mono on Linux; a pure function, with each system tested on any machine), `theme::apply_fonts`; this is independent of the palette and is also set under the Vestra palettes.
- Standard window shortcuts (user ruling 2026-10-22): tool windows, floating panels and the options window close by system convention (macOS ⌘W; Windows Ctrl+W, Ctrl+F4; Linux Ctrl+W); the main window does not respond. The table is in the platform layer, `platform/shortcuts.rs`: a per-system pure function `window_shortcuts(System)`, with each platform module only declaring its own `SYSTEM`, so every system's entries are tested on any machine; adding Linux desktop variants, Android or iOS later only adds entries (the mobile tables are empty, and the back gesture is mapped to `WindowAction::Close` by that platform module). `ui::view::WindowShortcuts` checks the key first in the winit hook of these windows (letters by the unmodified character of the current layout, non-Latin layouts by US key positions; modifiers must match exactly); on a match it calls `slint::Window::dispatch_event(CloseRequested)`, the same path as the title bar's close button (tool window `ViewClosed` → plugin `ui.closed`, floating panel `FloatingClosed`, options window `Event::Settings(_, None)`, the same as `close-window` of the "Close" button), and returns `PreventDefault`: Slint never receives this key press, so it also works while an input box has focus, and it never reaches the binding table or a plugin's Slint handlers. Previously the options window's ⌘W was written in Slint and looked at `modifiers.meta`, but on macOS Slint reports ⌘ as `control` (⌃ is `meta`, see `SLINT_CONTROL_IS_COMMAND`), so it never worked; that handler has been deleted.

## 4.1 Hardware decoding and the processing chain (`processing.rs`)

- Default modes: GPU rendering uses zero-copy `hwdec=auto-safe` (VideoToolbox on macOS), software rendering uses copy-back mode (`renderer::hwdec`). The video nodes of the processing chain are FFmpeg software filters that need frames in memory, so as soon as any plugin has a video chain, it switches to the copy-back version of the same mode (`copy_back`: `auto-safe` → `auto-copy-safe`), and once the player's graph has no filters left it switches back to the original mode (`frames_in_memory`; switched with the installed graph, not with each plugin's chain: a chain of only neutral nodes builds none, and pass-through slots stay up to 2 s, see 4.1a). If someone else changed `hwdec` in between, or the rendering method changed (`renderer_changed`), it no longer switches back.
- The exception (host 0.5.4, DEINT-AUTO-1): a `deinterlace` node with `when: "auto"` is not an FFmpeg filter in the player's graph but mpv's own deinterlacer, the global option `deinterlace=auto` (`Processing::set_deinterlace`). mpv decides per frame from the decoder's interlaced flag and runs it as its `userdeint` pre-filter, before the `vf` chain (so before `@vestra-orientation` too): `d3d11vpp` on zero-copy `d3d11va` frames, `bwdif mode=send_field` on frames in memory, after a download for frames with no hardware branch (VideoToolbox); always one frame per field. Once the first interlaced frame inserts it, it stays until the frame format changes or the next file, and later progressive frames pass through it (on macOS they are then downloaded too, so a mixed source loses zero-copy after its first interlaced frame); `deinterlace-active` reports the current frame's flag. Such nodes do not count for `frames_in_memory` (`effects::needs_frames_in_memory`) and are left out of the player's graph (`effects::render_player`); the offline graph of exports and processed snapshots renders them as `bwdif=mode=send_field:deint=interlaced`, first (`effects::render_lavfi`); offline FFmpeg autorotates before the graph, so a rotated interlaced source is deinterlaced after the rotation there (known limitation, as for the explicit modes). The option is shared: `auto` while any owner's chain has such a node, `no` otherwise, recomputed on every video change and in `disable`, and always switched before the graph change (`deinterlace_then`; a paused picture is redrawn by the graph change, so it must already see the new value; `replace` puts it back if the graph change fails); the host is its only writer. `output: "frame"` with it, or another `deinterlace` node in the same resource, is `invalid` (`VideoNode::validate_chain`).
- Switching at run time makes mpv reopen the decoder and seek from the previous keyframe back to the original position (mpv's `Seek` and `PlaybackRestart` events). Meanwhile a batch of VideoToolbox frames fails (`vt decoder cb: … -12909`; measured at 11–15 frames when switching between copy-back and zero-copy; with 50–60 fps sources it fails every time, more so the busier the machine). After `hwdec-software-fallback` consecutive failures mpv switches to software decoding, and does not return to hardware for the rest of the file. The host sets it to 32 at startup (`HWDEC_SOFTWARE_FALLBACK`; mpv's default is 3; 32 is the upper bound that still keeps mpv's packet replay during probing).
- Retry once if it still falls back to software (2026-10-25): after a switch the host made itself, it watches `hwdec-current` (`observe_hwdec`, `Event::PropertyChange` in the backend event loop; the state push also checks every 100 ms so the window can end even without events). Conditions: hardware decoding was active before the switch; mpv has finished this switch's seek (`PlaybackRestart` received); no more than 3 seconds have played since the switch (`HWDEC_WATCH_SECONDS`, measured by `time-pos`; pausing does not consume it, and seeking back or changing file ends it); and `hwdec-current` is now `no`. If all hold, the expected mode is reapplied: copy-back mode while chains remain, otherwise the configured mode. mpv treats "set to the current value" as no change, so it first sets `no` and then the expected mode, and only then is the decoder reopened. The retry must not happen before `PlaybackRestart`: reopening the decoder while mpv is still replaying packets for the switch makes the video end immediately (`video EOF reached`). Only one retry per switch; if it falls back again, the file uses software decoding; fallbacks outside the window (the file itself cannot be decoded) are not retried and are left to mpv. One `processing: hwdec …` line each is written to stderr at the retry and for its result. The decision is the pure function `HwdecWatch::step`, which has unit tests.
- After one file falls back to software, the next file tries hardware decoding again: mpv chooses again from `hwdec` every time it initialises a decoder.
- Do not change `hwdec-software-fallback` during playback: changing any vd-lavc option reopens the decoder (which is itself the same as a retry).
- Real-machine tests (`cargo test --locked -- --ignored`, macOS, needs a GPU and ffmpeg): `gpu_decoding_runs_the_owned_chain` (filters take effect with a chain, back to zero-copy without one), `gpu_decoding_comes_back_after_a_fallback_caused_by_a_switch` (sets the threshold to 3 and keeps all cores busy to force a switch to fall back to software, then confirms the retry restores hardware decoding and retries only once), `the_next_file_starts_with_hardware_decoding_after_a_fallback`.

## 4.1a The player's video graph: live changes, pass-through, processing size (filter performance)

Plugins describe video chains; what stands in mpv's `@vestra-owned` graph is the host's (`effects::PlayerGraph`, kept by `Processing::installed`; `Processing::video` stays what the plugins asked for, and snapshots and exports render that at full size through the offline graph, `render_lavfi`). Every plugin filter is a CPU lavfi filter in both render modes; the measurements behind this section are headless libmpv runs shaped like the host (software render API, `hwdec=auto-copy-safe`, the same labels and commands).

- **Live first.** A change goes to mpv as runtime commands (`vf-command`) whenever the installed graph can reach it (`PlayerGraph::plan`): each wanted node takes the next slot with the same filters and options, and its changed values must be live. Live options: eq (all four), hue `h`, gblur `sigma`/`sigmaV`, denoise (hqdn3d, all four strengths), deblock `filter`, deband thresholds and `r`, convolution (every option; the matrix is sent bare, the graph quotes it), lut3d `interp`, reframe's crop `x`/`y`. Not live: sharpen (unsharp has no commands), transform, pad, crop size, deinterlace, frameBlend, the lut3d file. Anything else rebuilds the graph (`vf add` with the label).
- **Neutral nodes and pass-through.** `VideoNode::neutral`: eq at its defaults, hue 0, gblur sigma 0, sharpen amount 0, denoise all 0, transform without a turn or flip, convolution with identity matrices (deblock, deband, deinterlace, reframe, frameBlend and lut3d have no neutral value). A switchable node (one FFmpeg filter with timeline support that keeps size and rate: eq, hue, gblur, sharpen, denoise, deblock, deband, convolution, lut3d) is switched to pass-through live with FFmpeg's generic `enable=0`, so it costs no processing. A node a plugin sets neutral or leaves out (`[]` included) keeps its slot as pass-through, and a neutral node without a slot is not added: a slider dragged through 0 (hue, or eq without `keepEq`) never rebuilds and never switches `hwdec`. A neutral node in a graph built from scratch is a pass-through anchor; a chain of only neutral nodes builds no graph at all (no copy-back decoding). A graph with only pass-through slots is removed after `TEARDOWN` (2 s) without changes (`processing_live`), which brings zero-copy decoding back under GPU rendering; a stopped plugin's chain (`disable`), a generated stream's removal and a new file without chains rebuild at once.
- **mpv rebuilds the graph text at every seek.** mpv's lavfi wrapper frees the graph on a reset (any seek) and builds it again from the text it was given (`f_lavfi.c`, `lavfi_reset`), so live values were lost at the next seek before this. After live updates the graph text is rewritten once the changes settle (`SETTLE`, 300 ms without a change): one rebuild, about one dropped frame while playing.
- **Paused preview.** A live update while paused shows nothing until a frame is decoded, and a rebuild makes mpv decode from the previous keyframe ("refresh seek", 0.14–1.5 s). While paused the host shows live updates by stepping forward (`frame-step 2 mute`, 3 right after pausing: mpv holds one or two frames filtered with the old values), at most every `STEP_EVERY` (150 ms), one step at a time; `StatePush` ignores the momentary `pause=no` of a step (`Processing::stepping`). A rebuild while paused is made at once unless one was made within `SETTLE`; then it waits for the settle. At the settle the picture goes back to where it was paused (`seek <time> absolute+exact`, sent before the rebuild so mpv makes no refresh seek of its own), unless someone moved it meanwhile (`PREVIEW_MOVED`); a user seek or step during the drag makes the next preview step start over from there, and the settle returns there. A step also runs while a rebuild is pending (otherwise each waited for the other). "Play" pressed during a step (mpv is unpaused already, and the step pauses again) is remembered and applied when the step is over (`Processing::pause_request`); a new source or a renderer switch drops it. A step in flight ends even after the video stage turned `backend-uncertain`. At the end of the file the settle's rebuild redraws instead.
- **Decoder frame dropping.** While an owned graph is installed, mpv's `framedrop` is `decoder+vo` (`Processing::decoder_drops`); without one it is back to mpv's `vo`. mpv then skips frames in the decoder while the video is late against the audio (`check_framedrop`), instead of filtering every frame and dropping most at the output: 4K60 eq+hue+gblur 8.6 → 27 fps with it alone, A/V offset 5.6 s → 37 ms. A chain that keeps up drops nothing (4K eq: 60 fps, 0 drops).
- **Processing size.** The graph runs at min(source, shown size × video zoom) (`processing_live::factor`): the graph output's display size at full size (from `video-params`, a quarter `rotate` swapped, through the chain's transform/crop/pad; the container's size before the decoder runs) fitted into the video area's physical size, times max(dw / w, dh / h) of the source (the scaler scales stored pixels: HDV 1440×1080 shown 1920 wide needs 1440·f ≥ the shown width), with an aspect override measured as the picture shown on screen over the graph's own output (a widened picture shows more pixels per stored one) (`render_target::Request::area`; keep fits, stretch and fill cover; an aspect override reshapes), times the view zoom, rounded up to quarter steps of the source, never above 1. Below 1 a `scale@vs` (bilinear; bicubic dropped frames at 4K) goes first in the graph, after the last deinterlacer (whole fields), and the spatial options of the nodes after it are scaled: gblur sigma, unsharp matrix size (odd, at least 3), deband range (at least 1), deblock block size (8 at full size, at least 4); strengths, colours and convolution matrices are not. A new size waits until the view held for 500 ms after a run of changes (a border drag) or 150 ms after a single one (full screen, maximize) (`Retarget`). Only while a graph acts; without filters nothing changes. `processing.state()` reports `videoScale: { factor, budgetSteps }` (additive).
- **Budget fallback.** While playing, a graph whose decoder drops more than 15 % of the frames (`decoder-frame-drop-count`, mpv's drops while the video is late against the audio; the output's own drops have other causes) in two 2 s windows in a row steps the size down a quarter, twice at most; 15 windows in a row at or under 1 % (30 s) step it back up, and a step down right after a step up doubles that wait (up to 16×), so it does not swing (`Budget`; `videoScale.budgetSteps`). A new source starts at the shown size.

Measured (headless, this machine, 2560×1440 output, so 4K runs at 0.75):

| 4K60 | before | after |
|---|---|---|
| eq+hue+gblur σ3 | 8.6 fps, A/V 5.6 s behind | 60 fps, 0 drops, 4.2 cores |
| unsharp 7×7 (la 0.5) | 57.7 fps, 23 drops (8.6 in the investigation) | 60 fps, 0 drops |
| hqdn3d | 8.2 fps | 24 fps at 0.75; 60 fps after one budget step (0.5) |
| paused slider step (eq on eq+hue, +gblur) | 0.72 s, 0.65 s | 62 ms, 48 ms (+ up to 150 ms throttle) |
| eq crossing 0 while paused (eq+hue+gblur) | 0.61 s | 53 ms |
| eq-only chain crossing 0 under GPU rendering (`hwdec` switch emulated) | 0.24–0.50 s to show, stalls up to 277 ms | 55–69 ms, no stall |

1080p sources play at 60 fps before and after; paused steps 0.63 s → 63 ms.

## 4.2 Rendering diagnostics: what reaches the screen (0.5.1)

mpv's counts stop at the renderer. `stats().framesShown` is the frames the video renderer produced and `framesDropped` is mpv's `frame-drop-count`. Neither sees frames lost after rendering: the UI took only the newest frame from `FrameSlot`, a vsync was missed, or a draw repeated the old picture.

- **Presented counter** (`render_target::Presentation`, owned by `renderer::Render`). It counts every draw of the main window, and the draws that show a new video frame:
  - GPU rendering: the `vestra-gpu-render` notifier reports `Draw::Begin` / `Draw::End { copied }`.
  - Software rendering with femtovg: the window's rendering notifier, where a new picture was set by `show_frame` since the last draw.
  - Slint's software renderer, which has no notifier: winit `RedrawRequested`, without draw times.
- `stats().presentedFps` is the new frames over the last second (`null` without a window or in the first second). `stats().video.decoding` is `"hardware"` or `"software"`, from `hwdec-current`.
- **`VESTRA_FRAME_LOG=1`** prints one stderr line per second (headless runs too: there `ticks` and `tick` time each loop pass after its wait, the other columns stay empty or `-`, so start-up work such as starting the installed plugins can be measured without a window):
  `vestra frames: produced P shown S (p/s fps) presented N redraws R refresh 60.0 Hz ticks T tick max A mean B ms render max A mean B ms set max A mean B ms target WxH`
  - `produced`: frames the renderer made (software sequence plus GPU publishes).
  - `shown`: frames the UI took (software) or copied into a window (GPU).
  - `presented`: main-window draws that showed a new frame. `redraws`: draws that repeated the old picture. Under Slint's software renderer (no rendering notifier) the window's one winit event hook counts each redraw it dispatches (`Host::bind_window_events`, `video::count_winit_draw`); before 0.5.15 a separate hook did, which the shell's hook replaced, so both stayed 0 there.
  - `refresh`: the refresh rate of the window's display (`platform::window_refresh`, winit).
  - `ticks`: host 16 ms ticks that ran.
  - `tick` / `render` / `set`: the longest and mean milliseconds on the UI thread for the tick body, one window draw (including the new picture's texture upload; `-` under Slint's software renderer) and handing a picture to the video area.
  - Then (0.5.2) the software renderer's stages: `mpv: calls C resize-only T resized Z copied K updates U took max A mean B ms work max A mean B ms dropped D delayed L`: mpv render calls; those for a new size only (no new frame); calls at another size than the previous one (a new buffer and texture each); frame buffers copied because the UI still held them; mpv's new-frame updates; the time of one call, and the work in it; and the growth of mpv's `frame-drop-count` and `vo-delayed-frame-count` (`-` when mpv reports none). mpv waits inside the render call until the frame's display time (`MPV_RENDER_PARAM_BLOCK_FOR_TARGET_TIME`, on by default; `render.h`), so `took` is about one frame interval while playing (16 ms at 60 fps) and says nothing about load; `work` is the call less that wait (mpv's render and conversion into the buffer; measured 4–6 ms for 4K60 H.264 through `d3d11va-copy` at every target from 780×554 to 3840×2160 on the Windows test machine, 2026-10-27). `work` near the frame interval means the render thread is the limit; fewer `updates` with `work` small means mpv itself delivers fewer frames (decoding or its own timing).
  - Where the main window is paced (Windows, below; 0.5.2), the line ends with `pacing: moves M held H eager E close C refused F skipped K late max A ms paint max A mean B ms`: pointer moves over the main window; redraw requests held for a vertical blank; draws made at once because the clock had stopped (off the display's phase); draws less than half a refresh after the previous one; pictures that waited in the frame slot because the previous one was not drawn yet; vertical blanks the UI thread was too busy to take (busy for a whole refresh); the longest a blank waited for the UI thread; and each draw dispatch until winit's next callback (Slint's draw plus `SwapBuffers`, which waits for the display). Then `ui: turn max A timers max A cursor max A pre max A mean B ms pointer max A mean B ms other max A ms`, the UI thread's time between winit's callbacks by what started each stretch: one whole loop turn (first callback to the wait); Slint's timers (the host tick among them); a pointer move (Slint only stores it); a draw request's preparation, from its callback to Slint's `BeforeRendering` (`pre`; `paint` then counts from `BeforeRendering` to the next callback, that is the draw and `SwapBuffers`); the stretches in which Slint processed the coalesced pointer moves (hit testing, hover changes and their callbacks and `if` elements: Slint does this right before the next draw or other event, or when the loop is about to wait, so `pointer` is a part of `pre` or of `other`); any other window event. Posted closures (`invoke_from_event_loop`) count with the stretch they land in. A `turn max` far above `paint max` with `tick max` small means UI work outside the host tick and the draw, which `pointer` and `other` then locate.
  - With it, each shell preparation also prints `vestra shell: N change(s), M panel(s), C compiled, prepared in X ms (ready|failed)` (M counts sidebar placeholders, C the panels in the shell; a change that leaves the compiled set alone does not compile, and a switch to a tab outside it logs 0 changes, [sidebar-tabs.md](sidebar-tabs.md)). Mounts and unmounts queued while one waits its 32 ms are prepared together, in one compile of the shell (`prepare_mount_tick`); at start-up a queued mount waits up to 400 ms (`STARTUP_MOUNT_GATHER`) for a built-in that declares `ui.mount` and is still activating, so that the built-ins' panels come in one compile. A batch that fails to compile is retried one change per tick, so one bad component fails only its own mount.
  - Start-up work kept off single ticks (2026-10-26): the installed plugins start from a queue, at most about 25 ms of process spawning per tick (`START_BUDGET`, logged as `vestra packages: N started in X ms, M to go`), built-ins first and then the others, each in id order (2026-11-02: in id order alone the built-ins, `vestra.*`, waited behind every third-party plugin, about 20 s at 2000 plugins), and each `settings.register` compiles its page alone on the `settings-check` thread, the reply waiting for it (8 pages at 60–160 ms each used to run on the UI thread). The UI tick reads the command registry's revision only; the menu tree is built when it changed while the menu is open (a snapshot per tick took 20 ms at 2000 plugins). Starting one queued plugin reads its own catalog record, and running plugins and plugins in standby are indexed by id, so the start-up queue is linear in the number of plugins.
  - The Options window (2026-11-03) is compiled when it opens and again only when its set of page sources changes (a page added, removed or registered with other files). A plugin woken from standby that registers its recorded page again with the same files writes only the changed values into the open window and moves its row if its title, category or order changed; its callbacks follow the new generation (each reads its page's owner when called). A recompile while it is open builds the new component tree inside the same native window (`view::replace_shell`), so it neither closes nor moves, resizes or flashes. The `settings-check` compile stays: it answers a broken page's `settings.register` with an error, so one bad third-party page cannot break the shared window, and it keeps 60–160 ms per page off the UI thread; the window's own compile on opening is the only compile on the open path.
- **Reading a line:**
  - `produced` below the source rate: the render thread is the bottleneck (decode, copy-back, mpv software render).
  - `produced` at the source rate but `shown` low: the UI thread is busy (see `tick`, `render`, `set`).
  - `shown` ≈ `presented` ≈ `refresh`, below the source: the display's refresh rate is the limit.
  - Many `redraws` with `presented` about half the source: vsync halving.
- **`VESTRA_RENDER_TARGET=WxH`** (for example `3840x2160`): the software renderer draws every frame at this size whatever the window (even sides, at most 3840x2160), and the picture is scaled into the video area. It reproduces the per-frame cost of a large display on a small screen; read it with `VESTRA_FRAME_LOG=1`.
- **Redraw pacing on Windows** (`frame_pacing.rs`): Slint's winit backend paces redraws there with a 16 ms timer that is not tied to the display, so the main window draws at the display's vertical blanks instead (a `vestra-win32` clock thread wakes the UI thread; macOS keeps Slint's display link). `VESTRA_FRAME_PACING=slint` turns this off for comparisons. Only a change while the window is idle draws at once; the clock keeps running for 100 ms after the last draw (0.5.2), so during playback a UI change (a hover in the context menu, the seek bar's thumbnail) waits for the blank with the next picture instead of drawing between two blanks (two draws in one refresh, the second waiting in `SwapBuffers` for the next blank while the picture after it waits too). The clock follows the display the window is on: a `Moved` or `ScaleFactorChanged` of the main window makes its next wait check the window's display and reopen the clock when it changed (0.5.15; before, the check ran every 64th wait, about a second at 60 Hz), and every 64th wait still checks for a display change without a move. When the new display's clock cannot be opened, the clock stays on the old display's blanks and one `frame pacing:` line says so (once until an open succeeds again).
- **Backend threads wait for events** (0.5.15): the software render thread blocks until mpv's update callback, a new render target (`render_target::Shared::set_waker`) or the stop wakes it (before: a 5 ms poll, about 200 wake-ups a second); the control worker blocks on `backend::Wake`, woken by a command (`backend::Commands::send`), mpv's wake-up callback (new events), the stop and the render thread leaving GPU rendering, and otherwise sleeps until the next `source.state` push (100 ms) or audio device check (1 s). While something it serves ends without an event (`Sources::polling`: a source resolution, a cover art listing, a generated stream; `Geometry::polling`: the orientation being prepared from mpv's properties; a frame or keyframe step landing; a full batch of 32 commands) it still sleeps 2 ms per turn with `thread::sleep`, as before (not a condvar timeout, which Windows rounds up to the timer tick, about 15.6 ms). Idle in a headless run (Windows, 2026-10-31) the process went from about 2300 to about 340 context switches a second.
  - **UI changes join the next video frame** (0.5.19): while a video plays (a picture set within 60 ms), a draw owed only for a UI change (no new picture) waits at the blanks for the next picture and is drawn with it, up to 50 ms; not after input within 250 ms (hover feedback stays at the display's rate) and not while Slint animates. An owed draw is drawn between blanks (`overdue`) only while no blank arrives. In full screen each draw is a present shown at once (independent flip, the panel following the presents), so a UI change's own present between two video frames had moved them off their blanks (about 11 extra presents a second, displayed time p99 31–36 ms on the 2560x1600 panel). The frame log's counts segment ends with ` folded N folded-late M` (blanks at which a UI-only draw waited; draws that carried such a change and ended past the next blank). `VESTRA_FRAME_FOLD=0` turns folding off for comparisons. Open: in full screen about 1 % of video frames still show for two blanks ([history](../process/rounds/history.md#4-open-topics), open topics).
- **Full screen on Windows** (`platform::fullscreen_resized`): a full-screen window is kept one pixel taller than its display, because a window that covers the display exactly can be switched by the driver or system to the panel's native variable-refresh timing, which blanks the display for up to seconds. `VESTRA_FULLSCREEN_MATCH=shorter` (one pixel short) or `=exact` (winit's rectangle; the switch for Independent Flip tests) for comparisons; a value other than the default is logged once. The extra row goes past the bottom edge; where another display lies directly below (the row would show there; `MonitorFromRect` of the strip), past the top, right or left edge, the first with no display beyond it, and with displays on every side the window is one pixel short instead (`vestra-win32::unmatched`). Only a window that covers its display exactly is changed, so a window already off by the pixel (a main window rebuilt at the old window's size) never grows.
- **Software frame buffers** (`render_target::BufferRing`): the renderer reuses four frame buffers round-robin; a new zero-filled buffer per frame cost ~20 ms at 3840x2160. The frame log's `copied` counts buffers still held by the UI when they came round (copy-on-write; data for a fifth buffer). While nothing is loaded (the session's `empty` phase: closed or never opened) the ring drops its buffers, so all are freed except what the frame slot or the UI still holds (the last picture; the rest is up to three 25 MB frames at 3840x2160), and the renderer draws nothing (the video area shows the backdrop), so a resize allocates no frame; an update mpv signals meanwhile is drawn once something is loaded.
- **Video texture on Windows** (`vestra-video-texture`): with software rendering in an OpenGL window, each picture is uploaded into one reused texture before the draw, instead of a new image per frame (femtovg makes a new texture per image and uploads it twice).

## 4.3 Render mode, driver denylist and crash guard (0.5.13)

The renderer pair (libmpv on the GPU with femtovg/OpenGL windows, or libmpv's software renderer with Slint's default windows) is decided once at start by `playback::render_mode::decide` from facts `host::rendering::startup` gathers; first match wins:

1. headless → software (`headless`); no GPU renderer on this system (`platform::GPU_RENDER`: Linux today) → software (`no-gpu-backend`);
2. `VESTRA_RENDER=cpu|software|gpu|auto` (`VESTRA_SOFTWARE_RENDER=1` is `cpu`) → that mode (`env`; `gpu` overrides the two checks below, with a `render:` note);
3. the saved preference `software` (`render.json` in the application data directory) → software (`preference`);
4. the crash guard (`render-state.json`, `playback::render_state`): `attempting` is written before GPU rendering starts (on Windows since 0.5.19 also before CPU mode's Direct3D 12 windows) and `ok` once it ran 5 s, gave up on its own or the player quit; a start that finds `attempting` records `crashed`, and GPU rendering stays off (`previous-crash`) until the adapter, its driver version (macOS: the system build) or the player version changes, or for 7 days (Firefox's `DriverCrashGuard`). The adapter is the one the mode uses (0.5.19: `VESTRA_GPU_ADAPTER`, else Windows' per-app order; the file's `schema: 2`; 0.5.23: GPU rendering's adapter by the hybrid-laptop default below, CPU mode's Direct3D 12 windows' adapter by Windows' order, each guarded with its own key, one record per key in the file (`schema: 3`, the current one at the top level, the others in `others`)); a file without `schema` was keyed on the first adapter and is compared with that until its next write;
5. the driver denylist (`playback::render_denylist`): the rules built into the host (`src/host/render-denylist.json`, Chromium's `software_rendering_list.json` fields) merged by id with `<app data>/render-denylist.json`, matched against the adapter GPU rendering uses (`platform::gpu_adapters`: the adapters and the indexes of GPU rendering's and CPU mode's Direct3D 12 windows' adapters; Windows: DXGI `EnumAdapters1` order, `EnumAdapterByGpuPreference` for the high-performance default and `VESTRA_GPU_ADAPTER=high-performance|minimum-power`, and the user-mode driver version from `CheckInterfaceSupport`, in `vestra-win32`; before 0.5.19 the first adapter; a Direct3D 12 window rule for CPU mode against that mode's adapter) → software (`denylist`; on Windows the message points to Settings > System > Display > Graphics);
6. otherwise GPU (`default`).

Denylist rules that hold are logged even when an earlier step decided. A rule with action `software-windows` also gives CPU mode Slint's software window renderer instead of OpenGL, whatever decided the mode, unless `SLINT_BACKEND` is set; it is matched against every adapter with a GPU of its own (OpenGL windows may draw on another GPU than the first), and `VESTRA_RENDER=gpu` does not override it (`cpu` rules are matched against the first adapter only) (the built-in `amd-780m-white-opengl-windows`: AMD Adrenalin 26.10.1 and later on the Radeon 780M draws OpenGL windows white). On Windows `software-windows` rules do not rule GPU mode out (its windows are wgpu, below). `renderer::Render` holds the effective mode and its reason (`pending` until the render thread installs GPU rendering; `init-failed`, `window-fallback` after a fallback), read together by `Render::now`.

Plugins (SDK 1.5.35): `plugin.app.system()` adds `renderingReason { code, message }`; `rendering.state` (no capability) reports the mode now and why, the saved preference, the next start's mode and reason, `restartPending` (the next start's mode differs from the one this run started with) and whether GPU can be chosen (`gpu { available, reason }`); `rendering.setPreference` and `rendering.restart` need `rendering.manage` (risky). A preference is saved at once and applies at the next start, restart or not. `rendering.restart` starts the player again with `--vestra-restart PID` (it waits up to 20 s for this player's instance lock, never hands files over, and runs on its own if the lock does not come, as any launch that cannot claim it; it refuses `rendering.restart` for 30 s, `busy`, so a plugin cannot make a restart loop), this run's `--plugin` directories and `--silent`, and the current local file with `--vestra-resume SECONDS:paused|playing` (`host.resume`: the first open of exactly that path takes the old pause state into its intent and loads with mpv's per-file `start=`, `source_backend::resume_claim`; any other first source drops the resume point; it is taken only once the session admits the source change, so a refused open keeps it), then quits as Quit does. The crash guard is an `Armed` value dropped when `main` returns by any path, so a start that fails with an ordinary error is not counted as a crash.

**Plugin shaders' crash guard (0.6.3).** The same file keeps a record for plugin shaders (`shaders`: `state`, the GPU-rendering key, `at`, the manifest ids of the plugins whose shaders were on, `crashes`, `skipped`; no paths). The UI thread follows the plugin shader lists (`video.shaders.set`, or `video.render.set` with `shaders`; `capabilities::processing_video` → `host/diagnostics.rs`) and arms the record (`applying`) only while they are drawn: a moving video track plays (`source.state` `hasVideo`, phase `ready`, not paused) and 2 new frames were presented since the list changed. It writes `ok` after 10 s of such playback (a new source starts the 10 s again), and at once when playback pauses or stops, the video track goes (audio only), every list empties (cleared, released, the plugin stopped or parked), the player quits, or the Windows session ends (`WM_QUERYENDSESSION`/`WM_ENDSESSION` through `vestra-win32::on_session_end`, which writes the `exit:` line once at `WM_ENDSESSION` TRUE and from then on writes no `applying`; a cancelled end logs one `session:` line and arms it again (each top-level window gets the messages: the first acts, a cancel only while an end is under way; a `WM_QUERYENDSESSION` that no `WM_ENDSESSION` follows leaves the guard disarmed for the run, which can miss a crash but never blames shaders for one); macOS: a logout or shutdown asks the app to quit, which ends the event loop like Quit). A shutdown, logoff, update restart or Task Manager kill while paused or idle is therefore not a shader crash; a process crash during the first 2 frames of a new list is not caught. **A GPU renderer failure before a new list is verified (0.6.4).** A first-use compile that hangs, or a first frame that loses the device, fails before any frame is presented, so the guard never armed. After a plugin shader list changes (any non-empty list) it is therefore untested until it is verified: the capability layer numbers each shader request (`guardSeq`: `video.shaders.set`, `video.render.set` with `shaders`, `video.render.release`; a plugin cannot set it) and the control worker reports each one processed, its list written to mpv or not (the same merged list, `limit`, `unsupported`: `backend::guard_processed` → `Render::shaders_processed`), so a render with an older list never verifies a newer one; then an mpv render call has to start after that while the source has a video track, and its frame has to finish on the GPU (its `ready` fence value reached, `vestra-gpu-render`'s `Handle::progress`; a released fence, `u64::MAX`, proves nothing). Render calls without a video track move the mark (mpv runs user shaders on video only); paused redraws count. A new source, video size (`video-params`) or output size (a new ring: full screen, a resize) makes the lists untested again, since `//!WHEN` hooks (Anime4K's) compile when their size condition first holds. The untested plugins are handed to the writer only while the source has a video track, so a device lost while idle or on audio only (a plugin that sets its list at start-up) is not theirs. Caught in that time: a device loss, a watchdog stall of either kind (the render call that compiles does not return within the CPU-time limit, or the first frame's fences stop moving), and mpv's own Direct3D 11 device removed (the in-process software fallback, `backend.rs`, which does not restart). Each calls `persist_shader_guard` → `ShaderWriter::gpu_failed` on the thread that noticed, which writes `applying` for the untested plugins before the restart, so the restarted (or next) player starts with plugin shaders off (`previous-crash`, the same one-run / two-in-a-day policy); not while the session ends. Not caught: a failure after the first frame finished, before the guard arms (2 presented frames while playing), or a process crash in that time. From a GPU renderer failure on, the writer takes no request (a `lost` flag): the UI thread, which ticks until its event loop ends, cannot settle the record to `ok` behind the restart. A request the worker never processes keeps the list untested until the next one, so a failure may be blamed on it for nothing, never the other way round; macOS's renderer does not report progress (no device-loss restart there), so nothing is untested there. A new list from the same plugins while armed writes nothing (a slider that sets lists as it moves); every other write goes through one thread of its own (`ShaderWriter`, the newest request wins), never the UI thread, except at quit and at the session's end, which wait for it; a device-loss restart (`restart_player`) waits up to 2 s for a pending write, so an `applying` handed over just before the loss is on disk when the restarted player reads it. A start that finds `applying` (the process died, or the windows' device was lost and the player restarted) records `crashed`; a GPU-rendering start that then finds `crashed` for its key keeps plugin shaders off: after one such run for this start only (`skipped` is written, the next start applies them again); **after a second such run within a day, until the GPU adapter, its driver or the player version changes, or for 7 days** (the escalation keeps a shader that crashes every time from crashing every other start). While they are off, non-empty lists are refused with `previous-crash` (message names the plugins and when they apply again; clearing still works), the plugin's handle turns `failed` through the usual reply path, and the OSD says once per run "Plugin shaders are off: the player ended unexpectedly while they were on" (at the first refusal, once a window exists). Lists are followed as requested, so a list the worker then refuses can arm the guard for nothing, never the other way round. Players before 0.6.3 ignore the record and drop it when they rewrite the file.

**Host log (0.6.3).** A release build with windows and no `--plugin` writes a few lines to `<app data>/logs/host.log` (Windows `%APPDATA%\Vestra\logs`, macOS `~/Library/Application Support/Vestra/logs`, Linux `$XDG_DATA_HOME/vestra/logs` or `~/.local/share/vestra/logs`): 512 KB, then renamed to `host.log.1` (one older file), like mpv's `--log-file`. It sits beside `restart.log` on purpose: both are the player's own files under its application data, where a user or a bug report finds them together. `VESTRA_LOG_FILE=<path>` chooses the file in any build (empty: none). Two players writing one file (only with `VESTRA_LOG_FILE`, or a player that could not claim the single-instance lock) interleave lines; a roll-over by one leaves the other writing into `host.log.1` until its own, and a rename that fails never truncates (writing goes on, and stops at twice the cap). A failed rename, a failed reopen and the stop at twice the cap are each said once on stderr (`host log: …`); a file that cannot be opened again is retried at the next line, and one line says when it opens again; the player runs on either way. `logged!` (`diag.rs`) writes the line to stderr as `diag!` does and to the file with UTC time and process id: the start line (version, build, OS), the `render:` decision and fallbacks, every adapter and the one the mode uses, what the crash guards found at start (`GuardFile::recover`: GPU rendering or the Direct3D 12 windows died while starting, plugin shaders were on), device losses and the restarts they cause (the restart lines of `host/restart.rs`, which say when the second loss within a day turns GPU rendering off; never the command line, which names the file played), `rendering.restart`, plugin shader list changes (manifest id, handle with the plugin's id reduced to identifier characters, file count), `host.error` (the code; the message, cut at the first path, link, quoted word or file name, only for codes known to carry no user data), a panic (thread, source location, redacted message), the exit line (`normal`, `restarting`, the session's end, or the event loop's error), and every 60 s the memory line (Windows: the process's private bytes, the system commit charge and limit from `GetPerformanceInfo` as Task Manager shows them, physical memory load; `vestra-win32::memory_status`; macOS and Linux none yet). Each line is one unbuffered write, so a process killed by the C runtime (0xc0000409) loses nothing written before; a missing exit line marks a run that did not end normally.

- **Windows (0.5.14, M3)**: GPU rendering (libmpv on Direct3D 11 into textures that femtovg-on-wgpu (Direct3D 12) windows show, `WindowKind::Wgpu`) is compiled in but opt-in: `auto` resolves to software (reason code `default`, "experimental and off until it is turned on"); the preference `gpu` (the Video menu switch) or `VESTRA_RENDER=gpu` turns it on at the next start, then the crash guard and `cpu` denylist rules apply as on macOS. With `auto` the crash guard and `cpu` rules are not looked at (only a `software-windows` rule, for the windows). CPU mode's windows were femtovg on OpenGL, named explicitly (with wgpu compiled in, Slint's default would be femtovg-wgpu), as on main, up to 0.5.18 (0.5.19: Direct3D 12 windows first, below). An OpenGL `software-windows` rule changes only CPU mode's windows there (wgpu windows do not use the driver's OpenGL). A lost window device records a loss in the crash guard and restarts the player (`host/restart.rs`); the second loss within a day turns GPU rendering off like a crash, and the new player is then started with `VESTRA_RENDER=software`; a player restarted less than 30 s ago does not restart again. `VESTRA_WINDOW_RENDERER=gl|software` (testing) chooses CPU mode's windows; `=wgpu` allows a software adapter.
- **Windows GPU path polish (0.5.19)**:
  - **CPU mode draws in Direct3D 12 (wgpu) windows** where Direct3D 12 is available and nothing keeps it from it (`WindowKind::Wgpu` for CPU mode): software video goes into one reused texture per window (`vestra-video-texture`'s wgpu twin, one upload per frame) and the windows present with the flip model and vsync instead of GDI (OpenGL femtovg, or Slint's software renderer through softbuffer). OpenGL windows, or Slint's software renderer under an OpenGL window rule (the AMD 26.10.1 white-window rule now matters only there), remain the fallback (`Decision::fallback_windows`) when the Direct3D 12 device or Slint refuses (a remote session's adapter, no Direct3D 12), when a Direct3D 12 window rule holds, or when the crash guard holds; `SLINT_BACKEND` and `VESTRA_WINDOW_RENDERER=gl|software` still choose them. The guard is armed for these windows too and settles once the first video picture was shown, or after the main window's first 3 draws when no source is being opened (5 s at the latest; only a crash while they are made and take their first picture counts); when it holds, CPU mode uses the fallback windows and a `render:` note and the reason's message say so. Their device's loss restarts the player as in GPU mode. The `render:` line names the windows, and in software rendering `renderingReason.message` (and `rendering.state`'s `reason`) ends with them ("…; the windows draw with Direct3D 12 (wgpu)").
  - **Denylist rules for Direct3D 12 windows**: `"action": "software-windows"` takes `"window_api": "opengl"` (the default, as before) or `"direct3d12"` (matched against the adapter GPU rendering uses). A Direct3D 12 rule turns GPU rendering off on Windows (`VESTRA_RENDER=gpu` does not override it) and keeps CPU mode on OpenGL windows; it is looked at whenever Direct3D 12 windows would be used, so also with `auto`. No such rule is built in.
  - **The render thread no longer waits on the CPU for each frame**: only the GPU-side fences order the frames (a window's queue waits for `ready`, mpv's device for `done`); at most two frames are in flight, a ring generation and the thread's end wait for mpv's last frame, and a removed device is asked for after each frame. `VESTRA_GPU_CPU_WAIT=1` restores the wait (A/B). The frame log's `complete` is now timed on a thread of its own, and ` throttled N` counts waits for the in-flight bound.
  - **Watchdog**: `ready` or `done` not moving for 10 s while work is outstanding, or mpv's render call not returning for 30 s, stops GPU rendering like a lost device (both fences released, the loss recorded in the crash guard, the player restarted where it was; the second within a day: software). `VESTRA_GPU_WATCHDOG=<seconds>` (`0`: off); `VESTRA_TEST_GPU_STALL=<seconds>` makes mpv's device wait for a fence value no window signals (hardware test). Inside one render call only the looks at which its thread did not run on the CPU (less than 20 % of a core since the previous look) add to the 30 s; a running look pauses that clock without resetting it, so a driver that polls below 20 % of a core still stalls (one that polls harder does not, until the 300 s), while a thread compiling shaders (running almost all the time) stalls only after 30 limits (300 s); mpv compiles a user shader inside the first render call that needs it, and Direct3D 11's compiler took 50 s for the shader upscaling plugin's ArtCNN C4F16 and several minutes for C4F32 (host 0.6.4; before, the 30 s render-call limit turned that compile into a "device loss", the 0.6.2 report). mpv keeps compiled shaders in `shader-cache` in the application cache directory (`gpu-shader-cache-dir`; `platform::app_cache_dir`: `%LOCALAPPDATA%\Vestra` on Windows, `~/Library/Caches/Vestra` on macOS, `$XDG_CACHE_HOME/vestra` elsewhere; `VESTRA_SHADER_CACHE` to override, empty for none; a cache that cannot be set up is logged and playback goes on without it), so a chain compiles once, not at every start (ArtCNN C4F16: 52.6 s cold, the next start draws at once). After a device loss (or a stall) every window of the process is cloaked at once, from the thread that noticed (`vestra_win32::cloak_process_windows`: no window message, so it works while the UI thread is stuck; the count goes to restart.log), and the new player is started. The old player then gets 5 s from the end of its event loop (`restart::event_loop_ended`; clean teardowns take 1 to 5 s) and at most 15 s from the restart (a UI thread that never leaves the loop), both under the 20 s the new player waits; then it logs the teardown step it was in (`restart::teardown_step`) and terminates itself with `TerminateProcess` (`platform::exit_now`: no DLL detach, which a stuck driver could hang). Up to host 0.6.3 the only limit was 15 s, which a teardown stuck in the driver used in full behind a black, unresponsive window. Slint's femtovg-wgpu renderer keeps drawing the frames already asked for until the loop sees the quit the loss asked for, and femtovg makes a uniform buffer with `wgpu::util::DeviceExt::create_buffer_init` whenever a draw switches between a layer texture and the window; on a lost device that buffer cannot be mapped and wgpu panics on the UI thread. Since host 0.6.5 `main.rs` runs the event loop through `restart::run_through_loss`: any panic out of it once `platform::window_device_lost` is set (a lost device, or a watchdog stall, which sets it with the device healthy) ends the loop like the quit, restart.log and the host log say so (`render: the event loop panicked after the GPU device loss (see the panic: line); …`, after the panic hook's `panic:` line, which names what panicked), and the usual teardown follows (`exit: restarting`, plugins told `quit`); a panic while it is not set still ends the process. Not covered: a `create_buffer` that fails with out-of-memory on a healthy device. wgpu-core treats that as a non-fatal error (`Device::handle_hal_error_with_nonfatal_oom`, as for textures, samplers and query sets), so the device is not lost, `window_device_lost` stays false, no restart starts, and femtovg's `create_buffer_init` panic still leaves `main` as before. Up to host 0.6.4 that panic left `main`: the teardown never ran, plugins read `host-lost`, and the host, still held by the UI thread's thread-locals (`FRAME_SINK`), dropped only at process exit, after Windows had ended its other threads, so joining one panicked again in std (`threads should not terminate unexpectedly`, a consequence, no fix of its own). Note that wgpu-core marks its device lost on an `E_OUTOFMEMORY` from Direct3D 12 as well as on a removed device (`Device::handle_hal_error`) in most calls (submits, presents, waits, pipelines, bind groups), but not when it creates a buffer, texture, sampler, query set or acceleration structure (`handle_hal_error_with_nonfatal_oom`: only that resource fails, see above), so a loss with no TDR in the System log can be memory exhaustion (video memory over budget, or the system commit limit).
  - **Frame pacing folds UI changes into video frames** (§4.2).
- **Hybrid laptops (0.5.23, user ruling 2026-10-31)**: GPU rendering uses the high-performance GPU (DXGI `EnumAdapterByGpuPreference`, `HIGH_PERFORMANCE`) unless the user set a preference for Vestra in Windows Settings > System > Display > Graphics (`HKCU\Software\Microsoft\DirectX\UserGpuPreferences`, the value named by the executable's path, `GpuPreference=1|2`; `0`, "Let Windows decide", is no preference), which Windows' order then follows; CPU mode's Direct3D 12 windows follow Windows' order; `VESTRA_GPU_ADAPTER` overrides both (an unknown value is ignored with a line). Each mode's adapter is resolved once at start (`platform::gpu_adapters` → `AdapterPick`, opened by LUID), and the high-performance default falls back to Windows' order when it cannot be resolved. The start-up `render:` lines say which adapter each mode uses and why.

## 4.4 Video upscaling (0.5.16)

Capability `video.upscaling` (not risky, residency live): `video.upscaling.state` and `video.upscaling.set { enabled }` (SDK 1.5.37, `plugin.video.upscaling`). The host adds its `rendering.state` and forwards both to the control worker (`playback/upscaling.rs`):

- **The system's check** runs once, on its own thread, at the first request (it wakes a sleeping discrete GPU): `platform::upscaler_probe`. Windows: every NVIDIA adapter (`0x10DE`) with a user-mode driver of at least `x.x.15.3000` (530) is asked through `vestra_win32::video_super_resolution`: a Direct3D 11 device with video support on that adapter, a 1080p → 2160p video processor, `VideoProcessorGetStreamExtension` with NVIDIA's PPE GUID; supported when it succeeds with a non-zero value (VLC's check; setting the extension proves nothing, AMD accepts it too). Elsewhere `platform`.
- **Availability** (`upscaling::check`, first failure wins): the check (`platform`, `no-gpu`, `driver`, `gpu-unsupported`), GPU rendering drawing now (`rendering`, with the advice from the rendering state: turn on Video ▸ GPU Rendering (Experimental) and restart, restart to apply, or why the GPU cannot be chosen), GPU rendering on a GPU the check passed for (`adapter`: the window device's LUID, `platform::gpu_render_adapter`; on a hybrid laptop choose the high-performance GPU in Windows Settings), and decoding on that GPU (`decoding`: mpv's `hwdec` is a copy-back mode or `no`, or `hwdec-current` is not `platform::UPSCALER_HWDEC`, `d3d11va`). `set(true)` fails with `unsupported` unless the reason is `decoding` or GPU rendering is still starting; such a request is kept and takes effect when the reason passes.
- **The filter**: while some plugin asked and it is available, `@vestra-upscale:d3d11vpp=scale=F:scaling-mode=nvidia` is last in mpv's `vf`. F = the display size fitted into `osd-dimensions` over `video-params` (before the filter chain, a quarter rotation swapped), the larger axis, at most 8192 px a side, in hundredths; none at 1 or below (`scale=1` bypasses the video processor). Every 200 ms the worker recomputes it (its `Wake` wait is capped by `Upscaling::due_in` while upscaling is on or a filter is in the chain; the check thread wakes it when it answers); a first filter and a removal are immediate, a factor 2 % or more off waits until it held for 300 ms (a border drag) and replaces the filter in place (`vf add` with the label), and a filter that is no longer last (a plugin's first `@vestra-owned` chain) is moved back. `set(false)` and the last owner stopping (`owner.disabled`) remove it at once.
- **The publish gate**: the filter is never in the chain while the renderer's publish gate is closed (a new source's orientation being prepared, `source_geometry.rs`; `Upscaling::follow_gate`). The gate closing (`source.submit` open/openProvider/restart, or a new load the geometry sees) takes it out at the worker's next turn, and the geometry confirming the output puts it back at once (`due_in` is 0 on either change). Before, the filter could go in while a slow stream started, or stay from the last file; its scaled output never matched the size the gate waited for, and the picture stayed on the last file's frame while the audio played (VestraTube after a local file, RTX VSR on). So on every source change `video.upscaling.changed` briefly reports `requested: false` (and `inChain: false`), and the filter comes back only after the new source's first frames confirmed the geometry: the picture may visibly sharpen a moment after it starts.
- **The gate's evidence and timeout** (`source_geometry::evidence`): the gate reads `video-out-params` after the whole chain, so it opens on the expected size (`exact`), on the expected aspect at another scale when the other orientation's aspect does not also fit (`aspect`: a scaler; a frame still turned by the previous file's orientation filter has the other aspect, a picture within a few pixels of square passes only as `exact`), or, after 2 s, without evidence (`timeout`, with a `source geometry ready … evidence=timeout` line), but only once a frame went through the new chain (`source_geometry::Mark`, with its base taken at the first tick after `vf pre` that sees an output: the output changed from it, playback went back (a seek flushes the chain), or `time-pos` moved forward 0.25 s from where it first moved, since the first move may be the first frame of a video that starts later than the audio, filtered by the old chain), or when the orientation filter before `vf pre` applied the same transform (or there was none and the new one is `null`): then the old chain's frames are already right, so a paused resume of the next episode with a plugin's crop opens without play. The reason for the condition: `video-out-params` keeps the previous chain's values until then: a stream that stalls after its first frame or starts paused after a portrait file must not publish the stale sideways picture. `aspect` is evidence about the shape, not about each frame (a stale frame turned by 180° or flipped, then scaled, passes as the size check let it pass before). The timeout covers what changes the shape after the orientation and is not held back: a plugin's crop, pad or quarter turn (`@vestra-owned`, replayed at FileLoaded), which before kept the gate closed for good. An aspect comparison alone would not cover those, and holding plugin chains back until the gate opens would publish a first uncropped frame.
- **No "active" signal**: `requested` means the filter is in the chain. The NVIDIA app's RTX Video Super Resolution switch must be on; nothing can read it.
- **Hardware test plugin**: `src/tests/hardware/upscaling-probe` (`--plugin`), Video ▸ Upscaling Probe ▸ State / On / Off (Ctrl+Alt+U / I / O); each answer goes to the OSD and the log.

## 4.5 Video primitives (0.5.20)

Plugins own their video algorithms instead of only toggling host features (SDK 1.5.39). No new capability: everything is `processing.video`.

- **Plugin files** (`playback/plugin_files.rs`): a file a plugin names for its processing is checked on the main thread by the capability layer (`capabilities/processing_video.rs`), which has the roots (`Host::image_roots`: the package directory and the data directory, as for images): absolute, inside a root after `dunce::canonicalize` (links and `..` resolved), a regular file of at most 16 MiB; `invalid` outside, `missing` when absent. The playback worker gets the canonical path. The check holds at the time of the request only: it stops a plugin from naming arbitrary paths through the API, but it is not a sandbox (mpv/FFmpeg read the file later, so a plugin can swap it for a link or use a hard link afterwards, and plugins are unsandboxed Node processes anyway). It runs on the UI thread (a canonicalize, a stat and up to 64 KiB of a `.cube` per request), like `ui.image`.
- **`convolution` and `lut3d` nodes** (`effects.rs`): typed, no raw lavfi. `convolution` writes `{i}m='…'`, `{i}rdiv`, `{i}bias`, `{i}mode` per given plane (integers ±1024; square 9/25/49 or odd row/column ≤ 49; `rdiv` 0–256; `bias` 0–65535). `lut3d` takes a `.cube` (header `LUT_3D_SIZE` 2–65 checked by `plugin_files::lut`) and writes `file=` quoted for FFmpeg's option parser (`'…'`, `'` as `'\''`) and escaped for its graph parser (`\ ' , ;`); `[` and `]` are refused because mpv's `lavfi=[…]` ends at an unbalanced bracket. Both are ordinary chain nodes: copy-back decoding, the same graph offline, so snapshots and exports contain them.
- **Shader channel** (`playback/video_shaders.rs`, `video.shaders.set { id, paths }`): any number of plugins, each with handles by id. The capability layer resolves the files and adds `manifestId` and `rank` (`Host::install_rank`: built-in 0, installed 1 with the first-install time, development load 2), which the plugin cannot set. The worker keeps `(tier, installedAt, manifestId, owner, id) → paths` and writes mpv's `glsl-shaders` through `video_render::Options`, the only writer: the render options' own `shaders` first, then the joined channel. At most 16 channel shaders (`limit`). GPU rendering only (`unsupported` in CPU mode; a GPU → software fallback pushes `video.shaders.status` `unsupported` to every handle and clears every list, so they neither count against the limit nor keep plugins resident; plugins set them again once the player draws on the GPU). `owner.disabled` / `owner.parked` remove the owner's lists (if mpv refuses the shorter list, the channel keeps the entries as stale, matching mpv, and every later write leaves them out again); `owner.resources` lists "video shaders". A `libmpv_render` compiler line (`video_render::compile_line`) goes to every holder not yet told for its current list (the render owner and each handle). mpv does not name the file, so the message form comes from everyone whose shaders are on now: mpv's line with one holder, "the player cannot tell whose failed" with several (also when the others were told already, so a good list joining a broken one is never blamed with certainty).

## 4.6 Clip exports: stream copy, progress, encoder options (0.7.6)

`jobs.start` (`playback/media_jobs.rs`) has two clip kinds, both run by the media worker from the snapshot's held lease (`HELD_FILE_INPUT`), with the same job limits (2 per owner, 8 workers, 128 records), cancellation and no-clobber publication of a validated temporary file:

- **`rawMp4` / `processedMp4`** (`media_worker.rs`): the re-encode, frame-accurate (`trim` from the start frame). A raw snapshot input-seeks the held file to the start (`-ss <start> -copyts -start_at_zero` before `-i fd:`): FFmpeg decodes from the keyframe before the start instead of from 0 s (a clip at 2:17 of a 4K60 file: about 4 s instead of about 200 s single-threaded before the first frame), and the copied timestamps keep the normalized source timeline, so the `trim`, the subtitle times and the audio graph are unchanged and the output is the same frame for frame and sample for sample (tested against the from-0 path, also on a TS with a nonzero start time); `facts.preroll` is `keyframe-before-start`. Effects chains are split by node type (user ruling 2026-11-07; `effects::History`, an exhaustive match per node kind, so a new kind must be classified): a stateless chain (eq, gblur, hue, sharpen, deblock, deband, transform, reframe, convolution, lut3d, spatial-only denoise, volume, channels, burned-in subtitles) seeks to the start like a raw snapshot (`keyframe-before-start`); a chain with stateful nodes (temporal denoise, deinterlace, equalizer, treble, dynaudnorm) seeks to 10 s before the start (`HISTORY_SECONDS`, `bounded-history`), after which the frames are those of decoding from 0 s (tested, md5) and the audio is close but not bit-exact (stateful audio filters such as dynaudnorm keep a trace of older input; measured correlation 0.9992, aligned); frameBlend still decodes from 0 s (`source-zero-to-start`): its output frame grid starts at the first decoded frame, so a seek shifts it (measured: 120 of 120 frames differ when the first frame after the seek is off the 60 fps grid). With audio the seek is 1 s earlier still (`AUDIO_WARMUP_SECONDS`: a cold AAC or MP3 decoder writes different first samples), , the seek point is whole seconds (a sample boundary at every integer rate), and the audio graph shifts its timeline so the seek point (less a negative audio offset) is 0 before the resampler (`offline_audio::audio_from`; `aresample`'s `first_pts` counts input samples, so the shift is done in seconds): with the source timeline it padded and held silence for everything before the seek (measured by review: 1.5 GB at 30 min, 3.1 GB at 2 h, and "Failed to compensate for timestamp delta"), and a positive audio offset moves it earlier by the offset; a seek that would reach 0 s is no seek. Only containers whose seek lands on the keyframe at or before the target seek (`seeks_exactly`: MP4/MOV, Matroska/WebM); MPEG-TS seeks by estimate and was measured landing 1.7 s after the target, so TS and other formats decode from 0 s. Video is the same frame for frame (md5). Audio without audio effects is the same sample for sample in MP4; with audio effects the filters get the decoded audio in other chunks after a seek, a sample can round one step differently (measured: at most 1 LSB before encoding), and the AAC encoder turns that into a different bitstream, so the audio matches closely (aligned, correlation above 0.99) but not bit for bit; Matroska times are whole milliseconds, so after a seek the 48 kHz resampler places the first sample up to half a millisecond from where a decode from 0 s puts it (measured: one sample, correlation above 0.99). Processed stills follow the same plan; raw stills keep their plain `-ss`. `encoding` is a closed set (`media_worker::Encoding`, `deny_unknown_fields`): CRF 14–30, x264 preset `veryfast`/`medium`/`slow`, a height ceiling 1080/720/480 (`scale` only when taller, even width), a frame-rate ceiling 60/30 (`fps` only when the probed source rate is higher), AAC 128/192/256 kb/s, `videoBitrate: "source"` (instead of CRF: `-b:v` the source video's bitrate, from the stream's `bit_rate` or the container's minus the other streams', `-maxrate` 1.5×, `-bufsize` 2×; `Refused` when unknown), threads `single` (1, the default) or `auto` (`auto_threads`: half the logical processors, 1–8, so playback and the UI keep their rate). Defaults are the old fixed settings.
- **`rawCopy`** (`media_copy.rs`, SDK `format: "copy"`): no decode or encode. ffprobe reads the video packet flags around the start (windows of 10, 60, 300 s back, then from the file's start; for a video that begins later, its first keyframe, searched forward from the file's start in 10 s steps up to 5 min so each step's lines fit the bounded output) and takes the last keyframe at or before the start, in integer `pts × time_base`. Only presented keyframes count: a `D` (discard) flag, an MP4 edit list's pre-roll with a negative time, is skipped. The container's name (`media_copy::named`) is checked before copying, so a taken name fails at once (publication stays no-clobber). FFmpeg copies with `-ss` = that keyframe rounded down to a microsecond and `-copypriorss 0`, so the backward seek lands on it and nothing earlier is written; `-t` cuts at the requested end (a few frames past it at most, FFmpeg cuts in decode order). Container: `auto` writes MP4 for H.264/HEVC/AV1/MPEG-4 with AAC/MP3/AC-3/E-AC-3/ALAC (HEVC tagged `hvc1`), MKV otherwise; the destination gets that extension (`media_copy::named`). Refusals are `media_worker::Refused`, which the job reports as `outcome.error.code` `unsupported` (every other failure stays `export-failed`): no video stream, a cover image, an external audio track, codecs `mp4` cannot hold, an FFmpeg muxer refusal. Validation decodes the first 3 s (not the whole clip: the packets are the source's), then probes the output's first video packet (must be a keyframe) and the end of its last frame.
- **Range written** (`Outcome::Completed.range`): a copy maps output times to source times through its first packet (the keyframe, `-copypriorss 0`) and reports the earliest presented time of its first 64 packets (an open GOP writes leading frames before the keyframe) and the end of its last frame; a re-encode the start and start + the encoded video duration. `jobs.state` gives them as `outcome.start` / `outcome.end`.
- **Priority**: the FFmpeg that writes a frame or a clip and the validation decode start through `platform::background_tool_command`: `BELOW_NORMAL_PRIORITY_CLASS` on Windows, `nice -n 10` elsewhere (HandBrake and OBS practice), so playback keeps the display rate; probes stay at normal priority.
- **Progress** (`Control::progress`, never backwards for the same total): clip commands write `-progress pipe:1 -stats_period 0.25`; `run_tool` reads `out_time_us` on a scoped thread to EOF (never closing the pipe under FFmpeg) and keeps `(done, total)` seconds; `jobs.state.progress` is `null` until the first frame is written (the first positive `out_time_us`; FFmpeg reports 0 while it decodes up to the start), and for frames; `total`/`total` once published.

## 6. UI state file

`$VESTRA_UI_STATE`, default `ui-state.json` in the application data directory (`platform::app_data_dir()`: `~/Library/Application Support/Vestra` on macOS, `%APPDATA%\Vestra` on Windows; `ui_state::default_path`); headless mode neither reads nor writes it. Contents (`UiState`): the main window's normal frame, on Windows also in desktop pixels (`windowPhysical`, the window placement), and `windowMaximized` (IA-CORE-03: maximized is restored, fullscreen never; a frame off every display's work area opens on the primary one, `view::reachable`), the sidebar width, `sidebarSlot` (visible, detached, active panel, tab order, floating frame; older files' per-panel `panels` entries are migrated into it), the user binding overlay `bindings` (`"<manifest id>/<command id>": [bindings…]`, `[]` means unbound; written through `bindings.set`/`bindings.reset`, capability `bindings.manage`, SDK `plugin.bindings`), `bindingsMigrated` (one-time migrations applied), `appearance` (palette and interface language), `settings` (the options window's last page) and `paletteRecent` (the command palette's recently run commands, newest first, at most 8). Changes are merged and written 1 second later (temporary file + rename), and written once more on exit; an unreadable file is renamed to `ui-state.json.bad` and defaults are used. The first design of the file (before the sidebar slot, appearance and settings) is in [core-ui-design.md §8](core-ui-design.md#8-c8-ui-state-persistence), a historical record.

## 7. File paths and persistence (cross-platform)

- Path canonicalisation always uses `dunce::canonicalize` (`src/host/clippy.toml` bans std's `canonicalize`). On Windows std returns the `\\?\C:\…` form, which Slint's `import` cannot find and mpv and FFmpeg do not necessarily accept; dunce strips the prefix when the plain path refers to the same file, and is identical to std on other systems. When it cannot be stripped (very long paths, reserved names), `composition::import_path` reports an error directly. The "inside the package" check for package paths uses dunce on both sides, so the results agree; when the forms differ, `starts_with` fails, which means refusal rather than letting it through.
- Relative paths inside packages (manifest fields, `.vxp` entry names, file names after directory capture) use `/` on all systems, with one set of rules (`manifest::relative_path`). A `\` in a `.vxp` entry name is refused (the zip specification requires `/`) and is not treated as a separator; directory capture (`package_stage::relative_name`) joins path components with `/`, so `ui\a.slint` on Windows and `ui/a.slint` on macOS have the same digest; a `\` in a Unix file name is refused (it is a separator on Windows).
- Directory persistence barrier: `platform::sync_dir`. Called by the install store after each atomic replacement (`tempfile` persist, `fs::rename`). On Unix it `fsync`s the directory. On Windows: a rename (`MoveFileExW`/`SetFileInformationByHandle`, without `MOVEFILE_WRITE_THROUGH`) is atomic on NTFS (metadata is journalled), but a crash before the journal reaches disk may roll it back, so it calls `FlushFileBuffers` on a directory handle: a directory can only be opened with `FILE_FLAG_BACKUP_SEMANTICS`, and flushing needs write access, so a read-only `File::open` fails with Access denied. Only std's `OpenOptionsExt::custom_flags` is used; no `unsafe` is needed. Both systems return the error to the caller (the catalog has been published but its durability is unknown; the caller queries/recovers instead of redoing).

## 8. Versions

The player has two version numbers (since 0.7.1, user decision 2026-11-03):

| | Player (release) version | Host version |
| --- | --- | --- |
| Where | `src/release.json` (`{ "version": "0.7.1" }`), packaged as `<resources>/release.json` | `version` in `src/host/Cargo.toml` (`CARGO_PKG_VERSION`) |
| What it names | A release of the player: host, runtime, built-in plugins together | One build of the `vestra-host` binary |
| Goes up | On every release | Only when the host input hash changes (`src/packaging/host.mjs`) |
| Seen in | The release tag and notes, `latest.json`, `plugin.app.version` (so the About window, the update check and the store's User-Agent), `minPlayerVersion` checks, the start-up log line | The Windows file version resource, the start-up log line, the GPU crash guard (`render-state.json`) and lazy-activation recordings, which are about the binary |

**Rule: release ≥ host.** A release that only changes built-in plugins raises the release version and reuses the built host, so CI skips the Rust build; a host change raises both. A test (`version::tests`) fails when `src/release.json` is below `Cargo.toml`.

The host reads `release.json` once at start (`src/host/src/version.rs`); a development run finds `src/release.json` through `runtime_paths`. A missing or invalid file falls back to the host version with one log line. The start-up log names both: `start: Vestra Player 0.7.2 (host 0.7.1, <build>) on windows x86_64`.

The Windows `VERSIONINFO` (`FileVersion` and `ProductVersion`) stays the host version: it is embedded in the binary at build time, and one binary ships in several releases. A file version that differs from the product release is normal on Windows; users see the release version in the About window and the update check.
