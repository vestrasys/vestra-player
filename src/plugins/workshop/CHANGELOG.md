# Changelog

## 2.2.38

- The vendored SDK is 1.7.12 (`npm run vendor:sdk`), the version the player now uses: the Tools menu (`@tools`) and the built-in tables of the short context menu. Who must change: nobody.
- **Ask Vestra runs commands** (PROPOSAL §9 step 5; built-in only; capability `commands.run` added). The model now gets the command palette's table from `plugin.commands.list()`, one line per command (id, English label and the shown one, place, keys, state: disabled with its reason, busy, toggle or radio on/off, "asks the user first", third-party with its plugin), sorted so it stays the same while the table does. Left out (doc/architecture/palette-lead.md, "Personal data"): Ask Vestra's own commands, the palette itself, the rows built-in plugins make from the user's data or the media's metadata (Recently Played, audio and subtitle tracks, audio devices, chapters, bookmarks), and any row of a plugin that is not built in whose title or path looks like a file name, a path or a URL. A `command` step names an id of that table; any other id ("There is no command “…”") is refused before any step runs. Commands run through `plugin.commands.run` with the ticket of the palette's run (and `step`/`of` for a request of several steps, for the player's own line "Vestra Player AI · 1/2 · …"); the player checks and confirms (destructive, Close and Quit, the Settings and Plugins menus, every third-party command). Don't Run stops the whole request ("Vestra · Stopped: <command> was not run"); a disabled command fails the step with its reason; busy, gone, the rate limit and an ended ticket have their own reasons; a command whose title ends in "…" opens a window and ends the request ("Vestra · Opened …"). The steps before a failure stay and keep their Undo.
- Undo and commands (v1): commands cannot be undone. The result names them ("Vestra · Mute · Cannot be undone", or "Vestra · Rotate: 90°, Speed 1.25× · Cannot be undone: Rotate: 90°" with Undo for the speed), and Undo says "Vestra · Undone · Cannot be undone: …". A toggle or radio is not restored either: that would need `commands.run` with a ticket the Undo action does not get.
- Undo compares the speed with a tolerance of 0.005 (a player that rounds the speed no longer reads as "changed since"), and a second press while an undo runs does nothing (the Undo command is busy meanwhile) instead of reporting "the speed was changed since".
- Consent scope v2: the consent now names the command list ("…the player's command list (names, menus, keys and whether each is on or available)… track and chapter titles… are not sent"), so a consent given for the first slice (v1) is asked again. README: what is sent, what the player confirms, what cannot be undone.
- Tests (`tests/askvestra-commands.test.mjs`; the TestHost lists only the player's core commands and the plugin's own, so most tests answer `commands.list`/`commands.run` as the player does): the player's Mute through the real TestHost with the ticket; a command and a speed (step 1 of 2, the result, Undo); a disabled command; Don't Run on a destructive one; a third-party command after its confirmation; an unknown id refused before the speed step; a window command ending the request; personal rows never sent and refused when named; consent v1 asked again and saved as v2; Undo tolerance and the double press.
- **Ask Vestra, first slice** (design: PROPOSAL §9 step 4; built-in only). The plugin puts up the command palette's first row (`palette.lead`): "Ask Vestra: <typed text>" with the AI icon, the field's placeholder "Type a command or ask Vestra", "Type a request or a question" after the title while nothing is typed, and "Set up a model first" on the right while no provider, model and key are set up (judged by the settings alone; the keychain is read only on Enter). Enter on the row: with nothing set up, the settings page opens; with an empty query, the AI window opens; otherwise the first request to a recipient asks once (the player's confirm dialog: "Ask Vestra sends your request to <provider>", naming what is sent: what was typed and the playback state; Continue / Cancel; remembered per provider, and per Base URL for a custom endpoint; the consent has a scope, so a later version that also sends the command list asks again). Requests made while the dialog or a keychain read is pending share one dialog, and only the latest goes on. Then the model (the plugin's own provider, model and key) plans the steps and they run. This slice has one kind of step, a playback speed of 0.25–4× set with the plugin's own `player.setRate`: "1.25× speed" shows "Vestra · Planning…" with **Stop**, then "Vestra · Speed 1.25×" with **Undo** (several steps: "Vestra · 1/2 · …" while each runs). The plan is checked before any step runs (at most 8 steps, known kinds, the speed in range); a refused plan, a model error ("Vestra · Could not reach <provider>: <message>"), a sentence instead of steps, a step the player refuses ("Nothing is playing") and the 90 s limit each end the request with an OSD line, and the steps already done stay and can be undone. While a request runs the palette row shows "Vestra is working · Planning…" or "… · Step 2 of 3 · Speed 1.25×" with "Enter stops"; Enter there, the OSD's Stop or the palette command "Vestra: Stop" stops it, and a new request stops the one running. "Vestra: Undo Last Request" (also the OSD's Undo) restores the speed from before the request, newest step first; a step leaves the journal only once restored, so a failed undo ("Vestra · Undo failed: Nothing is playing") can be tried again, and a speed changed since the request is left alone ("Vestra · Not undone: the speed was changed since"; the entry goes). A Stop or a newer request that lands while a step (or an undo) reads the player state changes nothing more: the check comes right before `setRate`, and a stopped request never shows its result line over the newer one. Up to 10 requests are kept in session storage (they survive standby, not a restart). Undo covers only what the plugin restores with its own capabilities; running player commands (`commands.run`), picture effects, presets and the chat record come with the next steps.
- How a request reaches the model: a worker of its own per request (profile `ask`: no file or documentation tools, no session file, only the `run_steps` tool, whose result ends the turn without a further model call; at most 4 model calls, thinking Low). The model gets the request and the playback state (open, playing, position, duration, speed), never the file name or path; the key stays in the worker's memory as for the chat. pi always writes the working directory into the system prompt (`<cwd>`); the ask profile gives it a neutral `/vestra` instead of its folder under the data directory, which would name the user's home and account.
- Manifest: `palette.lead` (built-in only), `playback.read`, `playback.control` and `ui.osd`. No `events`: the plugin reads the state when a request starts (`player.refresh`), so it does not follow playback while idle. New texts in all six languages (machine, marked `x-machine`).
- Tests (`tests/askvestra.test.mjs`, a local mock model; the TestHost as a built-in): the row and its note, its translation, a development load refused, no model, an empty query, consent (Cancel sends nothing; asked once), plan → setRate → OSD → Undo (also several steps), Stop from the status row and from the OSD, a new request replacing the running one, a model error, a sentence instead of steps, refused plans, nothing playing; the model sees no file name, no path of the data directory, home or temporary folder, and gets only `run_steps`; Stop landing while the step reads the state; Undo of a changed speed and a retried failed undo; two requests during one consent dialog; a new Base URL asks again.

Plugins this conversation installed stay installed (the player owns them) and the confirmation lists them; each install from a conversation is now recorded in its `meta.json` (`installed`), so a plugin of the same id installed from elsewhere is not counted. A run in the conversation stops first; deleting the open conversation shows a new, empty chat; a message sent or a tool that finishes while the conversation is deleted does not bring it back. A delete that fails says so in the conversation shown, and a conversation whose `meta.json` survived stays in the list. There is no undo.
- Reasoning models think again. Custom endpoints registered their model with `reasoning: false` and every session ran with thinking off, so a reasoning model such as MiniMax-M3 wrote its reasoning as ordinary replies (one session: 79 messages of 3–7k characters). Now the thinking level is **Low** by default (Settings ▸ Thinking: Off / Low / Medium, with the note that thinking tokens are billed like the answer); pi's catalog says which of its models reason, and for a custom endpoint only ids of clear reasoning models do (MiniMax M, DeepSeek R1 / reasoner, QwQ, o-series, GPT-5 but not its chat variant, gpt-oss, Claude 3.7 and 4+, Gemini 2.5+, Grok 3 mini, Magistral, ids with "thinking" or "reasoning" but not "non-reasoning" or "instruct"); hybrid families (Qwen3, DeepSeek V3.x, GLM, Kimi K2, Grok 3/4) default to no thinking. **This model can think before it answers** in the settings overrides it. An endpoint that refuses the reasoning parameters gets its own error, with Open Settings, naming both settings. A custom reasoning model gets 16384 output tokens, so the thinking budget (2048 low, 8192 medium) leaves room for the answer and its tool call. A change of thinking, model or key applies to the next message also when the agent was generating at the time (a new agent process continues the conversation). An unknown thinking level in the saved settings means Low instead of resetting the settings.
- Thinking and the notes the AI writes between tool calls are one collapsed line per turn, "Thought for 12 seconds" (or "3 progress notes" without thinking, "Thought process" for older conversations, whose thinking is shown the same way); a click, or Space / Enter once Tab reached it, shows them dimmed; screen readers see an expandable button. The answer is what the AI wrote after its last tool call; a turn that ends without one (the summary came with the last tool call, Stop, a timeout, an error) shows its last note as the answer. A collapsed line sends no text to the window, so long thinking costs the conversation list nothing. This replaces the rule that hid one short opening line.
