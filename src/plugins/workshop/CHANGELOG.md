## 2.2.39

- The vendored SDK is 1.7.16 (`npm run vendor:sdk`), the version the player now uses. 1.7.15: `PaletteLeadOptions.status.state` (`working`, the default, or the end states `done`, `failed`, `note`), which the player's new status strip reads. 1.7.16: `CommandRunOptions.then` (the rest of a plan, asked about once), and the TestHost models plans, counts `palette.lead.set` texts as shown (translated, filled in, one line) and judges `dangerous` by the Settings and Reset menus over the whole path, as the player does; no Workshop test needed a change for the stricter checks. Who must change: nobody.
- **One approval for the whole request** (Ask Vestra UX PROPOSAL step 3, P2 and P4; the player's approval sheet, doc/architecture/palette-lead.md §2 and §2.1). The first `commands.run` of a request carries `then`, the ids of the steps after it, so when any step asks first (a destructive command, Close, Quit, the Settings or Reset menus, a command of a plugin that is not built in) the player asks once, before anything runs, on its approval sheet listing every step; the later steps go without `then` and use up the approved plan without asking again (a step the model repeats too). The plan ends at the first command that opens a window (its title ends in "…"), as the request does, so the sheet lists only the steps that will run. Don't Run on the sheet runs nothing and ends the request with "Stopped: nothing was run"; "Stopped: <command> was not run" stays only for a later step the player asks about on its own (it no longer holds the plan for it; the plugin cannot reach this by itself). A `busy` refusal shows the player's message as given ("Step 1 failed: another command of this request is waiting for the user's answer"), no longer "<command> is busy" (PROPOSAL F4); the text "{} is busy" is gone from the catalogs.
- Tests: one sheet answer covers a plan of five steps with two that ask and a repeat (the sheet lists all five, the first run carries the other four, the later ones none); Don't Run on the sheet runs nothing, not even the steps that do not ask, and no later step is tried; a plan entry the player no longer holds asks again and Don't Run then names that step; busy passes the message through; the plan stops at a window command; plans of 5, 6, 7 and 8 steps ending in the player's Close run with one answer within the TestHost's limits (its own plan model and rates); an 8-step plan sends `then` once and keeps each step at least `STEP_GAP_MS` after the one before; `pace` waits the gap after one answer and the second after four; Stop during the gap.
- **Ask Vestra reports in the status strip, not on the OSD** (Ask Vestra UX PROPOSAL step 2, P1 and P3; user rulings 2026-11-12). The plugin no longer calls `osd.show` and no longer declares `ui.osd`: there is no "Planning…" OSD line with a Stop button, no result, failure or "Stopped" line. Everything goes through the palette row's `status`, which the player shows in a strip where the palette was while it is closed: "Planning…" (working) while the request waits for the key or the consent and while the model plans; from the first step on the player writes each step itself ("2/3 · <command>", from `step`/`of`, still passed for a request of several steps); then one end state: `done` "Done · <commands>" or "Opened <command>"; `failed` "Step {0} failed: {1}" (a step the player refused, or a step of the plan that is no command); `note` for the model's sentence, "Stopped", "Stopped: nothing was run" (Don't Run on the first step; "Stopped: <command> was not run" when steps before it ran, until the approval sheet asks before the first step) and every other error ("Could not reach …", "Took too long", "The model gave no steps", "The plan has more than 8 steps", "Cannot read the API key; …"). The player times the end state and shows it once; the plugin sets it after the request is no longer current, then the row without a status, then `palette.lead.done` at once (no timer of its own). Stop while the request waits for the key or the consent also shows "Stopped". A replaced request shows nothing. Stop is Enter on the status row, the strip's Stop button or "Vestra: Stop". Nothing reads the query after the run event, so Shift+Enter clearing the palette's field changes nothing here.
- Texts: the "Vestra · " prefix is gone from every Ask Vestra line (the strip's icon says who speaks); the row's planning status is "Planning…" (was "Vestra is working · Planning…", which the strip would have shown; the step status "Vestra is working · Step {0} of {1} · {2}" and "Enter stops" stay); new "Done · {}" and "Stopped: nothing was run"; all six languages (zh-Hans from the PROPOSAL §4.5 copy, the others machine-translated, `x-machine`).
- Every status text fits the player's limit (`status.text`: 1–80 characters as shown, translated and filled in, counted as Unicode scalar values like the host's `chars().count()`); a longer one was refused (`invalid`) and the user saw nothing, as with a long provider error or the result of an 8-step plan. `askvestra/status.ts`: status texts are built as lines (templates, data, lists); `fit` counts each template's own words in the interface language (`WORDS`, one row per language; a test checks it against every catalog) and the list separators, and cuts the data in order with a trailing "…" (a result list keeps whole labels while they fit and ends with the cut one). This covers the working status (the step label too) and every end state; the model's sentence and error messages are first made one line of at most 80 characters, by code points. The provider name is a line as well (`providerName`), so "Custom · OpenAI format" is counted in the language it is shown in. Tests (`tests/askvestra-status.test.mjs`): `WORDS` equals every catalog, the separators are the player's, and long cases (sentence, emoji and CJK, 8 long labels, each step failure, provider errors, a declined step, the step row) are at most 80 characters in all seven languages with "…"; `tests/lead-status.mjs` checks after every Ask Vestra test that each `palette.lead.set` status the plugin sent is 1–80 characters as the player counts them and that no lead-row update was refused; a long model sentence in English and Chinese ends at exactly 80 with "…".
- Store fallback (user ruling 2026-11-12, rule V1 without its "say which kind of plugin" half): the prompt says that only when no listed command can do what the user asked but a plugin for the player could (online video sites such as YouTube or Bilibili, games and emulators, cutting and exporting clips, extra video filters or upscaling shaders), the model runs Plugin Store… as the only step, and that a listed command that can do it is used instead. Benchmark behind the ruling: 0/20 false store runs on requests a listed command does, 9/10 store runs when needed. Plugin Store… ends in "…", so the request ends there ("Opened Vestra Player: Plugin Store…").
- Tests: the end state sent for each outcome (done, opened, failed step, refused plan, model sentence, provider error, too many steps, Stopped from the row, the palette command, the paced wait and the waiting request, Don't Run with and without earlier steps), only one end state per request and none for a replaced one, the order end state → idle row → `palette.lead.done`, `step`/`of` passed, no `osd.show` at all, and the store-fallback text in the prompt (without the left-out half).
- Steps are paced to the player's rate for one ticket (4 `commands.run` a second): each step after the first waits until `STEP_GAP_MS` (260 ms) after the player answered the step before, and until one second after it answered the run four steps before (`pace` in `askvestra/ask.ts`; the gap alone already keeps the rate, the second rule stays as a guard). Before, a plan of 5 to 8 steps of commands that answer at once failed at step 5 with "Step 5 failed: Too many commands at once" (reproduced with the TestHost, which applies the player's limits), and each step's line in the strip could last a few milliseconds (UX PROPOSAL §4.2: each step at least about 250 ms, F2). Stop during that wait ends the request at once.
- The row says "Vestra is working · Planning…" from the moment a request arrives, also while it waits for the keychain or the consent dialog, and Enter on it (or Stop) then ends that request before anything is sent. With the player's row rule from the same change (`command_palette::lead_shows_status`: the status also shows while the query is still the one sent with Shift+Enter), a second Enter after Shift+Enter stops the request instead of sending it again. When the player refuses the consent dialog (`busy`: another native dialog is open), the row and `askvestra.working` go back to idle. Tests: an 8-step plan runs all steps, `pace` never waits less than the second (a timer may fire early, so it reads the time again), Stop during the wait, the row working from the first moment and Enter on it stopping, the refused consent dialog.

Who must change: nobody.
- **Ask Vestra** (design: PROPOSAL; built-in only; user ruling 2026-11-11: Ask Vestra runs commands only, and commands take no parameters). The command palette's first row (`palette.lead`) reads "Ask Vestra: <typed text>" with the AI icon; the field's placeholder is "Type a command or ask Vestra", "Type a request or a question" follows the title while nothing is typed, and "Set up a model first" shows on the right while no provider, model and key are set up (judged by the settings alone; the keychain is read only on Enter). - What the model gets: the palette's table from `plugin.commands.list()`, one line per command (id, English label and the shown one, place, keys, state: disabled with its reason, busy, toggle or radio on/off, "asks the user first", third-party with its plugin), sorted so it stays the same while the table does; the request; whether something is open and playing (for toggles such as Play/Pause). Never the file name or path, nor a path of the machine (pi's `<cwd>` is a neutral `/vestra`). Left out of the table (doc/architecture/palette-lead.md, "Personal data"): Ask Vestra's own commands, the palette itself, the rows built-in plugins make from the user's data or the media's metadata (Recently Played, audio and subtitle tracks, audio devices, chapters, bookmarks), and any row of a plugin that is not built in whose title or path looks like a file name, a path or a URL.
- Consent: the first request to a recipient (a provider; a custom endpoint per Base URL) asks once with the player's confirm dialog ("Ask Vestra sends your request to <provider>", naming what is sent; Continue / Cancel). It is saved with a scope (v2: the request, the command list and whether something plays), so a version that sends more asks again. Requests made while the dialog or a keychain read is pending share one dialog; only the latest goes on.
- The plan: the model calls the tool `run_steps` once with up to 8 `command` steps; every id is checked against the table it was given, and any other step kind is refused, before anything runs ("There is no command “…”", "Vestra cannot do “…”", "The plan has more than 8 steps"). A sentence instead of steps is shown as it is. A worker of its own per request (profile `ask`: no file or documentation tools, no session file, only `run_steps`, whose result ends the turn without another model call; at most 4 model calls, thinking Low, 90 s).
- Running: each step through `plugin.commands.run` with the ticket of the palette's run (and `step`/`of` for several steps, for the player's own line "Vestra Player AI · 1/2 · …"); the player checks and confirms (destructive commands, Close and Quit, the Settings and Plugins menus, every third-party command). The OSD shows "Vestra · Planning…" with **Stop**, then a result line listing the commands that ran ("Vestra · Rotate: 90°, Vestra Player: Mute"). Don't Run stops the whole request ("Vestra · Stopped: <command> was not run"); a disabled command fails the step with its reason; busy, gone, the rate limit and an ended ticket have their own reasons; a command whose title ends in "…" opens a window and ends the request ("Vestra · Opened …"). A model error reads "Vestra · Could not reach <provider>: <message>". The steps before a failure stay.
- No Undo: nothing Ask Vestra does is its own change (an earlier slice set the speed directly and could undo it; both are gone with the ruling). A command's effect is changed back as by hand.
- Stop and replacing: while a request runs the palette row shows "Vestra is working · Planning…" or "… · Step 2 of 3 · <command>" with "Enter stops"; Enter there, the OSD's Stop or the palette command "Vestra: Stop" stops it, and a new request stops the one running. The player keeps the plugin out of standby during a request because one of its commands is busy (doc/architecture/supervisor.md §4): `askvestra.working`, a panel-only command of a plugin without a panel and without keys, so it is in no menu, palette or bar (Stop cannot carry the flag: the player does not run a busy command).
- Manifest: `palette.lead` and `commands.run` (both built-in only), `playback.read` (whether something plays) and `ui.osd`. No `events` and no `playback.control`. New texts in all six languages (machine, `x-machine`).
